\subsection{Preliminary}
A migration task $\mathcal T=(P,L_s,F_s,L_t,F_t,W)$ specifies a source program $P$, its language and framework $(L_s,F_s)$, the requested target environment $(L_t,F_t)$, and an editable file scope $W$. Migration produces a target program $\hat P$ that preserves the source's training behavior. The scope can include the translated program, its supporting library, or a repository. An edit modifies code within $W$.

At step $t$, we record source observations $(e_t,v_t,g_t,\theta_{t+1}-\theta_t)$ and target observations $(\hat e_t,\hat v_t,\hat g_t,\hat\theta_{t+1}-\hat\theta_t)$, with numerical values recorded when available. Here $e_t$ records the execution outcome, including success or an exception, $v_t$ contains selected forward values and losses, $g_t$ contains gradients, and $\theta_t$ denotes the parameters before the update. After aligning corresponding tensors and parameters, we define
\begin{align}
d_{\mathrm{execution},t}&=\mathbf{1}[e_t\ne\hat e_t], &
d_{\mathrm{forward},t}&=v_t-\hat v_t,\\
d_{\mathrm{gradient},t}&=g_t-\hat g_t, &
d_{\mathrm{update},t}&=(\theta_{t+1}-\theta_t)-(\hat\theta_{t+1}-\hat\theta_t).
\end{align}
For a numerical comparison $d=x-\hat x$, $d\simeq0$ denotes agreement within its tolerance, such as $|d_j|\leq\alpha+\beta|x_j|$ for absolute tolerance $\alpha$ and relative tolerance $\beta$, or a specified norm bound. Forward values determine the loss, differentiation produces the gradients, and the optimizer uses those gradients and its state to update parameters. The updated parameters then affect subsequent forward computations.

The LLM $M$ performs translation, investigation, and repair under role instructions $A_T$, $A_V$, and $A_R$. The Orchestrator $\mathcal O$ evaluates candidates and manages their shared investigation and repair budget $B$. In the algorithms, $S.\hat P$ is the candidate, $S.m$ contains its measurements, $q$ is its verification status, and $H$ is a conversation. Context $C$ retains evidence and provides tools; for repository tasks, it also stores the dependency plan and local check results. A submission sends the complete candidate for external verification after a repair stage that can contain several LLM calls, tests, and edits. Each $\textsc{LLMCall}(M,A,H,b,B)$ invokes $M$ with instructions $A$ and conversation $H$, charging its usage to the stage allowance $b$ and shared budget $B$. The Orchestrator counts each submission against $B$.

\subsection{Verifier Agent with Layered Diagnosis}
\label{sec:hierarchy}
% Keep wrapping local to this subsection.
{
\begin{wrapfigure}{l}{0.55\textwidth}
\begin{minipage}{\linewidth}
\setlength{\intextsep}{0pt}
\begin{algorithm}[H]
\caption{Layered Diagnosis}
\label{alg:diagnose}
\raggedright
\begin{algorithmic}[1]
\Require $\mathcal T,S,M,B,C$
\Ensure Evidence $E$
\Function{LayeredDiagnosis}{$\mathcal T,S,M,B,C$}
  \State $H\gets\Call{StartConversation}{A_V,\mathcal T,S}$
  \State $b\gets\Call{DiagnosisAllowance}{B}$
  \State $\mathcal D:\ \mathrm{execution}\to v_t\to g_t\to\Delta\theta_t\to v_{t+1}$
  \While{$\Call{WithinLimits}{b,B}$}
    \State $H\gets C.\Call{PrepareContext}{H,S}$
    \State $(\ell,h,a)\gets\Call{LLMCall}{M,A_V,H,b,B}$
    \State $H\gets\Call{ToolFeedback}{a,H,S,A_V,C}$
    \State \textbf{if} $a.\mathrm{complete}$ \textbf{then break}
  \EndWhile
  \State \Return $\Call{PublicEvidence}{H,C}$
\EndFunction
\Function{ToolFeedback}{$a,H,S,A,C$}
  \State $(C,S,r)\gets C.\Call{ExecuteTools}{a,S,A}$
  \State \Return $H\mathbin{\|}(a,r)$
\EndFunction
\end{algorithmic}
\end{algorithm}
\end{minipage}
\end{wrapfigure}
The Verifier Agent receives the Translator Agent's candidate and the Orchestrator's measurements. It uses Layered Diagnosis to focus its investigation on the computations responsible for observed discrepancies. For an \textbf{execution discrepancy} ($d_{\mathrm{execution},t}=1$), it inspects the exception and the calls that produced it. For a \textbf{forward discrepancy} ($d_{\mathrm{forward},t}\not\simeq0$), it traces the operators that produce different values and tests the suspected computation. When forward values agree but a \textbf{gradient discrepancy} ($d_{\mathrm{gradient},t}\not\simeq0$) remains, it examines parameter registration and the path from the parameters to the loss. When both forward values and gradients agree, it investigates an \textbf{update discrepancy} ($d_{\mathrm{update},t}\not\simeq0$) through the optimizer's rule and state. The first step with an observed discrepancy further guides this investigation because a changed update can alter later forward computations. The LLM selects code inspections and tests that distinguish possible causes, then records the code locations and observations supporting its hypotheses. These records form the evidence for the independent handoff to the Repair Agent.

\cref{alg:diagnose} expresses this reasoning through the training dependency relation $\mathcal D$, where $\Delta\theta_t=\theta_{t+1}-\theta_t$. The symbols $\ell$ and $h$ summarize the LLM's choice of computation and hypothesized cause within a call, and $a$ is its tool request or completion response. The Verifier uses both agreement and disagreement between layers to select $\ell$, then tests $h$ against code and execution evidence. The shared \textsc{ToolFeedback} operation executes requests in order and adds their results to the conversation. During investigation, the Verifier Agent can create and run scratch tests while candidate and supporting library code remain unchanged.\par}

\subsection{Repair Agent with Evidence Handoff and History}
\label{sec:repair-agent}
% Keep wrapping local to this subsection.
{

Independent evidence handoff gives the Repair Agent the Verifier Agent's recorded code observations, test results, and hypotheses, identified as the Verifier Agent's findings. The Repair Agent reassesses this evidence, runs further tests, and edits files in $W$, including supporting library code when the task permits it. The Orchestrator verifies each submission and returns the remaining discrepancies to guide the Repair Agent's next investigation and edits.
\Needspace{15\baselineskip}
\begin{wrapfigure}{l}{0.55\textwidth}
\begin{minipage}{\linewidth}
\setlength{\intextsep}{0pt}
\begin{algorithm}[H]
\caption{\textsc{Repair}$(\mathcal T,S,E,q,M,B,C)$}
\label{alg:repair}
\raggedright
\begin{algorithmic}[1]
\State $H\gets\Call{IndependentHandoff}{A_R,\mathcal T,E,C}$
\While{$\Call{SubmissionsLeft}{B}\land\allowbreak\Call{BudgetLeft}{B}$}
  \State $H\gets H\mathbin{\|}S.m$; $b\gets\Call{RepairAllowance}{B}$
  \While{$\Call{WithinLimits}{b,B}$}
    \State $H\gets C.\Call{PrepareContext}{H,S}$
    \State $a\gets\Call{LLMCall}{M,A_R,H,b,B}$ \Comment{Test and edit}
    \State $H\gets\Call{ToolFeedback}{a,H,S,A_R,C}$
    \State \textbf{if} $\Call{RepairComplete}{a,H}$ \textbf{then break}
  \EndWhile
  \State $(S.m,q)\gets\mathcal O.\Call{Submit}{S.\hat P,B}$
  \State \textbf{if} $q=\mathrm{accepted}$ \textbf{then return} $(S.\hat P,q)$
\EndWhile
\State \Return $(S.\hat P,q)$
\end{algorithmic}
\end{algorithm}
\end{minipage}
\end{wrapfigure}
Repair history preserves earlier edits, observations, and hypotheses across attempts. The continuing conversation includes failed tests and verification feedback, allowing the agent to relate a changed result to the preceding modification and revise explanations that did not resolve the fault. The current candidate also persists, so later attempts build on applied changes.

\cref{alg:repair} reuses \textsc{ToolFeedback} from \cref{alg:diagnose}, with $H\mathbin{\|}x$ denoting the addition of a record $x$ to the repair history. Its \textsc{RepairComplete} condition requires a completion response, an applied edit in the current stage, and a test executed after the last edit. If an edit or test is missing, the conversation requests that action within the remaining budget. The Orchestrator evaluates the candidate when the repair stage ends.\par}

\subsection{Repository Coordination}
\label{sec:repository-method}
Repository migration raises two problems that single-program migration does not: a repair may span several files that depend on each other, and evidence gathered on one file must remain available while the agent works on others. Repository context management addresses both through three components, described below.

\textbf{Repository Structural Analysis.} This tool returns an inventory of the target repository: its files, the imports among them, the functions and classes each file defines, and the cells of each notebook. It also lists target files that are not yet assigned to any work unit, showing which parts of the repository remain unplanned. The agent invokes the tool on demand; it is not run at initialization or when the context is rebuilt.

\textbf{Repair Dependency Graph Planning.} Based on this inventory, the agent partitions the target files into \emph{work units}. Each unit specifies the files it may edit, a repair goal, and the tests that check it, and declares the units it depends on; together, the units form a directed acyclic graph $C.G$. The agent may start a unit only when the checks of its prerequisite units remain valid, and may edit only the files assigned to that unit, so prerequisite units such as shared implementations are repaired before the units that depend on them. For each unit, LaDiM stores the results of syntax checks and selected tests in $C.Q$, together with the code version on which they ran. When a file or the plan changes, these results are invalidated for the affected units and all of their dependents, which must then be checked again. Unit checks only guide the agent; acceptance is decided by the Orchestrator, which verifies the complete repository, including its entry points and training computations.

\textbf{Evidence archive and context reconstruction.} Tool observations, code read by the agent, measurements, hypotheses, and conversations are stored in an archive $C.E$ outside the editable workspace, each tagged with the code version it describes. When evidence is handed to the Repair Agent, when the agent switches to another work unit, or when the conversation exceeds 75\% of the context capacity, \textsc{PrepareContext} replaces the conversation with a compact one. The new conversation contains the current plan and progress, the structured findings and hypotheses, the latest measurements and tool results, and previously read code that is relevant to the active unit and unchanged since it was read. Notebook tools let the agent read and edit individual code cells, with a syntax check after each edit.

\cref{alg:repository} connects these components to \cref{alg:diagnose,alg:repair}. \textsc{UpdateDependencyGraph} applies Repair Dependency Graph Planning, and \textsc{Execute} handles unit selection, file and notebook operations, tests, and evidence retrieval. Each operation updates the shared state $S$ and context $C$, and returns an observation $o$ together with the set $U$ of units affected by changes to files or the plan. All work units share the repository files, the repair history, and the total budget.
\begin{algorithm}[!htb]
\caption{Repository migration and repair coordination}
\label{alg:repository}
\begin{algorithmic}[1]
\Function{RepositoryMigrate}{$\mathcal T,M,B$}
  \State $C\gets\Call{RepositoryContext}{\mathcal T}$
  \State $S.\hat P\gets\Call{LLMTranslate}{M,A_T,\mathcal T}$
  \State $(S.m,q)\gets\mathcal O.\Call{Verify}{S.\hat P}$ \Comment{Complete repository}
  \State \textbf{if} $q=\mathrm{accepted}$ \textbf{then return} $(S.\hat P,q)$
  \State $E\gets\Call{LayeredDiagnosis}{\mathcal T,S,M,B,C}$ \Comment{\cref{alg:diagnose}}
  \State \Return $\Call{Repair}{\mathcal T,S,E,q,M,B,C}$ \Comment{\cref{alg:repair}}
\EndFunction
\Function{$C$.ExecuteTools}{$a,S,A$}
  \State $r\gets[\,]$
  \ForAll{$c\in a.\mathrm{tools}$}
    \State $U\gets\varnothing$
    \State \textbf{if} $c.\mathrm{kind}=\mathrm{structure}$ \textbf{then} $o\gets\Call{RepositoryStructuralAnalysis}{C,S}$
    \State \textbf{else if} $c.\mathrm{kind}=\mathrm{plan}$ \textbf{then} $(C.G,U,o)\gets\Call{UpdateDependencyGraph}{c,C}$
    \State \textbf{else} $(C,S,o,U)\gets\Call{Execute}{c,C,S,A}$
    \State $C.E\gets C.E\mathbin{\|}(o,\Call{CodeVersion}{S})$; $r\gets r\mathbin{\|}o$
    \State $C.Q[U\cup\Call{Dependents}{C.G,U}]\gets\mathrm{invalid}$
  \EndFor
  \State \Return $(C,S,r)$
\EndFunction
\end{algorithmic}
\end{algorithm}
