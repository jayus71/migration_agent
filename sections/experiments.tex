\section{Experiments}

\subsection{Experimental Setup}
\label{sec:setup}

\textbf{Tasks.}
The main comparison contains 50 PyTorch-to-MindSpore migration tasks covering tensor operations, CNNs, MLPs, Transformers, language models, and parameter and optimizer interfaces. Table~\ref{tab:collections} summarizes this collection and the supplied candidates used to study repair and training signals. Across languages, we migrate 18 Java/DJL programs to Python/PyTorch, comprising eight textbook examples and ten applications~\citep{djl2026,d2ljava2026}. Their sources average 221.2 nonblank lines. The public time series~\citep{jingles2026timeseries} and recommendation~\citep{chak2026twotower} repositories contain 13 and 24 code files or notebooks, totaling 865 and 2,086 nonblank lines, including original tests and notebook code cells.

\textbf{Evaluation protocol.}
Methods use common source programs, evaluation inputs, and corresponding initial parameters. Repair methods also share initial translations. Acceptance requires all applicable comparisons of execution, forward values, gradients, parameter updates, and specified optimizer state, together with shape, data type, and trainability checks. In the main migration comparisons, individual programs retain their own state over two consecutive steps, and repositories use three. Candidates that pass the public checks undergo confirmation on additional seeds. Main MindSpore absolute/relative tolerances are $10^{-4}/10^{-4}$ for forward values, $10^{-4}/10^{-3}$ for gradients, and $10^{-5}/10^{-3}$ for updates. BF16 matrix multiplication uses absolute tolerance $10^{-2}$. Appendix~\ref{sec:supplementary-protocols} gives the settings for each study.

The repository tables report \emph{behavior checks passed}, counting numerical comparisons, execution, and source behavior. Time series has 69 checks across public and confirmation evaluations. Recommendation has 145 public checks, comprising 114 numerical, 24 execution and differentiation, and seven source-behavior checks. Its ten original tests are reported separately. Complete repository acceptance also requires the declared entry points, file coverage, and documentation checks.

We retain the baselines' algorithms, prompts, tools, parsers, and retry policies, using the same DeepSeek backend. CodeTransEngine uses its direct translation configuration. Individual migration allows 40 investigation and repair calls, 120,000 output tokens, 1,800 seconds, and four external submissions. Repository limits are 80 calls, 480,000 output tokens, 3,600 seconds, and four submissions. A submission can follow several model calls and edits. Migration costs include the common initial translation once and all subsequent input and output tokens, including failed attempts. Supplied-candidate studies report repair costs. Failures remain in the task denominator, and acceptance at each budget scores the current candidate.

\textbf{Migration to MindSpore.}
LaDiM completes all 50 migrations with less than half the total tokens used by MatchFixAgent (Table~\ref{tab:main-results}a). Its savings extend to both faulty translations and programs that are already correct. On faulty inputs, LaDiM uses training discrepancies to investigate the code and guide corrective edits. On initially correct inputs, investigation and confirmation establish acceptance without corrective changes. Figure~\ref{fig:repair-comparison} separates these costs and shows lower token use on 27 of the 29 distinct inputs. LaDiM reaches 46/50 acceptance after one submission and 50/50 after two, retaining full acceptance at four. Seven of the nine faulty inputs are repaired at the first submission, and new measurements guide the remaining two corrections. The complete process uses 326 model calls, compared with MatchFixAgent's 619, with reduced input usage accounting for 93.0\% of the token savings.

\textbf{Migration across languages.}
LaDiM completes all eight textbook examples and one application in the Java/DJL collection, covering MatchFixAgent's accepted set and an additional recurrent network example (Table~\ref{tab:main-results}b). All repair methods preserve the initially accepted application. The added coverage comes from training examples where corresponding interfaces permit comparison of the training computations. LaDiM achieves the highest acceptance with 11.7\% fewer tokens than SWE-agent and 24.2\% fewer than MatchFixAgent.

\textbf{Repository migration.}
All three agents pass 69/69 checks and execute the three time series entry points, which share a model across a training script, notebook, and teaching examples. LaDiM completes repair in 35 calls, compared with 80 for SWE-agent and 69 for MatchFixAgent, using 68.1\% and 80.8\% fewer total tokens. This result extends the efficiency advantage to changes that must work across several callers.

On recommendation, LaDiM achieves the highest behavioral coverage, passing 130/145 checks and all ten original tests. Its repaired implementation supports reward model inference and retrieval, which remain unresolved in both baselines, and executes the training command. This coverage extends from the shared model computations to their use in training, inference, and retrieval, where repairs must work together across repository interfaces. Appendix~\ref{sec:repository-results} gives the detailed checks.

\subsection{Analysis Experiments}
\label{sec:fault-characterization}

\textbf{Repairing Natural Translation Faults.}
LaDiM repairs four of five initially incorrect translations and preserves all five initially correct programs, yielding 9/10 final acceptance (Table~\ref{tab:natural-repairs}). The baselines preserve the correct programs and leave all five faulty programs unresolved. An LSTM translation illustrates how successive measurements guide these corrections. After the first submission leaves an unregistered recurrent operator unresolved, LaDiM reproduces the failure, inspects registration, and adds the recurrence using target-framework operations. The second submission exposes recursive tensor indexing. A focused test identifies the dispatch cycle, and the third submission corrects it and passes loss, gradient, and update checks. As execution reaches further code, new measurements guide the next correction (Appendix~\ref{sec:natural-protocol}).

\textbf{Training Signals and Detection Latency.}
LaDiM's gradient and update checks detect their respective faults at step~1 in all 12 runs per fault, while the mean loss-difference curves cross the detection threshold at steps 31 and 18 (Figure~\ref{fig:gradient-drift}). These trajectories follow four models for 50 steps with source and target executions retaining separate state. Gradient faults can preserve current loss, and update faults can preserve forward values and gradients; their effects enter later forward computations through the changed training state. Individual loss trajectories cross within 50 steps in only 3/12 and 4/12 runs. Direct checks expose the affected computation as soon as it diverges. The comparisons use loss absolute difference, gradient norm absolute difference, and relative update L2 difference at thresholds 0.02, 0.05, and 0.03. With per-step synchronization, each target starts the checked step from the source state. Correct translations pass the recorded checks, with maximum loss difference $3.815\times10^{-6}$.

\textbf{Agent components.}
We cumulatively add a read-only Verifier investigation, independent evidence handoff, and repository context management to the Repair Agent on the time series repository (Table~\ref{tab:cumulative-components}b). Each condition runs once with the same initial candidate, full training signals, base repair tools, and total budgets. The base condition retains the repair prompts and tool assistance. Investigation continues in the repair conversation until the independent handoff is added.

All four conditions complete the migration and pass 69/69 behavior checks. The full method uses the fewest total tokens, 1.937 million, reducing cost by 68.4\% relative to the base Repair Agent. The cost of an independent handoff depends on how its evidence is carried forward: adding repository context management reduces investigation and repair input tokens from 5.731 million to 1.700 million. Retaining current findings and relevant code allows the Repair Agent to continue from the investigation with less repeated context.
