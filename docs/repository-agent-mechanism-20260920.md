# 完整仓库协调机制

用户要求仅为我们的方法设计完整仓库机制，baseline 保留原设置。新模式在 LaDiM 的独立调查与修复交接上增加仓库状态管理，已接入独立实现工作树，并完成时间序列仓库到原生 MindSpore 的一次验证。全部代码入口和核心训练数值通过；README 仍保留源框架说明，因此文档迁移尚未完成。

协调机制面向 Python 文件和 notebook，不包含时间序列、LSTM、已知错误或目标修复位置的规则；当前实证范围是一个小型教学仓库。仓库协调层与该案例的数值及入口测试分别实现。原来的精简方法继续用于小程序任务。

机制包含五部分：

1. 从公开代码提取顶层符号、方法、import 与 notebook 单元索引。语法错误、动态依赖缺口明确记录，不把语法依赖等同于实际运行依赖。
2. agent 提出功能单元、文件范围、接口目标、依赖关系与局部测试。控制器只检查路径和依赖图是否合法；不替 agent 指定故障分类或正确拆分。
3. 每次聚焦一个依赖条件已满足的单元。跨单元修改先更新计划，避免修改调用方时遗漏共同实现。
4. 每个单元有局部检查和文件状态；上游文件或计划改变后，使依赖它的检查失效。局部语法通过与实际测试通过分别记录，完整仓库是否接受仍由外部验收决定。
5. notebook 以单元源码读取和编辑，自动维护 JSON 格式并清除旧输出。切换任务单元时，只带入当前计划、独立调查结论和原始检查证据；完整工具轨迹保存在审计文件，避免重复发送 notebook 中的大量历史图片输出。

实现仓库中的 `autofix/autonomous/repository.py` 提供独立的 `RepositoryAgent` 与 `RepositoryTools`，实现索引、计划、聚焦、检查、notebook 单元编辑和按工作单元组织上下文；本论文工作区的 [`scripts/repository_agent_mode.py`](../scripts/repository_agent_mode.py) 保存对应源码。[`scripts/run_repository_agent_mode.py`](../scripts/run_repository_agent_mode.py) 执行单独的 LaDiM 条件；`scripts/test_repository_agent_mode.py` 直接测试框架模块，覆盖循环依赖、未知依赖、只读源文件、越界编辑、连带失效、notebook 编辑事务和角色交接。最终 12 项机制检查和 59 项原有 agent 检查全部通过。

单次推理上限与整仓库预算分别管理：本次修复每次最多输出 16,384 token，整个仓库共用 40 次调用、120,000 输出 token 和 1,800 秒，而非给每个文件重新分配一份预算。调查阶段最多 6 次调用，连续修复阶段最多 32 次，剩余预算支持外部验收后的修复。agent 可把有共同接口的多个文件纳入同一功能单元。当前运行并未增加模型或并发子代理。

本次评估仍使用同一份源仓库、共同初译、DeepSeek、40 次调用和 120,000 输出 token 预算。原来的 LaDiM 条件与仓库模式分别保留，不混为同一方法版本结果。先前读取整个 notebook JSON 导致大量输入 token，单元读取与局部上下文旨在减少这部分开销；是否带来实际提升，由同一产物标准和完整费用记录判断。

## 已发现的验收缺口

初版冻结验收实际执行了主脚本的完整训练流程和数值检查，但 notebook 仅做了语法与禁用导入检查。原 LaDiM、SWE 与 MatchFix 都通过该验收。随后只读运行各自 notebook，原 LaDiM 在 `.train()` 调用处失败，MatchFix 在 `nn.Module` 处失败，SWE 成功完成 100 个 epoch、200 个 MindSpore 自动微分批次和五幅图。源 PyTorch notebook 同样通过。所有原产物保持字节不变。

这些结果说明冻结验收的“通过”不能直接称为完整仓库成功。原始评分保留，notebook 执行作为额外核查单列。完整仓库模式需要实际执行所有公开入口，并对教学片段的共享上下文进行检查。后续若更改正式共同验收，应在新的协议记录中说明，并给比较方法相同的公开测试入口；不回写先前记录、不替 baseline 修复候选。

仓库模式在 32 次调用后通过初版冻结验收，修复阶段总 token 为 1,070,830；原 LaDiM 为 3,411,298，减少 68.6%。调用次数由 16 增加为 32。随后真实 notebook 执行发现参数格式化错误，按源教学顺序执行片段还发现缺少 DataLoader 名称。此前三个方法的片段也在相同位置失败。PyTorch 源 notebook 和源片段序列均实际通过，排除了把原本不可执行内容当作迁移失败的情况。

继续利用仓库模式原预算剩余的 8 次调用和第 4 次外部提交，加入 `entrypoints` 测试，提供 notebook 与片段的真实执行观测。原始结果、源码快照及调用记录保留，累计预算从第 33 次调用续接，既有 token 与时间计数全部继承。修复仅由模型在公开工具内完成，没有由主代理替它修改目标。这个追加观测只用于我们方法的开发；baseline 未重跑，因此不得把这次改进后的通过率作为共同反馈条件下的正式排名。

最终入口覆盖实现为 `scripts/repository_entrypoint_evaluation.py`，仓库模式的后续入口已默认同时要求核心三种子数值验收、完整脚本、notebook 和教学片段执行。原冻结主流程评分仍单独保存。最终报告同时列出完整费用和剩余范围，不从不同验收中选择有利数字。

补充入口运行达到累计 40 次调用后仍未通过完整验收，累计修复 token 为 1,833,632。主要工程问题是完整入口观测接入过晚，以及继承的每阶段 8 次调用限制把剩余预算切得过碎。完整协议启动时已经执行所有入口；独立调查最多 6 次调用，连续修复阶段最多 32 次，生命周期上限仍为 40 次、120,000 输出 token、1,800 秒和四次外部提交。这是独立保留的一次完整协议验证，初译与源程序继续复用，前面的开发费用单列；baseline 不追加模型调用。

## 最终验证结果

从共同初译开始的完整协议运行已经结束。第 1 次外部提交中，主流程与 notebook 通过，教学片段因 `DataLoader` 未定义失败。agent 在剩余两次模型调用内修改教学片段；第 2 次提交全部通过。目标文件的修改均来自被测 agent 的工具调用。

| 验证对象 | 最终结果 |
| --- | --- |
| 核心数值 | 3 个种子、各 3 次连续 Adam 更新均通过；比较前向值、损失、梯度和参数更新 |
| 主脚本 | 100 个 epoch、200 次原生自动微分调用、128 个训练预测、32 个验证预测和 5 幅图 |
| notebook | 10 个代码单元顺序执行通过，200 次原生自动微分调用和 5 幅图 |
| 教学片段 | 11 个片段按源教学顺序执行通过，200 次原生自动微分调用和 5 幅图 |
| 文档 | README 与源文件相同，仍有 PyTorch 安装与代码说明，尚未迁移 |

数值检查的三个种子用于验证同一候选。最大前向绝对差为 6.31e-6，最大梯度向量 L2 差为 1.41e-4，最大参数更新相对 L2 差为 0.00774，分别低于 1e-4、0.05 和 0.03 的阈值。notebook 和教学片段目前验证的是实际运行、预测形状、有限性、图表与原生训练执行；尚未独立比较它们与源端的完整数值轨迹。

本轮使用 40 次修复调用、2 次外部提交，修复输入 2,076,106 token，输出 100,365 token，其中推理 78,322 token；合计 2,176,471 token，耗时约 738 秒。加上共同初译的全部失败与成功调用，本候选端到端归属成本为 43 次调用、2,340,132 token。输出预算包含推理；输入累计量记录但未设置上限。

所有原方法运行、仓库机制开发和初译合计实际产生 163 次模型调用、13,551,013 token。原型的 32 次调用及其后续 8 次调用按累计 40 次核算，未重复加总。原始失败轨迹全部保留。本轮与旧条件使用了不同的入口反馈，且包含阶段预算调整，因此成本或通过情况的差异尚不能归因于某一机制。

最终代码增加了整份 notebook 写入的 JSON 与代码语法事务校验。这项保护是在最后一次运行启动后加入的，12 项机制测试已覆盖，模型运行使用的是启动时的旧模块。两个源码快照分别保存为 `repository-at-launch.py` 和 `repository.py`，避免把离线修正算作已完成的模型实验。

## 后续完整源仓库验证

Simple MoE 从原始源副本直接进入调查修复，在 36 次调用、120,000 输出 token 内没有修改生产文件。随后在双塔仓库增加按公开文件依赖先生成、再调查修复的阶段，初始短额度仍产生多次空内容截断。用户要求加长单次推理预算并保持请求前缀后，使用原候选和会话续接，单次上限提高到 32,768，累计输出上限提高到 240,000；源、验收和原费用均保留。

双塔最终六条模型路径能运行、十个原测试通过，但 CLI 和训练数值等价尚未通过。新增调用的输入缓存命中率为 98.21%。这次续接为保持前缀，不在功能单元切换时替换既有消息；依赖规划、编辑范围和局部检查继续使用仓库工具。此次不是对原单元上下文机制的独立消融。完整结果、预算变化和证据见[双塔试验报告](repository-twotower-20260920.md)。
