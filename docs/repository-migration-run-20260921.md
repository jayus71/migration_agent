# 仓库迁移统一比较

用户于 2026-09-21 授权改进上下文管理并开展实验。本轮沿用时间序列和双塔两个源仓库，比较 LaDiM、SWE-agent、MatchFixAgent，共六个修复条件。论文正文和旧实验结果保留。

## 方法与接入改动

LaDiM 将完整观察和会话保存在工作区外的证据归档中。Agent 可以通过只读工具，按记录编号、JSON pointer 和分页范围取回内容。首次选择工作单元、普通修复阶段的续接保留完整对话；独立角色交接、实际切换工作单元或消息达到上下文上限的 75% 时重建上下文。重建时保留当前计划、生成状态、完整假设与下一步、最新测量、最后工具结果，以及已读取且文件哈希仍匹配的当前单元代码，代码缓存上限为 120,000 字符。归档备注附有可直接使用的记录编号与指针。只有实际候选代码变化才使旧测量失效，新的失败测量会替换旧通过状态。

旧双塔第 33 次请求的离线回放从 932,245 字符降至 38,185 字符，保留全部 145 项数值检查、21 项失败和 CLI 失败。该回放使用模拟响应，测量的是上下文构造，未调用模型。

调查阶段最多六次调用、64,000 输出 token。剩余修复调用和输出按剩余外部提交次数分配，第一次修复最多 16 次调用，以便较早取得完整验收反馈。剩余资源交给后续阶段，整个条件的调用、输出和时间计数连续累计。

双塔数值 worker 改为调用候选仓库的 `train.train.make_optimizer(model, learning_rate=0.001)`，训练 CLI 也使用同一工厂。验收继续记录实际原生自动微分、梯度和参数更新，源端 Adam 和数值阈值保持原定义。公开任务说明工厂接口及源训练要求；开发审查中的优化器偏差推导未写入 agent 提示。

SWE-agent 和 MatchFixAgent 保留各自原生算法、提示、解析、工具组织与重试策略。SWE 的仓库入口校验复用此前审查过的接入版本，读取任务声明的入口。上下文归档与阶段分配仅作用于 LaDiM。

本轮上下文修正只修改 LaDiM 的 `autofix/autonomous/repository.py`。`agent.py`、`tools.py`、`baselines.py` 和 `swe_upstream.py` 与启动时快照的 SHA256 一致。四个 baseline 条件均使用 `memory_policy=native`、`workflow_policy=standard`，未配置 `repository_evidence` 工具，也未产生 `repository_context` 事件。MatchFixAgent 在第二次外部提交后继续修复，是其既定运行流程；它没有获得 LaDiM 的上下文改进。

## 共同输入和验收

每个仓库的三个方法使用字节相同的源程序、初译、公开任务和验收器。每次启动都检查输入哈希。

- 时间序列复用历史共同初译，包含原三次生成调用及失败费用，共 163,661 token。
- 双塔按公开文件导入关系顺序生成 21 个单元，包括非空 Python 文件及最终元数据、依赖和 README。每单元最多两次格式或语法生成，整次初译上限 48 次调用、240,000 输出 token、每调用 32,768、3,600 秒。生成阶段不调用数值验收，不筛选有利候选；所有生成尝试计费，失败和未生成状态保留。
- 三个方法从第一次调用起均可取得核心数值、声明入口、代码覆盖和文档依赖的公开反馈。时间序列包括主脚本、notebook 和顺序教学片段；双塔包括原测试、训练 CLI 和六条源端可执行训练路径。源端异常及空实现沿用源行为。
- 公开验收通过后，在相同候选上运行两个确认种子。数值比较共三个种子、各连续三步。时间序列的 notebook 和片段提供执行覆盖；核心模型提供配对训练数值测量。

修复条件的共同上限为 80 次调用、480,000 输出 token（含推理）、每调用 32,768、3,600 秒和四次外部提交。达到接受条件后停止。每个方法的端到端成本包含其全部修复调用和共同初译全部费用，物理初译只执行一次。输入 token 完整记账。

同一次运行在达到 40 次调用、240,000 输出附近保存当前候选和实际用量，不额外调用模型。这些观察点描述高预算运行的进度。

时间序列仓库中，三种方法均通过公开验收和两个确认种子。主脚本、notebook、教学片段的执行检查通过，各入口记录 200 次原生自动微分。确认种子复核数值与覆盖，完整 100 epochs 工作流和教学入口在公开验收中执行。LaDiM 用 35 次修复调用达到完整验收，端到端 token 比 SWE-agent 少 68.1%，比 MatchFixAgent 少 80.8%。该仓库的结果支持 LaDiM 在完成相同迁移任务时降低调用次数和上下文输入开销。

双塔仓库中，三种方法均用完 80 次调用，未通过完整验收。LaDiM 的原有 10 项测试、训练 CLI、文件覆盖和文档依赖均通过；六条可执行训练路径的每一步梯度检查均通过，仍有 12 项后续 item embedding 检查与 3 项参数更新检查失败。SWE-agent 通过原测试、CLI、覆盖和文档，但存在 40 项数值检查失败。MatchFixAgent 通过 CLI，存在 15 项数值检查失败，原测试因残留 PyTorch 导入而收集失败，文档检查未通过。双塔三个条件均未触发后续确认种子。

双塔的 LaDiM 数值记录含 145 项检查，两个 baseline 各 144 项：源行为匹配后的分支会生成不同数量的后续检查。完整验收仍使用同一协议和共同任务；这里按实际测量报告检查内容，不把这些检查数量作为方法成功率的分母。三个方法在两仓库上的完整接受数均为 1/2；本轮明确优势来自时间序列仓库的效率，双塔尚需改善连续训练中的数值一致性。

上述总 token 包含输入和输出；API 缓存命中输入另记在机器汇总中。人民币或美元费用需结合实际缓存和输出计费计算。

LaDiM 相对 SWE-agent 的数值检查通过比例高 21.9 个百分点，额外通过的内容主要来自训练返回损失、部分用户 embedding、梯度和参数更新。LaDiM 与 MatchFixAgent 均通过 99 项数值检查：LaDiM 完成奖励模型推理检索，MatchFixAgent 多通过一项参数更新。LaDiM 在原有测试、覆盖和文档上完成更多工作。当前双塔结果体现了 LaDiM 的仓库功能完成度，以及相对 SWE-agent 的训练一致性优势；连续参数更新仍是 LaDiM 的直接优化目标。

三个方法共同出现物品 embedding 在第二、第三步的 12 项失败。这解释了仓库级完整验收都失败的现象。LaDiM 的 15 项数值失败中，这一类占 12 项，其余三项属于参数更新。后续改进应检查跨步状态更新和优化器行为，并沿用现有数值阈值。

时间序列的每个种子有 23 项检查，三个方法均为公开种子 23/23、三种子合计 69/69。此前论文主集合的 50/50 表示另一批小程序迁移任务。仓库结果可报告检查通过数与 token 开销，并将完整仓库接受状态放在同一表中；时间序列的优势主要由完成相同验收所需的调用与 token 体现。

## 运行中发现的上下文缺口

时间序列的首轮 LaDiM 在 56 次调用后通过公开验收及两个确认种子，修复费用为 3,028,949 token，含共同初译为 3,192,610 token。SWE-agent 在 80 次调用后同样通过，修复费用为 8,036,164 token，端到端为 8,199,825 token。两者的源程序和任务均保持不变。

轨迹同时暴露出四项交接缺口：首次选择工作单元就重建上下文，引起刚读过的文件再次读取；计划版本变化使未变候选的测试被标为过期；结构化最终回复的顶层假设与下一步总结被当作长文本截断；部分备注缺少可直接检索的归档编号。完整观察与数值检查仍在，但工作状态的传递需要修正。[轨迹审查](../tmp/repository-run-20260921/context-progress-audit.md) 保存具体证据。

在双塔修复任务启动前暂停调度，已启动的三条时间序列进程继续使用原冻结实现。修正先在隔离运行时开发和离线验证，随后冻结同一份修正用于两个仓库的 LaDiM。有效 baseline、共同初译、源程序和验收全部复用。时间序列原 LaDiM 的完整通过结果与费用作为开发测量保留；另一次从共同初译开始的 LaDiM 验证用于评估修正后的实现。这项追加验证由实际交接缺陷触发，选择规则在新结果产生前确定。

双塔共同初译使用 20 次调用、240,000 输出 token，总费用 368,368 token。计划共 21 个单元，已尝试 18 个；截断失败和三个未尝试单元保留在共同候选状态中，由各修复方法自主处理。未据此生成或挑选另一份初译。

修正后的隔离验证实际执行 118 项检查，116 项通过、两项可选 MatchFix 集成跳过。真实轨迹回放确认首次选择单元后保留 301,336 字符的完整历史，结构化最终回复的 16,810 字符、五个假设与下一步总结完整保留，同时携带 16 项当前文件读取结果。上下文整理前后用量与计时器不变。安装后的上下文测试发现执行 31 次且全部通过，其中包含导入测试的重复执行。

最终时间序列 LaDiM 使用 35 次调用、2,614,230 端到端 token，通过两次外部提交完成验收。与保留的开发测量相比，调用从 56 次降至 35 次；这是两次实际运行的观察差异，独立消融尚未测量各项修正分别带来的收益。正式比较采用两个仓库相同的修正实现，开发测量保留在 `development/timeseries_initial_context`。
