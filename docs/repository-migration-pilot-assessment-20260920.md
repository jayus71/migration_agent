# 小型仓库 PyTorch → 原生 JAX 迁移评估

建议第一项选择 `jinglescode/time-series-forecasting-pytorch`，第二候选保留 `gauravchak/two_tower_models`。时间序列仓库的主要完整流程短、计算量小，源端已在服务器通过完整入口检查；双塔适合检验多文件依赖，但仓库本身存在未实现功能，不能仅运行基础双塔就宣布全仓库功能迁移成功。若本轮只选一个，选择时间序列。

本评估承接任务 [筛选易跑的 Torch-JAX 仓库](codex://threads/01a0a8cc-df81-72c3-9b23-49e02c5e7422) 的候选范围。此前基础双塔优先的判断针对基础模型子任务；本次按用户要求把完整仓库文件、训练入口和已有功能覆盖纳入考虑。没有使用模型生成或修复候选，也没有启动三方法正式比较。

本地抓取了三个上游仓库，记录当前提交与逐 Python 文件哈希，执行静态清点和服务器源端检查。行数均为物理行，包含注释、文档字符串和空行。

时间序列仓库将归一化、滑窗、训练验证划分、两层 LSTM、MSE、Adam、StepLR、验证和预测集中在 `project.py`。默认模型仅 17,025 个参数，CPU 足够。迁移范围可以清楚定义为整个仓库的可执行 Python 内容，主程序承担端到端运行验收，教学片段检查与主程序的一致性，不将这些片段当成额外独立仓库样本。

原仓库依赖 Alpha Vantage 在线行情。此次源端可行性检查使用 180 条明确标记的合成行情作为 API 响应夹具，保留原 `download_data` 解析逻辑；它验证程序能执行，不测量真实金融预测质量。完整入口最初在新版 NumPy 下于最后绘图的数组到标量赋值处失败。独立源环境固定 NumPy 1.26.4 后通过，未修改仓库文件。Matplotlib 旧参数 `grid(b=...)` 通过环境包装映射为 `grid(visible=...)`，使用无界面 Agg 后端。依赖兼容、固定外部数据和未来的目标框架转换分别留账。

正式评估需要冻结一份双方共用的价格序列和数据顺序。可以继续采用已声明的合成序列检验语义与流程，或在准备阶段加入一份有来源的固定历史价格文件；不能将合成数据结果写成真实股票预测效果。LSTM 迁移要对齐门顺序、权重转置、各层隐藏状态与偏置参数；训练验收还要保留 Adam 的 `betas=(0.9, 0.98)`、`eps=1e-9` 和学习率衰减行为。仅比较最终预测形状不足以确认这些部分正确。

双塔仓库有基础检索、用户历史编码、位置与用户去偏、轻量排序等模块。基础训练与现有测试通过，且自带合成推荐数据，不需要下载模型或真实推荐数据。它能提供比单脚本更有意义的多文件依赖、Embedding、Attention、Top-k 和自定义训练损失挑战。

完整性上有两个已确认的源端边界：`TwoTowerPlusLightRankerWithKD.train_forward` 只有 `pass`；奖励模型扩展的对齐损失停留在注释，函数返回继承的基础损失。现有十项测试没有覆盖全部排序变体。若采用此仓库，应把全部原文件纳入转换清单，保持既有功能及原本未实现行为，并在验收登记表中逐模块注明可测范围。不能为凑齐“全功能迁移”由我们补写源程序缺失算法，也不能只取基础模型后称为完整双塔仓库转换。想要第二个范围同样完整、源端功能均有验收的仓库，双塔仍需补做所有已实现公开入口的源端检查。

simple-moe 在 JAX 中还涉及数据相关的专家选择、布尔索引、原地累加、随机路由噪声以及 Dropout，代码量不能直接代表迁移难度。其 `_model_stack.py` 有外部运行时与原生 PyTorch 回退两条路径；本次检查运行的是未加载外部运行时的原生回退路径。`MoEMetrics.compute_metrics` 对多元素利用率张量调用 `.item()`，实际运行抛出异常。源代码还复用了 `total_loss` 作为批损失和累计量，训练报告语义需要单独核对。它适合后续挑战性迁移，目前不作为最省事的首批任务。

当前框架能复用自主调查、证据交接、修复、验收重试、DeepSeek 客户端和费用账本。仓库输入与原生 JAX 评估需要补接入：

| 接入环节 | 当前实现 | 仓库任务需要的准备 |
| --- | --- | --- |
| 公开源与可编辑目标 | `source.py`、`candidate.py` 及限定目录 | 完整只读源目录、独立目标目录、文件范围清单；允许正常的 Python、配置和依赖文件操作 |
| LaDiM 工具与快照 | 写入白名单、不可变文件检查、快照围绕既定文件 | 按任务清单扩展路径规则、源目录哈希、目标快照与执行隔离 |
| SWE 接入 | 原生工具保留，但挂载、Git 跟踪、写入范围及提示仍指定既定文件 | 扩展为完整目标仓库，并保留已验证的进程恢复修正；不改变原生算法与重试 |
| MatchFix 接入 | 当前 `_fragment()` 构造单个完整源模块与候选模块对 | 结合上游项目／fragment 输入组织，提供真实源目标文件和目录；文件对应仅表示迁移映射，不携带故障位置或正确目标 |

MatchFix 上游本身面向仓库验证修复，要求项目配置、片段和代码库；限制来自我们当前接入只喂一个模块对。准备阶段需要按其现有输入约定接入完整目录，保持上游语义分析、修复、判决编排及解析规则。不能给它加入我们的调查策略，或者把仓库机械串成一个伪 Python 文件。若必须增加跨文件任务调度，应明确记录这是新的接入层，并在正式比较前核对其没有额外修改方法的调用结构与预算。

服务器已有 Python 3.11、JAX 0.10.2、jaxlib 0.10.2、Flax 0.12.7、Optax 0.2.8 和 PyTorch 2.8.0 环境。此次额外依赖安装在独立的 `repository-pilot-assessment-20260920/assessment_env`，没有改动既有正式实验环境。源端兼容环境与目标 JAX 环境应分别冻结；前者的 NumPy 1.26.4 不能直接作为现有 JAX 0.10.2 的依赖环境。

建议三方法按同一端到端任务比较：每个仓库先由固定 DeepSeek 设置生成一份完整原生 JAX 初译，LaDiM、SWE-agent、MatchFixAgent 分别从它的独立副本开始。完整源代码、公开契约、可调用测试、起始候选与预算相同；三个方法独立修复，保留各自原生控制逻辑。初译仅生成一次，在每个方法端到端成本中归属，并单独记录初译通过情况。不给故障分类、目标修复位置、手写健康目标或其他方法轨迹。

这样单仓库是 1 次初译加 3 个修复条件；两仓库是 2 次初译加 6 个修复条件。先用现有每条件 40 次调用、120,000 输出 token、1,800 秒、4 次外部提交作试点预算，三方法同等适用。单仓库最多 121 次模型调用，两仓库最多 242 次，属于上限而非预计消费；初译请求上限单列，输入 token 按实测记录。三个验收种子只用于检验同一候选，不算三次独立迁移。只有一两个仓库时，结果定位为仓库案例与扩展验证，不能据此估计广泛的仓库迁移成功率。

验收建议包含相互独立的三层证据：

1. 文件与功能覆盖：核对整个源仓库的文件清单、已实现公开接口和目标产物；不能删除难模块、留空训练入口或仅返回固定结果。保留源端未实现接口的登记，不把它们算作已实现迁移功能。
2. 可执行流程：目标环境不安装 PyTorch/TorchAX，独立执行训练、验证、预测，以及适用的检索、检查点保存与恢复。允许 NumPy 承担数据预处理和绘图；模型计算、求导和优化器更新必须有 JAX 运行证据。
3. 数值语义：固定输入、源端导出的初始参数与参数映射，比较前向值、损失、梯度及至少连续两步更新，并测试学习率变化边界。使用 101、202、303 三个种子确认，公开开发输入与最终输入分开保存。阈值在实际模型调用前用健康参考及受控偏差校准。

随机性需要单独处理：PyTorch 与 JAX 使用同一个整数 seed 不会自动产生相同 Dropout 掩码。确定性前向可在推理模式比较；训练路径应采用公开定义的共同随机输入／掩码协议，再额外检查原生随机训练能执行。若首轮只验证关闭 Dropout 的训练配置，就必须把该配置范围写明，不能当作默认随机训练等价。参考数值由外部验收器保存，代理只能得到公开输入及实际测试观测。

正式运行前仍需完成完整目录接入、源端覆盖登记、目标运行隔离、数值校准和三种控制器的无模型模拟检查。本次已经完成候选筛选、源码规模登记、源端运行可行性验证及接入缺口定位；没有把这些检查称为 JAX 转换成功，也没有启动付费迁移。建议先完成时间序列仓库的准备，以一组三方法试点确认仓库流程；双塔随后作为第二个、多文件结构更明显的案例。
