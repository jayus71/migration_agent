# 双塔仓库迁移试验

本次按照用户要求，使用新的仓库机制尝试将 `gauravchak/two_tower_models` 迁移到原生 MindSpore。六条源端可执行路径已能运行，十个原测试通过；训练 CLI 和数值等价验收未通过，最终结果仍为迁移未完成。冻结源提交为 `cf86221775efec3184e83b9417bf9daeddc4e057`，包含 24 个 Python 文件、2,366 行。初始配置在付费调用前固定；用户随后授权提高输出预算并要求保持消息前缀，续接单独记录。

## 与 Simple MoE 的关系

Simple MoE 的失败运行已经启用了仓库规划、功能单元聚焦、上下文裁剪和独立调查交接。该运行从未翻译的源副本直接进入调查与修复循环，36 次调用耗尽 120,000 输出 token，其中推理为 104,663 token；8 次调用执行临时测试，目标生产文件没有修改。因此，失败同时暴露了生成阶段缺失和调查推进过慢的问题。它没有提供动态路由或训练转换本身无法完成的证据。

双塔的基础模型主要使用 embedding、线性层、矩阵乘法和 top-k，计算结构较规整。完整仓库还包含多头注意力、去偏模块、训练 CLI 和原有测试，其文件数和代码量均大于 Simple MoE，不能把它等同于一个简单的双塔层。

## 本次机制

先从公开源代码的 AST 提取文件依赖，对直接使用源框架的文件进行有界生成。每次请求读取当前源文件、公开接口约束和已生成的直接依赖，返回完整文件。控制器验证路径和语法后写入目标副本。生成失败保留记录，由后续修复处理。最后一个计划单元生成参数名称映射、依赖文件和 README。

随后执行冻结验收，将实际错误交给独立 Verifier；修复角色利用其证据，自行建立功能单元计划、定位并修改。沿用原有仓库级依赖失效、局部检查和全局验收机制。源程序和任务只读，没有提供健康目标实现、故障类别或预定修复位置。

生成、调查和修复共用 40 次调用、120,000 输出 token、1,800 秒，最多 4 次修复后提交。生成阶段最多使用 20 次调用、80,000 输出 token，每次最多 12,288；剩余预算用于调查和修复，单次上限恢复为 16,384。调查阶段最多 4 次调用，连续修复阶段最多 24 次。输入累计量记录但不设上限。所有调用仍使用原 DeepSeek 配置，推理开启、强度 high。

本次是一个仓库的独立开发验证。相较 Simple MoE，任务和生成流程同时变化；不能用两次运行的差异估计单一组件的效果。没有重跑 baseline 或旧集合。

## 源端边界与验收

源程序通过十个原有测试以及 CPU 上的一轮训练 CLI（16 个样本、批量 8）。三个源种子确认以下行为：

| 路径 | 源端推理 | 源端训练 |
| --- | --- | --- |
| 基础检索 | 通过 | 通过 |
| 用户历史编码 | 通过 | 通过 |
| 位置去偏 | 通过 | 通过 |
| 用户去偏 | 通过 | 通过 |
| 联合去偏 | 通过 | 通过 |
| 奖励包装 | 通过继承的基础行为 | 通过继承的基础行为；新奖励目标未实现 |
| 轻量排序 | 抛出 TypeError | 抛出 TypeError |
| 蒸馏包装 | 抛出 TypeError | 返回 None |

六条可执行路径从相同的源初始参数和候选语料开始，比较检索结果、用户及物品表示、损失、梯度、三步 Adam 参数更新，并实际调用仓库的 `train_one_epoch`。另外两个种子用于验证同一候选。其余两条路径记录源端异常或空返回，不将保持这些行为算作实现排序和蒸馏算法。

表示的绝对容差为 1e-4，损失绝对/相对容差为 0.002/1e-4，梯度分量绝对/相对容差为 1e-4/0.005，单步参数更新相对 L2 阈值为 0.03。检索下标要求一致。目标使用原生 MindSpore `value_and_grad`，禁止导入 PyTorch 及兼容替代后端。

还执行迁移后的十个原测试、CLI，并检查文件、公开符号、测试名称、框架导入、README 和依赖。原测试中的两个精确输出断言沿用源值及容差；提供源端初始权重以对齐跨框架初始化。这些权重是公开输入，不含隐藏目标或参考执行输出。测试断言的保持情况另做产物审查。

## 启动前修正

源 CLI 首次运行自动选择 CUDA，触发源程序中的 CPU/GPU 张量混用。评估环境固定为声明的 CPU 后通过；源代码未修改，首次错误保存在 `source_cli_pre_cpu_fix.json`，既有 CPU 数值测量复用。

第一次启动在发出任何 API 请求前，因生成阶段直接修改只读 `AgentConfig` 而失败。修正为通过 `dataclasses.replace` 创建临时配置，阶段结束恢复原配置。三项生成测试改用真实配置类并通过。零调用、零 token 的失败目录和原 manifest 单独归档，修正后的生成代码重新冻结；预算和验收没有变化。

## 原预算结果与用户授权续接

原预算运行在 20 次调用时耗尽 120,000 输出 token，累计输入 612,239 token，总计 732,239 token。9 次生成请求写入 4 个文件；5 次生成截断，剩余 8 个计划单元尚未执行。随后独立调查和修复建立了三组工作单元，但最后一次提出的编辑因响应截断而没有执行。数值、CLI 和测试仍在源框架导入处失败；原预算结果为未通过。14 项源文件、协议、代码、预算和账本完整性检查全部通过。

用户随后明确要求提高推理预算，并保持请求前缀以利用缓存。续接从原目标快照和完整会话开始，保留原失败结果与全部费用，将单次输出上限提高为 32,768、累计输出上限提高为 240,000；累计调用上限仍为 40，时间上限仍为 1,800 秒。原 20 次调用及 120,000 输出 token 不清零。

首个续接请求严格复用原第 20 次请求，只有 `max_tokens` 从剩余额度 15,167 改为 32,768；模型、推理强度、全部消息和工具定义不变。后续会话追加工具结果与反馈，保留此前发送的消息前缀；续接期间不启用单元切换时的上下文替换，达到上下文上限时明确停止。离线检查覆盖请求字段一致、消息前缀保持以及累计调用和用量。

首个重发请求实测输入 116,369 token，其中 116,224 命中缓存（99.88%），145 未命中。该响应仍因达到输出上限截断；其推理上下文随后保留用于继续。第 22 次调用成功执行了历史编码器和基础模型的编辑，随后完成其余模型、训练器、测试、参数映射和文档的转换。新增的 13 次调用中，输入缓存命中率为 98.21%；逐条核对确认 12 个后续请求均保留了前次请求的完整消息前缀。

## 最终结果

累计第 33 次调用用尽 240,000 输出 token 后停止，最后一条响应截断，未执行额外修改。没有再追加新一轮调用。最终变更 19 个文件；原预算候选和完整失败轨迹保持不变。

| 验证对象 | 最终结果 |
| --- | --- |
| 六条可执行模型路径 | 均能完成推理、原生求导和三步训练 |
| 原有测试 | 10/10 通过；21 个原断言的含义、测试规模、预期数值和容差保持 |
| 文件与框架检查 | 通过；README、依赖、参数映射已生成 |
| 源端已有缺陷 | 保持排序异常和蒸馏空返回，单独登记 |
| 训练 CLI | 未通过；MindSpore Adam 调用仍使用不支持的 `lr` 关键字 |
| 连续训练等价 | 未通过；六条路径均至少有一个数值检查未满足 |
| 额外两个种子 | 未执行；公共种子尚未通过，按冻结流程没有进入确认阶段 |

数值检查失败包括 14 项表示差异、6 项参数更新差异和 1 项梯度差异。最大的物品表示绝对差为 0.001446，超过 1e-4；最大的参数更新相对 L2 差为 0.05866，超过 0.03。前向和训练入口已能执行，误差主要在连续更新后显现，后续应调查训练数值语义。原有测试偏重形状、范围和少量固定前向值，其全部通过不足以覆盖这种训练轨迹偏差。

测试迁移审查核对了全部原断言以及两个精确值测试加载的源初始权重。形状、索引边界、标量类型和 `allclose` 比较保持原含义；源权重与公开 fixture 一致，没有改写预期输出。候选通过测试的记录有效，完整迁移失败的结论也保持。

| 用量 | 初始运行 | 本次续接新增 | 累计 |
| --- | ---: | ---: | ---: |
| 模型调用 | 20 | 13 | 33 |
| 输入 token | 612,239 | 2,672,456 | 3,284,695 |
| 输出 token（包含推理） | 120,000 | 120,000 | 240,000 |
| 总 token | 732,239 | 2,792,456 | 3,524,695 |
| 缓存未命中输入 token | 173,839 | 47,944 | 221,783 |

累计输出中推理为 201,674 token，占 84.03%；共出现 8 次截断。累计实际运行约 975 秒，不含两阶段间准备时间。18 项完整性检查全部通过，包括原结果不变、源与验收不变、从同一候选续接、首请求仅改输出额度、后续前缀一致和累计用量相符。缺少可核验单价，未换算货币费用。

这次结果支持提高复杂迁移请求的单次额度，并保留稳定前缀降低重复输入费用。加长后的调用完成了可运行模型和测试的迁移，原来的短额度确实阻碍了产出。当前仍有单次及累计预算截断；库规模、生成流程、累计预算和上下文保留方式共同变化，因此尚不能据此报告单一机制的成功率提升或正式 baseline 优势。
