# 仓库迁移的研究逻辑与实验方案

仓库迁移放在主实验中，检验 LaDiM 从单个程序扩展到多文件、多入口后的有效性，是泛化评估的一部分。这里使用直接的名称 `Repository Migration`。先确定研究问题、比较条件和实测结论，再决定方法章节的具体组织与正文。

本轮依据任务「移除答案泄露并优化自主定位 (4)」末尾记录、最终 JSON、产物审查和代码核对现有证据，并由独立子 agent 检查方法优势、终止原因和预算调整。先前记录的结果、原有论文修改及其他方案均保留。本轮没有启动模型 API 或训练。

## 二、先确定实验要回答的问题

主实验的共同问题是：LaDiM 能否完成保持训练行为的迁移，并取得怎样的效果与成本。统一 MindSpore 集合给出基本比较，语言和目标框架的变化检验执行环境上的泛化，仓库迁移检验程序组织和依赖范围上的泛化。这些实验共同说明方法的有效性及适用范围。

仓库迁移新增的困难是模型、数据流程、训练器、测试和使用入口分布在多个文件中；一处接口变更会影响多个调用方。单文件生成完成后，其他入口可能仍有未迁移实现。实验因此要观察整个声明范围内的训练流程是否完成，而文件数量、修改行数和局部测试通过数用于解释推进到了哪里。

需要分别回答三个问题：

1. **能力**：从源仓库与公开要求出发，LaDiM 能否产出通过最终验收的目标仓库？
2. **相对优势**：在相同仓库、起始候选、公开反馈与预算下，LaDiM 是否完成更多迁移，或以更少成本达到相同验收结果？
3. **扩展过程**：跨文件依赖、入口覆盖和训练数值差异怎样影响迁移？工具与检查轨迹用于解释结果及改进方法。

前两项决定主实验结论。第三项帮助理解主实验结果，并为后续分析和消融选择问题。章节位置由前两项的研究目标确定。现有结果的完整程度决定可以写出多强的结论。

当前能确认时间序列的三类代码入口与核心训练验收已经通过；双塔完成了更多文件和原测试，但最终完整验收尚未通过。两组体现了可继续验证的完成覆盖优势。现有反馈和预算过程的差异、以及双塔尚未完成的训练修复，是补充比较要解决的具体问题。

## 三、方法中实际增加了什么

框架仍由翻译、独立调查、修复和验收组成。处理仓库时，这些活动作用于文件集合及其接口，工作状态需要同时反映局部实现与全局入口。方法说明应解释下面的因果关系。

| 仓库中的具体问题 | 已实现的处理方式 | 需要解释的作用 |
| --- | --- | --- |
| 一次生成容易耗尽输出，多个文件需要衔接 | 读取公开文件结构，分阶段生成并携带已生成依赖 | 使初译逐步形成可调查的目标程序 |
| 相关实现分散在多个文件 | Agent 自主提出功能单元、文件范围和依赖 | 把同一接口涉及的修改放在一起处理 |
| 修改上游后，旧的下游检查已经过时 | 使相关单元和下游检查失效 | 提醒调查与修复重新取得有效观测 |
| 长轨迹包含大量旧代码、notebook 输出和重复观察 | 按当前工作组织计划、调查结论与检查证据；按单元读写 notebook | 为下一步决策保留相关上下文 |
| 局部运行完成后仍可能遗漏其他入口 | 检查声明的执行入口及训练数值 | 以整个任务的完成情况决定接受与继续修复 |

这些行为的必要性先由仓库任务解释。方法章节是否需要独立小节，以及小节篇幅，等实验方案和方法范围确定后再安排。Translator 继续承担初始生成；仓库范围扩展不会增加一个只负责改名字的角色。

实际配置需对应已有测量：主表和跨语言结果使用原冻结流程；仓库实验使用其扩展实现。时间序列启用了局部上下文，双塔后半段为保持缓存前缀保留完整历史。初译方面，时间序列按核心程序与示例两阶段生成，双塔按公开导入关系安排文件生成。论文中的行为说明应沿用这些事实。

## 四、怎样判断预算是否值得增加

预算调整要针对已经发生的停止原因，同时检验更多预算能否转化为可执行修改和完整验收。

双塔的 LaDiM 累计 33 次调用、240,000 输出 token 后停止；生成阶段 9 次调用已消耗 80,000 输出 token，其中 75,590 用于推理。后半段 13 次调用输入共 2,672,456 token，平均每次约 20.6 万。SWE-agent 和 MatchFixAgent 都先耗尽 40 次调用，分别只用了 50,812 和 73,637 输出 token，没有输出截断。

因此需要分别判断单次输出、累计输出、调用次数、时间和上下文长度。扩大累计输出可给我们的数值修复留下空间；扩大调用次数可让两个 baseline 继续其工具交互；单次额度需要与实际空响应截断对应；时间与上下文上限则检查是否成为新的提前停止原因。

比较采用预先确定的共同预算规则，保留全部方法的结果与完整成本。高预算结果检验能力上限，各检查点的验收与用量说明效率。缓存命中输入仍计入总 token，缓存量单独记录。

只读轨迹审查已经发现：双塔 LaDiM 在第 32 次调用取得一组完整的入口、覆盖和数值反馈，第 33 次剩余 24,286 输出全部用于推理，没有返回可执行工具调用。这为继续修复留出预算提供了具体依据，也指出我们应提前取得可执行检查并预留后续修复空间。主代理已只读复核这三份原始请求和响应，记录及文件哈希见 [终止点复核](../tmp/repository-paper-plan-20260921/terminal-budget-audit.json)。请求消息已达 932,245 字符，接近 1,000,000 字符上限；扩大调用和输出前，还需安排上下文交接。

## 五、优势比较的起点与结果复用

时间序列已有共同初译，可以保留这份文件及其生成成本。正式比较需要从开始就提供一致的完整入口反馈，并统一最后接受条件。已完成的旧轨迹保留其实际协议；源仓库、合法输入、初译和合格测量工具优先复用。

双塔原有比较让目标目录从 PyTorch 源副本开始。MatchFixAgent 的原生任务是验证和修复已有译文，因此三方法共享一份真实初译更能直接比较其调查修复能力，也与论文主实验一致。初译生成归入端到端费用，候选在查看修复结果前冻结；各方法保留自身的算法、提示、解析器、工具组织和重试。我们的方法可以改进自己的推进策略和证据管理。

旧结果的复用依据是源程序、候选、公开反馈、方法实现、预算规则与验收是否保持一致。修改方法后产生的新结果按新条件记录。单纯分析已有产物可以复用全部测量，补齐不同反馈下的比较需要相应方法的实际运行。

## 六、下一步先解决什么

独立子 agent 已交付 [优势与预算审查](repository-advantage-audit-20260921.md)。主代理复核了关键停止点和评估器构造优化器的代码，并独立用已有记录完成首步更新的纯算术复算。建议按下面的顺序准备。

首先修正数值验收的优化器控制接口。当前 worker 自己构造源、目标 Adam，候选训练器接收这个外部对象。保存记录表明，两端更新中的 epsilon 处理不同：用各自公式重建实际首步更新，最大残差约 1.01×10⁻⁷。将目标已有梯度代入源端更新公式，历史编码、位置去偏、用户去偏、联合去偏四条路径的首步相对更新差从 0.04057、0.05866、0.03038、0.03873 降到 0.01826、0.02173、0.01816、0.00651，均低于原 0.03 阈值。这确认了首步偏差中的评估器影响；后续步骤仍需要完整执行验证。[主代理独立复算](../tmp/repository-paper-plan-20260921/first-step-optimizer-audit.json)

我建议由候选提供目标优化器的构造入口，让 agent 能按源训练语义选择和实现目标更新；评估器统一注入初始状态、记录梯度及实际更新，并继续检查原生目标后端执行。时间序列已经采用候选提供优化器构造入口的方式，可参考它的接入职责。公共任务保留源程序、源训练配置与行为要求；本轮推导的 epsilon 修复公式保留在开发审查中，修复提示由实际观测生成。三个方法使用同一接口，baseline 的算法与候选实现保持自身行为。CLI 的参数错误仍需要被测 agent 自主修复。

这次复算没有产生新的候选或通过记录。评估接口调整后重新测量全部适用训练步骤与确认种子，原阈值和既有失败记录保持。

其次改进我们自己的通用推进过程：让未生成的依赖显式进入计划；核心接口能够运行时及时取得数值反馈；给调查、有效修改和复验保留额度；在阶段边界交接结构化证据，避免完整历史持续增长。改动针对一般仓库状态及实际观测，不把当前案例的故障答案写进提示。

之后冻结共同初译、公开反馈、最终验收、各方法实现与资源规则。时间序列优先复用原共同初译；双塔需要一份按预先定义的生成流程得到的共同候选。生成的全部尝试计费，原有失败与产物保留。baseline 的算法、提示、解析器、内部重试和候选缺陷沿用自身设定。

待上述问题解决后，我倾向于一次共同较高预算的运行，先完成两个现有仓库、三个 agent 的比较，共六个修复条件。建议供审查的共同上限为每条件 80 次调用、480,000 输出 token、单次 32,768、3,600 秒、四次外部提交，仍使用原 DeepSeek。将 40 次调用和 240,000 输出附近的当前候选及实际用量作为过程观察点保存，达到接受条件即可按原流程停止。

这样可以用同一次运行观察预算使用和完成过程，节省额外 API 调用。其观察点用于描述这一较高预算运行的进度；若以后研究“预先给定不同预算怎样改变策略”，再设计独立预算消融。六个条件的累计修复输出硬上限合计 2.88M，另计共同生成的实际费用；输入按完整调用账本记录，总 token 与实际消费需要结合上下文及渠道单价估算。上限不会要求已经完成的任务继续耗尽预算。

80 次调用和 480,000 输出同时放宽，分别跨过 baseline 的调用瓶颈和 LaDiM 的输出瓶颈。原运行都未达到时间上限，3,600 秒用于给较长运行保留空间。单次先保持已实测能产出复杂编辑的 32,768；早期 12,288 的生成限制需要消除。具体生成额度在准备阶段单列，避免把生成费用隐藏在修复预算之外。

本轮先完成研究逻辑和运行方案，不预写论文段落，也不启动付费实验。仓库结果在主实验中的位置已经确定；后续根据统一比较的结果组织泛化结论，分析实验继续解释调用成本、修复过程和训练信号。
