# 仓库扩展与旧实验重跑评估

当前建议保留已经完成的统一小程序实验，暂不全量重跑。另一个仓库的独立验证已经结束：从原始源副本起步的 `simple-moe` 转换未通过，在目标代码产生有效修改前耗尽了输出预算。新增仓库协调层并未替换精简单文件方法；其依赖计划、notebook 单元操作和模块切换主要适用于多文件任务。因此旧实验不会仅因仓库模式新增而失效。若将其中的上下文或停止策略移植到通用方法，再对受影响实验做一次预先固定的验证。

## 实现差异与可能收益

对比统一主实验工作树和仓库试点工作树的 `autofix/autonomous/agent.py`，公共控制器新增的行为只有仓库目录存在时的任务描述、把 `target/` 修改计入生产代码修改，以及承认 `checkpoint_unit` 为检查动作。依赖规划、上下文切换、notebook 编辑等机制位于独立的 `RepositoryAgent` 和 `RepositoryTools`。现有 `source.py`／`candidate.py` 任务未调用这一协调层；直接按原入口重跑仍执行原方法。

统一主实验已经通过 29/29 个不同输入。重新运行最多改善成本和结果稳定性，接受率已没有上升空间。仓库计划在单文件任务中可能增加额外调用。更值得检查的是跨语言长轨迹：原方法 18 例中通过 9 例，其余 7 例输出预算耗尽、2 例上下文预算耗尽。按单元保留证据可能减少重复上下文，但不能保证解决程序本身的迁移难点。

时间序列仓库的新模式修复成本为 2,176,471 token，旧流程为 3,411,298 token，观察值下降 36.2%；同时调用数从 16 增加到 40，新增了入口反馈并调整了阶段调用分配。这是开发观察，不是单一组件的等预算消融，也不宜直接用 36.2% 折算所有旧任务的新成本。输入 token 的减少还可能改变缓存命中比例，因此货币费用需另行核对。

## 用旧实测量估算新增开销

以下只估算我们的方法，复用冻结初译，不重跑 baseline。原来的源程序、验收、任务分母和模型保持一致。数字来自历史完整运行，尚无新机制在这些任务上的用量测量。

| 运行范围 | 条件数 | 历史新增 token 基准 |
| --- | ---: | ---: |
| 统一主实验中的全部实际初译故障 | 9 | 3,320,339 |
| 统一主实验全部输入 | 29 | 4,730,025 |
| 跨语言全部输入 | 18 | 20,785,268 |
| 主实验与跨语言 | 47 | 25,515,293 |
| 主实验与现有三项组件消融 | 116 | 18,174,339 |
| 主实验、三项组件消融及跨语言 | 134 | 38,959,607 |

三项组件消融指连续原会话、移除修复历史、移除进展提示。以上不包含仓库协调新组件的额外消融，也不包含训练信号消融、插拔到 baseline 的变体或独立重复。早期受控 50 例和自然迁移 10 例合计旧用量为 53,189,707 token；这些是不同协议的归档实验，本次不建议再全量复跑。

主实验 29 组基准中，输入为 4,279,883 token，输出为 450,142 token；历史输入缓存未命中为 839,509 token。人民币费用需使用该 DeepSeek 接口的实际命中输入、未命中输入、输出单价，按 `(命中输入×单价＋未命中输入×单价＋输出×单价)/一百万` 计算。当前没有可核验的接口账单或单价，不以其他模型或渠道价格替代。

可先固定一个成本不超过约 300 万总 token 的诊断批次，从跨语言任务中覆盖已通过、输出预算耗尽和上下文预算耗尽三类运行状态。旧轨迹继续保留，若只测失败子集，该批仅用于开发诊断，不能直接替换全量通过率。正式决定替换通用方法时，应冻结实现，重跑该方法的整个比较集合及直接依赖其实现的消融；数据、验收、预算和 baseline 均不变时，可复用原 baseline 结果。若改变公共反馈或验收，各方法需按同一协议重新比较。

## 本次实际执行

新增选择 `peytontolbert/simple-moe`，冻结提交 `eae129393941b3d6017ae6f4861d8e5f31c5466b`，包含 7 个 Python 文件、776 行。它在原论文候选中代码较短，具有专家、路由、模型、训练器、指标和测试的跨文件依赖。目标仍为原生 MindSpore，后端仍为固定 DeepSeek。

本次直接从完整源仓库的独立副本开始，由仓库 agent 在同一生命周期内完成翻译与修复，不另做大输出初译。总预算为 40 次调用、120,000 输出 token、1,800 秒、最多 4 次外部提交；每次输出上限 16,384 token，输入累计量如实记录。运行方式与时间序列试点的“共同初译＋修复”不同，分别记录端到端成本，不拿修复阶段费用直接排序。

最终使用 36 次调用、1 次外部提交，输入 1,839,589 token、输出 120,000 token，总计 1,959,589 token，耗时约 580 秒。输出中推理占 104,663 token（87.2%），出现两次截断。36 个请求均有实际响应，用量与结果账本一致。没有追加试跑或重置预算。

这次返回了 9 次编辑工具结果，全部面向 scratch 测试，目标生产文件的最终哈希与初始副本一致。agent 在 8 次调用中执行临时 API 探查，第 27 次调用才选择第一个模型单元，最终仍在源框架导入处失败。因此本轮没有获得可接受的迁移产物，也没有形成成本优势证据。这里使用原始源副本，而时间序列成功案例使用共同初译；该结果反映从零生成路径的推进问题，不能把两者当作同任务新旧版本对照。

完整性检查 12 项通过：源文件、任务、验收代码、控制器和仓库机制均未在运行中改动，最终目标哈希与记录一致，模型仍为固定 DeepSeek，未超过调用和输出预算。baseline、旧实验和论文未修改。

已完成三个源种子的训练、评估、检查点恢复及恢复后更新检查，原生三个测试通过；验收正控制通过，前向偏差与遗漏更新负控制被拒绝。依赖安装在现有独立目标环境中。验收覆盖连续三步前向、损失、梯度和参数更新、不同 top-k、额外输入维度、指标函数、随机训练、源测试迁移与 README 代码块的框架检查。

源仓库的可选外部 `model-stack` 运行时未启用；此次范围为实际通过源检查的原生回退路径。源指标集合在多元素张量转标量时抛异常，训练损失汇报也保留源语义。它们按源行为登记，不由评估方修补。模型计算、求导和优化器更新必须实际执行 MindSpore。README 目前检查代码块、依赖和说明的框架一致性，不宣称所有文档片段均为可独立运行程序。

接下来值得改进的是生成与修复的阶段划分：先按依赖形成能落盘的有限文件修改，再使用独立调查修复真实执行失败；还应限制连续无生产修改的 API 探查，并使局部检查只依赖当前可运行单元。这些改动需要先在声明的开发任务上验证。当前证据尚不足以建议扩大推理预算或批量替换已有方法。
