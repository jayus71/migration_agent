\begin{abstract}
Migrating deep learning code across frameworks enables the reuse of training programs in new software and hardware environments. Framework differences can silently change gradients and parameter updates even when a translated program runs successfully. To address this problem, we propose LaDiM, a framework with multiple agents that uses dependencies between training computations to guide diagnosis and repair. The Verifier Agent investigates discrepancies and passes supporting evidence to a separate Repair Agent. The Orchestrator schedules their work and returns verification results after each submission. Repository context management preserves relevant evidence to coordinate repair across dependent files. On 50 migrations from PyTorch to MindSpore, LaDiM matches the state of the art in acceptance with 57.4\% fewer total tokens, including initial translation. Evaluation across framework migration, language migration, and repository tasks demonstrates LaDiM's effectiveness in preserving training behavior.
\end{abstract}

\section{Introduction}

Migrating deep learning code allows existing models and training programs to run in new software and hardware environments. Differences in operator semantics, numerical precision, and random number handling can change the computations performed after migration. Automatic differentiation and optimizer interfaces introduce further differences in how a model learns~\citep{paszke2019pytorch,mindspore2020whitepaper}. Large language models (LLMs) reduce the manual effort involved in code translation~\citep{he-etal-2025-execoder,macedo2024intertrans}, while automated tests and interactive repair help assess and correct translated behavior~\citep{roziere2021unittests,yang2024sweagent,ibrahimzada2025matchfixagent}. Training programs require these capabilities to preserve the computations that determine each parameter update.

{\hyphenpenalty=10000\emergencystretch=1em
A translated program can produce a loss close to that of the source while computing incorrect gradients. An optimizer error can also alter the parameter update without changing the current loss or gradients. We use semantic drift to describe these changes in training behavior caused by migration. Training computations have dependencies that help investigate such errors. A forward error may change gradients and updates, while an incorrect update may affect later forward computations. Locating the cause requires examining how the translated code produces the observed differences. This investigation also affects migration cost. Figure~\ref{fig:migration-motivation} compares complete token use on common migration tasks, where LaDiM achieves full acceptance with less than half the tokens used by MatchFixAgent.\par}

We introduce LaDiM (Layered Diagnosis for Multi-Agent Code Migration), which uses training behavior to guide diagnosis and repair of an initial translation. The Verifier Agent inspects code and runs tests to establish where source and target computations diverge. For example, matching forward values with missing gradients directs attention to parameter registration and the differentiation path. Independent evidence handoff supplies the supporting code observations, measurements, and hypotheses to a separate Repair Agent. The Orchestrator schedules their work and returns verification results after each submission. The Repair Agent retains its earlier attempts and feedback as repair history, connecting each correction to its measured effects and using unresolved discrepancies to guide the next attempt.

For repositories, migration must preserve shared implementations across multiple entry points. A change that corrects one caller can alter the behavior of another, and investigation may need evidence collected earlier in a different file. LaDiM's repository context management combines Repository Structural Analysis, which exposes files and their interfaces, with Repair Dependency Graph Planning, which organizes related files into work units and coordinates their prerequisites. Notebook editing tools, evidence associated with code versions, and context reconstruction carry the investigation across files. Changes to shared code invalidate affected checks and prompt the agent to verify dependent callers again.

We evaluate migration acceptance and token use from common initial translations under a shared protocol. LaDiM completes all 50 migrations from PyTorch to MindSpore with 57.4\% fewer tokens than MatchFixAgent, covering both programs that require repair and programs that pass the initial checks. It also accepts 9/18 migrations from Java/DJL to Python/PyTorch, compared with 8/18 for SWE-agent and MatchFixAgent. On the time series repository, all three agents complete migration, and LaDiM uses 68.1\% and 80.8\% fewer tokens than the two baselines. On recommendation, LaDiM achieves the highest behavioral coverage and passes all ten original tests. The JAX study verifies the same repair procedure on a second target framework. Our contributions are as follows.

\begin{itemize}
  \item We develop training behavior diagnosis that uses dependencies among execution, forward values, gradients, and parameter updates to identify the computations to investigate. Adding these signals increases full acceptance from 4/16 to 16/16 in the controlled repair study.
  \item We introduce independent evidence handoff and repair history to connect investigation, edits, and verification, together with repository context management for shared code. LaDiM repairs four of five failed saved translations, including errors in a supporting library; all three repair baselines repair none.
  \item We establish migration acceptance and efficiency under common evaluation protocols across frameworks, programming languages, and repositories. LaDiM preserves complete MindSpore acceptance with 57.4\% fewer tokens than MatchFixAgent and reduces token use in the Java/DJL and time series comparisons.
\end{itemize}

\section{Related Work}

\paragraph{Code Translation and Framework Migration.}
Neural translation methods learn code mappings from multilingual corpora and use automated tests or compiler representations to improve translations~\citep{roziere2020transcoder,roziere2021unittests,szafraniec2023compiler}. ExeCoder encodes functional semantics, syntax structure, and variable dependencies~\citep{he-etal-2025-execoder}, while InterTrans explores intermediate translation paths~\citep{macedo2024intertrans}. Framework migration tools such as MindConverter supply mappings between programming interfaces~\citep{mindspore2023mindconverter}. RepoTransAgent uses repository context, test failures, and reflection to refine translated code~\citep{guan2025repotransagent}. LaDiM investigates how a translated training program computes and updates its state. At repository scale, it coordinates changes to shared interfaces and checks their effect across declared entry points.

\paragraph{Differential Testing and Deep Learning Verification.}
Differential testing exposes compiler and program faults through disagreement between related executions~\citep{yang2011csmith,le2014emi}. DeepXplore and DeepGauge investigate behavioral differences and test coverage in deep learning systems~\citep{pei2017deepxplore,ma2018deepgauge}. More directly related to framework migration, TensorScope tests corresponding APIs across frameworks to identify inconsistent behavior~\citep{deng2023tensorscope}. NablaFuzz compares execution scenarios to test automatic differentiation, including first-order and higher-order gradients~\citep{yang2023nablafuzz}. LaDiM uses training differences as evidence for code repair. Its Verifier Agent relates the measured forward values, gradients, and parameter updates to the implementation, develops hypotheses about their origin, and supplies evidence that the Repair Agent can test when selecting a change.

\paragraph{Automated Program Repair and LLM Agents.}
Automated program repair uses tests or semantic constraints to guide patch generation~\citep{nguyen2013semfix}, and pretrained language models generate patches from code and failure evidence~\citep{xia2023aprplm}. Interactive agents combine repository navigation, editing, and execution~\citep{yang2024sweagent,shinn2023reflexion,chen2023selfdebugging,wang2024codeact}. Multi-agent systems distribute development activities among specialized roles~\citep{qian2023chatdev,hong2023metagpt,wu2023autogen,chen2023agentverse}. MatchFixAgent takes a source program and an existing translation and uses several semantic analyses to guide test generation and repair~\citep{ibrahimzada2025matchfixagent}. LaDiM includes initial translation and organizes diagnosis around dependencies in training computations. The independent investigation and its supporting observations pass to a separate Repair Agent, which uses measurements after each submission to revise its hypotheses. The comparison evaluates both methods from the same initial translation and includes translation costs.


\section{Methods}
\label{sec:method}

LaDiM uses dependencies between training computations to guide diagnosis and repair. The Translator first produces a candidate in the requested framework. The Verifier Agent investigates discrepancies between source and target executions and passes its findings and supporting observations to a separate Repair Agent. The Repair Agent tests these hypotheses and revises the candidate. The Orchestrator schedules their work and returns verification results after each submission to guide further repair. Figure~\ref{fig:architecture} shows this process.

\subsection{Preliminary}

A migration task $\mathcal T=(P,L_s,F_s,L_t,F_t,W)$ specifies a source program $P$, its language and framework $(L_s,F_s)$, the requested target environment $(L_t,F_t)$, and an editable file scope $W$. Migration produces a target program $\hat P$ that preserves the source's training behavior. The scope can include the translated program, its supporting library, or a repository.

At step $t$, the source produces $(e_t,v_t,g_t,\theta_{t+1}-\theta_t)$, and the target produces $(\hat e_t,\hat v_t,\hat g_t,\hat\theta_{t+1}-\hat\theta_t)$. Here $e_t$ records the execution outcome, including success or an exception, $v_t$ contains selected forward values and losses, $g_t$ contains gradients, and $\theta_t$ denotes the parameters before the update. After aligning corresponding tensors and parameters, we define
\begin{align}
d_{\mathrm{execution},t}&=\mathbf{1}[e_t\ne\hat e_t], &
d_{\mathrm{forward},t}&=v_t-\hat v_t,\\
d_{\mathrm{gradient},t}&=g_t-\hat g_t, &
d_{\mathrm{update},t}&=(\theta_{t+1}-\theta_t)-(\hat\theta_{t+1}-\hat\theta_t).
\end{align}
For a numerical comparison $d=x-\hat x$, $d\simeq0$ denotes agreement within its tolerance, such as $|d_j|\leq\alpha+\beta|x_j|$ for absolute tolerance $\alpha$ and relative tolerance $\beta$, or a specified norm bound. These discrepancies follow the training computation. Forward values determine the loss, differentiation produces the gradients, and the optimizer uses those gradients and its state to update parameters. The updated parameters then affect subsequent forward computations.

The LLM $M$ performs translation, investigation, and repair under role instructions $A_T$, $A_V$, and $A_R$. The Orchestrator $\mathcal O$ evaluates candidates and manages their shared investigation and repair budget $B$. In the algorithms, $S$ holds the candidate and observations, $q$ is its verification status, $H$ is a conversation, and $C$ manages retained evidence. A submission sends the candidate for external verification after a repair stage that can contain several LLM calls, tests, and edits. Each $\textsc{Query}(M,A,H,b,B)$ invokes $M$ with instructions $A$ and conversation $H$, charging its usage to the stage allowance $b$ and shared budget $B$.

\subsection{Verifier Agent}
\label{sec:hierarchy}

The Verifier Agent uses discrepancies to narrow the code and computations it investigates. An execution discrepancy ($d_{\mathrm{execution},t}=1$) identifies an exception and the calls that led to it. A forward discrepancy ($d_{\mathrm{forward},t}\not\simeq0$) directs the investigation toward operators that produce different values. When forward values agree, a gradient discrepancy ($d_{\mathrm{gradient},t}\not\simeq0$) points to parameter registration or the differentiation path. When both forward values and gradients agree, an update discrepancy ($d_{\mathrm{update},t}\not\simeq0$) directs attention to the optimizer's rule and state. The first affected step provides further evidence because a changed update can alter later forward computations.

Under $A_V$, the LLM selects code inspections and distinguishing tests, then records the observations supporting its hypotheses. Production files remain read-only during this investigation, while scratch tests can be created and modified. Independent evidence handoff transfers these findings to a new repair conversation so that the Repair Agent can assess the diagnosis against its supporting code and measurements. Algorithm~\ref{alg:diagnose} gives the layered investigation and defines the shared \textsc{AgentStep} for querying the LLM, executing tools, and recording observations.

\begin{algorithm}[!htb]
\caption{Layered Diagnosis}
\label{alg:diagnose}
\begin{algorithmic}[1]
\Function{LayeredDiagnosis}{$\mathcal T,S,M,B,C$}
  \State $H\gets\Call{StartConversation}{A_V,\mathcal T,S}$; $b\gets\Call{DiagnosisAllowance}{B}$
  \While{$\Call{WithinLimits}{b,B}$}
    \State $(H,a,R)\gets\Call{AgentStep}{M,A_V,H,S,b,B,C}$
    \State \textbf{if} $a.\mathrm{complete}$ \textbf{then break}
  \EndWhile
  \State \Return $\Call{PublicEvidence}{H,C.\mathrm{archive}}$
\EndFunction
\Function{AgentStep}{$M,A,H,S,b,B,C$}
  \State $H\gets C.\Call{BeforeCall}{H,S}$; $a\gets\Call{Query}{M,A,H,b,B}$
  \State $H\gets H\mathbin{\|}a$; $R\gets[\,]$
  \ForAll{$c\in a.\mathrm{toolCalls}$}
    \State $r\gets\Call{Execute}{c,S,\mathrm{productionReadOnly}=(A=A_V)}$
    \State $H\gets H\mathbin{\|}(c,r)$; $R\gets R\mathbin{\|}(c,r)$; $C.\Call{Record}{c,r,S}$
  \EndFor
  \State \Return $(H,a,R)$
\EndFunction
\end{algorithmic}
\end{algorithm}

\subsection{Repair Agent}
\label{sec:repair-agent}

The Repair Agent receives the Verifier Agent's code observations, test results, and hypotheses through independent evidence handoff. It reassesses this evidence, runs further tests, and edits files in $W$, including supporting library code when the task permits it. The agent tests its changes before submission. The Orchestrator then verifies the candidate and returns the remaining discrepancies, which guide further investigation and repair.

Repair history preserves earlier edits, observations, and hypotheses across attempts. The continuing conversation includes failed tests and verification feedback, allowing the agent to relate a changed result to the preceding modification and revise explanations that did not resolve the fault. The current candidate also persists, so later attempts build on applied changes. Algorithm~\ref{alg:repair} reuses \textsc{AgentStep} from Algorithm~\ref{alg:diagnose}.

\begin{algorithm}[!htb]
\caption{\textsc{Repair}$(\mathcal T,S,E,q,M,B,C)$}
\label{alg:repair}
\begin{algorithmic}[1]
\State $H\gets\Call{StartConversation}{A_R,\mathcal T,\operatorname{AttributeToVerifier}(E)}$
\State $C.\mathrm{handoff}\gets\mathrm{true}$
\While{$\Call{SubmissionsLeft}{B}\land\Call{BudgetLeft}{B}$}
  \State $H\gets H\mathbin{\|}S.m$; $F\gets(\mathrm{false},\mathrm{false})$; $b\gets\Call{RepairAllowance}{B}$
  \While{$\Call{WithinLimits}{b,B}$}
    \State $(H,a,R)\gets\Call{AgentStep}{M,A_R,H,S,b,B,C}$; $F\gets\Call{UpdateFlags}{F,R}$
    \State \textbf{if} $a.\mathrm{complete}\land F.\mathrm{edited}\land F.\mathrm{tested}$ \textbf{then break}
    \State \textbf{if} $a.\mathrm{complete}$ \textbf{then} $H\gets H\mathbin{\|}\Call{PendingAction}{F}$
  \EndWhile
  \State $(S.m,q)\gets\mathcal O.\Call{Verify}{S.\hat P}$; $B.\mathrm{submissions}\gets B.\mathrm{submissions}+1$
  \If{$q=\mathrm{accepted}$} \State \Return $(S.\hat P,q)$ \EndIf
\EndWhile
\State \Return $(S.\hat P,q)$
\end{algorithmic}
\end{algorithm}

\subsection{Repository Coordination}
\label{sec:repository-method}

A change to a shared implementation can affect several callers in a repository. Repository context management carries the plan, code context, and evidence needed to investigate these relationships across files. It combines Repository Structural Analysis, Repair Dependency Graph Planning, notebook tools with edit validation, an archive of evidence associated with code versions, and context reconstruction.

Repository Structural Analysis exposes files, imports, function and class definitions, and notebook cells for the agent to inspect through a tool call. The agent uses Repair Dependency Graph Planning to group related files into work units, specify their repair goals, and organize their prerequisites as a directed acyclic graph. It selects a unit whose prerequisites have current checkpoints, then edits the files assigned to that unit. Local syntax checks and selected tests establish each unit's current status. When an edit changes a shared implementation, LaDiM invalidates the checks for affected units and their dependents, prompting the agent to check the relevant callers again. The Orchestrator evaluates the complete repository, including its entry points and training computations, to determine acceptance.

Notebook tools expose cell source and apply edits with transaction and syntax validation. The evidence archive retains code observations, measurements, hypotheses, and conversations with their code versions, and supports retrieval of relevant records. At independent evidence handoff, an actual switch between work units, or a context capacity boundary, LaDiM rebuilds the conversation around the current plan, findings, and measurements, retaining relevant code already read whose file hashes still match. These operations extend the program repair history to investigations that span multiple files and conversations. Algorithm~\ref{alg:repository} combines repository verification with the diagnosis and repair procedures.

\begin{algorithm}[!htb]
\caption{Repository migration and context operations}
\label{alg:repository}
\begin{algorithmic}[1]
\Function{RepositoryMigrate}{$\mathcal T,M,B$}
  \State $S.\hat P\gets\Call{Translate}{M,A_T,\mathcal T}$; $C\gets\Call{RepositoryContext}{\mathcal T}$
  \State $(S.m,q)\gets\mathcal O.\Call{Verify}{S.\hat P}$
  \If{$q=\mathrm{accepted}$} \State \Return $(S.\hat P,q)$ \EndIf
  \State $E\gets\Call{LayeredDiagnosis}{\mathcal T,S,M,B,C}$
  \State \Return $\Call{Repair}{\mathcal T,S,E,q,M,B,C}$
\EndFunction
\Function{$C$.Record}{$c,r,S$}
  \State $C.\mathrm{archive}\gets C.\mathrm{archive}\mathbin{\|}(c,r)$
  \If{$\Call{CodeChanged}{r}$}
    \State $\Call{MarkHistorical}{C.\mathrm{measurements}}$
    \State $\Call{Invalidate}{C.\mathrm{checkpoints},\operatorname{AffectedUnitsAndDependents}(r,C.\mathrm{plan})}$
  \EndIf
  \State $(C.\mathrm{plan},C.\mathrm{unit},C.\mathrm{checkpoints})\gets\Call{Update}{c,r,C}$
\EndFunction
\Function{$C$.BeforeCall}{$H,S$}
  \If{$C.\mathrm{handoff}\lor\Call{UnitSwitched}{C}\lor\Call{AtCapacity}{H}$}
    \State $\Call{Archive}{C,H}$
    \State $K\gets\Call{CurrentReadCode}{C.\mathrm{unit},S.\hat P}$
    \State $E\gets\Call{PublicFindings}{H,C.\mathrm{archive}}$
    \State $H\gets\Call{Rebuild}{H.\mathrm{role},C.\mathrm{plan},E,S.m,K}$
    \State $C.\mathrm{handoff}\gets\mathrm{false}$; $C.\mathrm{previousUnit}\gets C.\mathrm{unit}$
  \EndIf
  \State \Return $H$
\EndFunction
\end{algorithmic}
\end{algorithm}

\textbf{Compared methods.}
We compare LaDiM with SWE-agent~\citep{yang2024sweagent} and MatchFixAgent~\citep{ibrahimzada2025matchfixagent} using a common DeepSeek backend and each baseline's native algorithms, prompts, tools, parsers, and retry policies. \textbf{Evaluation.}
Methods use common source programs, evaluation inputs, and corresponding initial parameters. Repair methods also receive the same initial translations. Acceptance requires agreement in execution, forward values, gradients, and parameter updates, together with the task's optimizer and interface checks. The main migration comparisons check consecutive training steps, and repository evaluation also covers shared entry points and original tests. Candidates that pass the public evaluation are checked on additional seeds. Investigation and repair allow up to 40 LLM calls per program and 80 per repository, with at most four submissions. Appendix~\ref{sec:supplementary-protocols} gives the numerical tolerances, seeds, and complete budgets.

\textbf{Migration across languages.}
LaDiM accepts all programs completed by MatchFixAgent and an additional recurrent network example in the Java/DJL collection (Table~\ref{tab:main-results}b). Its 9/18 accepted programs comprise all eight textbook examples and one application, compared with 8/18 for SWE-agent and MatchFixAgent. LaDiM uses 11.7\% fewer tokens than SWE-agent and 24.2\% fewer than MatchFixAgent. These results extend training behavior repair to tasks that change both the programming language and framework.

\textbf{Repository migration.}
All three agents complete the time series migration, preserving the shared model across a training script, notebook, and teaching examples. At the same complete acceptance of 69/69 checks, LaDiM uses 68.1\% fewer end-to-end tokens than SWE-agent and 80.8\% fewer than MatchFixAgent. The coordinated repair therefore preserves training behavior across several callers with substantially lower token use.

On recommendation, LaDiM restores reward model inference and retrieval, which remain unresolved in both baselines, and executes the training command. It achieves the highest behavioral coverage, passing 130/145 checks and all ten original tests. These results cover the shared model's use in training, inference, and retrieval. Appendix~\ref{sec:repository-results} gives the remaining numerical differences and detailed checks.

\textbf{Repair history and independent evidence handoff.}
Repair history and independent evidence handoff improve repair on the saved initial translations (Table~\ref{tab:signal-ablation}b). With repair history, LaDiM repairs four of five failed programs; removing that history reduces the count to zero. Independent evidence handoff repairs one more program than a continuous investigation and repair conversation, increasing final acceptance from 8/10 to 9/10. All three conditions preserve the five programs that pass the initial checks. The complete reference retains earlier attempts and their verification feedback while allowing the Repair Agent to reassess the Verifier's evidence in its own conversation.

\textbf{Repository context management and Repository Structural Analysis.}
On the time series repository, repository context management reduces end-to-end token use by 68.0\% while preserving acceptance on all 69 checks (Table~\ref{tab:signal-ablation}c). Both conditions retain investigation and independent evidence handoff. In a separate paired ablation, Repository Structural Analysis reduces end-to-end token use by 19.8\% and LLM calls from 42 to 30, with the same complete acceptance. Structural context identifies relevant implementations, while the broader context mechanism carries plans, measurements, and inspected code across the investigation. Appendix~\ref{sec:component-study} gives the complete program component results, and Appendix~\ref{sec:repository-component-results} reports both repositories' cumulative comparisons and independent ablations of Repository Structural Analysis and Repair Dependency Graph Planning.



\section{Conclusion}

We introduced LaDiM, a multi-agent framework that uses training behavior to guide code migration and repair. Dependencies among execution, forward values, gradients, and parameter updates direct investigation, while independent evidence handoff and repair history connect each change to its verification results. Repository context management extends this procedure to shared implementations and multiple entry points. LaDiM completes all 50 MindSpore migrations with 57.4\% fewer tokens than MatchFixAgent and repairs four of five failed saved translations that all three repair baselines leave unresolved. Experiments from Java/DJL to Python/PyTorch and on the time series repository also show token savings, while the JAX study confirms the repair procedure across target frameworks. These results demonstrate effective migration of training behavior across individual programs, supporting libraries, and repositories.

\subsection{Detection Measurements}
\label{sec:detection-measurements}

The detection study uses four models, three seeds, and 50 training steps. Gradient scaling and partial update suppression are evaluated both with per-step synchronization to the source state and with each execution retaining its own state. With synchronization, each target starts the checked step from the source state. Loss, gradient norm, and relative update thresholds are 0.02, 0.05, and 0.03. Figure~\ref{fig:gradient-drift} uses trajectories with separate state and reports the mean and range across 12 runs per fault. The loss threshold crossings at steps 31 and 18 refer to mean curves. Direct gradient or update checks detect all respective faults at step~1. Healthy translations pass the recorded checks, with maximum loss difference $3.815\times10^{-6}$.

The scalar summaries are
\begin{align}
\Delta_{\mathrm{loss}} &= |L(P)-L(\hat P)|, \\
\Delta_{\mathrm{grad}} &= \left|\|\nabla_{\theta}L(P)\|_2-\|\nabla_{\hat\theta}L(\hat P)\|_2\right|, \\
\Delta_{\mathrm{param}} &= \frac{\|\Delta\theta-\Delta\hat\theta\|_2}{\|\Delta\theta\|_2+\epsilon}.
\end{align}
Here $\Delta\theta$ and $\Delta\hat\theta$ denote source and target parameter updates, and $\epsilon$ prevents division by zero. Figure~\ref{fig:gradient-drift} divides each difference by its detection threshold. The main migration comparison uses the task-specific tensor comparisons defined above.

\section{Repository Context and Evidence}
\label{sec:repository-context}

The repository extension separates the version of its dependency plan from the version of the candidate files. Every recorded test stores the candidate version on which it ran. An actual change to candidate code makes earlier measurements stale, and a new result replaces the preceding result for the same test even when the new test fails. Work-unit checkpoints additionally depend on their declared file scopes, test selections, and prerequisite units. A checkpoint without a selected test records syntax validation only. The final acceptance decision uses the complete repository evaluation.

Full tool observations, file reads, and conversations are archived outside the editable workspace. Records carry content hashes and can be retrieved by identifier, JSON pointer, and character range. When the context is rebuilt, it retains the current dependency plan and generation status, the complete structured hypotheses and next steps, the latest measurements, and the last tool batch. Cached code consists only of content returned by earlier reads, with matching current file hashes and relevance to the active unit. The cache contains at most 120,000 characters. Reconstruction is triggered by an independent role handoff, an actual work-unit switch, or messages exceeding 75\% of the configured context capacity. Ordinary stage continuation and the first selection of a work unit retain the existing conversation.

For the repository experiments, diagnosis allows up to six calls and 64,000 output tokens. The remaining repair calls and output budget are allocated over the remaining external submissions, with at most 16 calls in the first repair stage. The cumulative limits apply to the whole repository.
