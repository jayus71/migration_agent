\title{LADDER: Layered Differential Diagnosis for Execution Repair in Cross-Framework Training-Code Migration}

\author{\IEEEauthorblockN{Anonymous Authors}
\IEEEauthorblockA{Anonymous Institution\\
anonymous@example.com}}

\maketitle

\begin{abstract}
The maturation of LLM-based code translation has made it practical to port deep learning training programs across frameworks. Automated migration offers a route to reusing these programs on a new backend, but is frequently defeated by differences in operator semantics, automatic differentiation, and optimizer behavior. Existing translation and repair pipelines validate a candidate against a single outcome such as a clean execution or a passing test, without questioning whether one verdict can locate the semantic layer at which training broke. We argue that the granularity of repair feedback is itself a critical but overlooked factor in migration correctness. To this end, we introduce Layered Differential Diagnosis for Execution Repair (LADDER), which compares paired source and candidate executions through execution, forward-numerical, and gradient/update signals, reporting the first failing layer as the diagnosis that drives targeted repair. Each layer becomes measurable only once the layer above it holds, which makes the ordering a property of training semantics rather than a reporting convention. A common adapter interface carries the same diagnosis to a new target backend without changing the feedback logic. Repair and re-verification are then driven by the reported layer, and a candidate is accepted only once every layer holds. Extensive experiments on MindSpore and JAX target paths demonstrate that LADDER verifies more migrations than execution-only feedback and than blind-repair agents, at an order of magnitude lower token cost.
\end{abstract}

\begin{IEEEkeywords}
cross-framework migration, training-code translation, hierarchical feedback, program repair, differential testing

\section{Introduction}

Large language models (LLMs) have made source-code translation increasingly practical, and recent systems improve generated programs through execution, repository context, and iterative feedback~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent,erer2025fullyautomated,gray2025workflows}. Cross-framework migration of deep learning (DL) training code raises a stricter problem. Correctness for such a program extends beyond control flow and API behavior to the tensor computations, automatic differentiation, optimizer state, and parameter updates that determine learning.

This requirement creates failures that ordinary executability checks cannot see. A translated training script may run successfully while producing different logits or losses. It may match the forward computation but propagate incorrect gradients, or compute plausible gradients while updating a different parameter set. Such failures arise across framework boundaries because runtimes differ in operator conventions, execution modes, differentiation interfaces, and optimizer semantics~\cite{paszke2019pytorch,mindspore2020whitepaper,google2025torchax}. A successful run is only the first condition of a correct training migration.

Existing systems supply repair feedback in three main ways. Translation pipelines validate against a single outcome such as compilation, unit tests, or repository-level pass rates~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent}. Repair agents explore the program until a test or execution trace exposes the fault~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact,xia2023aprplm,yang2024sweagent}. Conversion and differential-testing tools compare a converted output or a single behavioral property against a reference~\cite{mindspore2023mindconverter,yang2011csmith,pei2017deepxplore}. Despite their variety, all three share a critical implicit assumption, that one verdict on the whole program is a sufficient unit of repair feedback.

This assumption, however, does not hold for training code. Execution failures, forward mismatches, and backward/update errors collapse onto the same verdict even though each calls for a different repair. Training correctness instead carries an ordered semantic structure. A candidate first executes, then preserves the forward computation, and finally preserves gradients and parameter updates. The first failing layer in this sequence provides an actionable diagnosis. Execution failures point to compatibility and lowering, forward failures point to operator semantics, and gradient/update failures point to automatic differentiation, parameter registration, or optimizer behavior.

Based on this observation, we propose Layered Differential Diagnosis for Execution Repair (LADDER), which turns the three signals into an ordered verdict rather than a single one. Paired source and candidate executions are normalized into a common diagnosis report, and a repair component uses the first failing layer to produce a targeted patch before re-verification. Because each layer is measurable only once the layer above it holds, the order is a property of training semantics rather than a reporting convention. A common adapter interface separates this feedback logic from backend execution, so the same diagnosis drives repair on \texttt{torch4ms}/MindSpore\footnote{The primary prototype repository is available at \url{https://gitee.com/feixiao13/ascend-torch4ms.git}.} and on TorchAX/JAX.

This paper makes three contributions:
\begin{itemize}
  \item We identify the granularity of repair feedback as the factor existing migration pipelines overlook, and formulate training-code migration as an ordered semantic validation problem in which the first failing layer is the actionable signal.
  \item We introduce LADDER, a backend-independent hierarchy over execution, forward-numerical, and gradient/update behavior, integrated with translation, targeted repair, and re-verification through a common adapter interface.
  \item Extensive experiments on MindSpore and JAX target paths demonstrate that LADDER verifies more migrations than execution-only feedback and than blind-repair agents, at an order of magnitude lower token cost.
\end{itemize}

\section{Related Work}

\subsection{Translation with Outcome-Level Validation}
Early neural code translation showed that programming languages can be translated without direct supervision from multilingual code corpora~\cite{roziere2020transcoder}.
Later work added automated unit tests as validation and self-training signals~\cite{roziere2021unittests}.
Compiler representations were then introduced to narrow source--target semantic gaps~\cite{szafraniec2023compiler}.
Recent LLM-based systems incorporate executability representations, intermediate translation paths, and repository-level context~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent}.
MatchFixAgent decomposes repository-level equivalence checking across specialized agents and repairs the inequivalences it finds~\cite{ibrahimzada2025matchfixagent}.
We use it as an external repair baseline.
In each case validation is organized around a single outcome, whether compilation, unit-test results, or repository-level pass rates.
Our work instead treats validation as an ordered set of semantic layers, so a passing outcome is no longer the unit of feedback.

\subsection{Repair Driven by Execution Feedback}
Automated program repair has long used tests or semantic constraints to guide patch generation~\cite{nguyen2013semfix}.
Pre-trained language models made patch generation more fluent and enabled iterative repair from execution feedback~\cite{xia2023aprplm}.
Repository-level agents such as SWE-agent use interactive tools and test feedback to edit code iteratively~\cite{yang2024sweagent}.
Reflection and agent-based methods feed natural-language critiques, self-debugging traces, or executable code actions back into the generation loop~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact}.
Multi-agent systems show that role specialization, structured communication, and explicit workflows improve complex software tasks~\cite{qian2023chatdev,hong2023metagpt,wu2023autogen,chen2023agentverse}.
These approaches motivate our translator--verifier--fixer decomposition.
They locate a fault by exploring the program until a test or trace reveals it.
We instead read the fault location from the layer at which the two executions first diverge, which removes the search rather than guiding it.

\subsection{Cross-System Comparison and Framework Bridging}
Modern DL frameworks expose different execution models and optimization abstractions.
PyTorch emphasizes an imperative, dynamic front end~\cite{paszke2019pytorch}, whereas TensorFlow demonstrates large-scale dataflow execution~\cite{abadi2016tensorflow}.
Compiler infrastructures such as MLIR lower domain-specific computation through extensible intermediate representations~\cite{lattner2021mlir}.
Bridging tools address parts of the resulting compatibility problem.
MindConverter targets migration from third-party frameworks to MindSpore~\cite{mindspore2023mindconverter}.
Ivy\footnote{\url{https://github.com/unifyai/ivy}} and \texttt{torch2jax}\footnote{\url{https://github.com/rdyro/torch2jax}} convert PyTorch computations to JAX, while TorchAX preserves a PyTorch-style front end over a JAX backend~\cite{google2025torchax}.
A separate line compares semantically related executions to expose defects.
Differential testing has found compiler and program-analysis bugs this way~\cite{yang2011csmith,le2014emi}, and DL-system testing has explored behavioral coverage and differential-style validation of networks~\cite{pei2017deepxplore,ma2018deepgauge}.
Both lines compare either the conversion output or a single behavioral property.
We instead compare paired training executions at several ordered semantic depths, so the comparison itself yields the repair target.

\section{Problem Formulation}

\subsection{Task Formulation}
Given a training program $P$ in a source framework $F_s$ and a target framework path $F_t$, the migration task is to produce a candidate $\hat{P}$ that executes under $F_t$ while preserving the training semantics of $P$. Training semantics includes the quantities that determine whether learning remains equivalent in practice, namely compatible tensors and modules, comparable forward values and losses, comparable gradients, and parameter updates with comparable direction and magnitude. We instantiate this formulation on \texttt{torch4ms}/MindSpore and TorchAX/JAX target paths.

We evaluate correctness through paired executions under controlled inputs, synchronized initialization, and matched optimizer settings. Let $\mathcal{O}_{t}(P)$ denote the observable state at training step $t$, comprising execution status, selected outputs or losses, gradients, and parameter-update statistics. A candidate is semantically aligned when $\mathcal{O}_{t}(\hat{P})$ remains within predefined tolerances of $\mathcal{O}_{t}(P)$ for the checked steps. All observables are framework-independent. The same diagnostic logic compares executions produced by different target runtimes.

\subsection{Diagnosis-Guided Repair Objective}
The repair objective identifies the earliest semantic layer at which $\hat{P}$ departs from $P$ and exposes evidence for the corresponding edit. Execution failures call for compatibility or lowering changes; forward mismatches call for operator-semantics changes; and gradient/update mismatches call for differentiation, parameter-registration, or optimizer changes. Each layer implies its own edit. The verifier preserves this structure in the feedback delivered to the repair component.

\section{Hierarchical Semantic Feedback}
\label{sec:hierarchy}

\subsection{Design Principle}
LADDER evaluates training-code correctness as an ordered hierarchy. Correctness requires that a migrated program execute under the target backend, then preserve the forward computation, and finally preserve the backward and update behavior that determines learning. The order is not a convention. Each layer is only measurable once the layer above it holds. We organize validation around three semantic layers:
\[
\text{execution} \rightarrow \text{forward numerical} \rightarrow \text{gradient/update}.
\]
This ordering defines both a testing procedure and a repair policy. A deeper comparison is interpreted only after its prerequisites are available, and the first failing layer becomes the primary diagnosis. Later signals may provide supporting evidence, but they do not replace the earliest point at which the source and candidate executions diverge.

\subsection{Framework Adapter Interface}
The hierarchy operates on a common observation schema rather than framework-specific error formats. Each target path supplies an execution adapter that runs the candidate and exposes phase status, selected forward values, gradients, and parameter deltas in a normalized report. The adapter is the only backend-specific component. Runtime-specific details remain inside it; the layer ordering, comparison metrics, diagnosis format, and repair routing remain unchanged.

\subsection{Execution Signal}
The execution signal checks whether $\hat{P}$ can complete the required training step under the target backend, recording whether module construction, data movement, forward execution, loss computation, backward execution, and optimizer stepping each terminate without runtime failure. When a failure occurs, the verifier stores the exception type, stack location, operator or API name when available, tensor shape and dtype context, and the phase in which the failure appears. The phase is what makes the record actionable. Typical failure classes include missing operators, unsupported lowering paths, interface mismatches, device-placement errors, dtype incompatibilities, shape errors, and invalid parameter registration.

\subsection{Forward-Numerical Signal}
The forward-numerical signal checks whether the computation of $\hat{P}$ remains aligned with $P$ once both executions complete. Under controlled inputs $(x,y)$ and synchronized initialization, the verifier compares quantities such as logits, selected intermediate activations, and losses. The minimal scalar comparison is
\begin{equation}
\Delta_{\mathrm{loss}} =
\left| L(P; x, y) - L(\hat{P}; x, y) \right|.
\end{equation}
When intermediate outputs are available, the verifier also computes output- and layer-level discrepancies and locates the earliest module whose difference exceeds tolerance. This localization matters because an end-to-end loss mismatch can originate in an early operator difference, a reduction convention, a broadcasting rule, a normalization layer, or the loss function itself. The scalar alone cannot separate these causes. The earliest exceeding module can.

\subsection{Gradient and Update Signal}
The gradient/update signal checks whether the migrated candidate preserves backward and optimizer behavior. This layer is necessary because two programs may produce similar forward losses while computing different gradients, updating different parameter subsets, or applying optimizer state differently. The verifier compares gradient norms and parameter-update statistics:
\begin{equation}
\Delta_{\mathrm{grad}} =
\left|
\|\nabla_{\theta} L(P)\|_2 -
\|\nabla_{\hat{\theta}} L(\hat{P})\|_2
\right|,
\end{equation}
\begin{equation}
\Delta_{\mathrm{param}} =
\frac{\|\Delta \theta - \Delta \hat{\theta}\|_2}
{\|\Delta \theta\|_2 + \epsilon}.
\end{equation}
Beyond aggregate norms, the verifier records missing gradients, zero-gradient parameters, parameter-name mismatches, and update outliers. Norms alone conflate two failures. These fields separate them. A normal forward loss with missing gradients suggests an automatic-differentiation or parameter-registration issue, whereas aligned gradients with divergent updates suggests an optimizer-state or parameter-step issue.

\subsection{Structured Diagnosis and Repair Routing}
The verifier emits the status of each layer, the first failing layer, the supporting metrics, and a bounded set of root-cause hints. The repair component routes execution failures to compatibility edits, forward-numerical failures to operator-semantics edits, and gradient/update failures to backward or optimizer edits. This mapping is fixed rather than learned. The report turns the hierarchy into an actionable interface between validation and repair instead of a collection of independent metrics.

\section{Cross-Framework Migration Repair System}

\begin{figure*}[t]
\centering

\caption{The migration-repair system on \texttt{torch4ms}/MindSpore. Translation, hierarchical verification, diagnosis-guided repair, and re-verification communicate through explicit artifacts. The TorchAX/JAX implementation uses the same diagnosis schema.}
\label{fig:architecture}
\end{figure*}

Figure~\ref{fig:architecture} shows the primary instantiation as an iterative repair system rather than a single-pass converter. A translator produces an initial target-path candidate, the verifier compares paired source and candidate executions, and the fixer edits the candidate using the structured diagnosis. Each patch is restricted to the repair scope the diagnosis points to, so a gradient-layer diagnosis cannot trigger an unrelated rewrite elsewhere. An orchestrator controls rounds, stopping rules, and reversion of failed attempts. No component holds hidden state. The components communicate through a shared pool of files containing the source program, candidate program, diagnosis report, and patch log, so every repair action is tied to an executable artifact and explicit evidence.

The primary execution adapter uses \texttt{torch4ms}, which provides a PyTorch-style front end and dispatches operators, backward execution, and optimizer behavior to MindSpore-backed implementations. The second adapter uses TorchAX with JAX automatic differentiation and Optax updates. Both expose phase status, forward values, gradient evidence, and parameter-update statistics to the verifier.

For each checked training step, paired harnesses synchronize inputs, initialization, and optimizer settings before recording execution status, loss and optional layer-level differences, gradient-norm differences, and parameter-update relative $\ell_2$ differences. A candidate is accepted only after its final version passes re-verification at every configured semantic layer.

\section{Evaluation}

\subsection{Experimental Setup}
\label{sec:setup}
The evaluation answers three questions. Does LADDER improve verified repair success under a fixed budget (RQ1)? Which component of the hierarchy produces that improvement (RQ2)? Do the semantic layers expose the failure types they were designed to expose (RQ3)?

\textbf{Fault pool.}
The faults come from real migration failures rather than synthetic mutation. We migrated PyTorch training programs to the two target paths and recorded the cases that failed. The recurring failures fall into 25 categories, grouped by the semantic layer at which each one surfaced and by the framework mechanism responsible. Each category is instantiated on two model families, giving a pool of 50 instances over CNN, image MLP, Transformer classifier, and tiny causal LM. The JAX pool is built the same way and contributes six MLP and CNN faults across the three layers.

\textbf{Repair scope.}
A repair scope is the code the fixer is permitted to edit. Candidate-level repairs may change only the migrated program. Core-operator repairs may also change the adapter's operator implementations. Core autograd/optimizer repairs may additionally change its differentiation and optimizer code. Scopes matter because the same observed failure can be fixed at more than one level, and an edit outside the assigned scope may mask the fault instead of repairing it.

\textbf{Conditions and baselines.}
We compare LADDER with two reduced forms of our own feedback, with direct LLM repair, and with the external systems SWE-agent, MatchFixAgent, Ivy, and \texttt{torch2jax}. The execution-only condition reports runtime status alone and withholds the numerical and gradient comparisons. The unordered condition computes every signal but presents them together as one undifferentiated set, without ranking them or naming the layer that failed first. It isolates what the ordering contributes, separately from what measuring the signals contributes. Every method receives the same faulty candidate and the same repair budget. Where an external interface exposes more of the reference implementation than ours sees, we report that asymmetry with the result rather than adjusting the denominator.

\textbf{Metrics.}
A repair counts as verified only when the patched candidate passes all three semantic layers against the source execution. The patched candidate runs to completion and holds $\Delta_{\mathrm{loss}}\leq0.02$, $\Delta_{\mathrm{grad}}\leq0.05$, and $\Delta_{\mathrm{param}}\leq0.03$ at every checked step, using the quantities defined in Section~\ref{sec:hierarchy}. Repair@$k$ is the fraction of instances verified within $k$ repair attempts, so Repair@4 equals verified success under the four-attempt budget used throughout. The out-of-scope edit rate is the fraction of repairs that modified code outside the assigned scope. Tokens are prompt plus completion tokens summed over the pool.

Because every result below is read off a comparison between two executions, we first confirm that the comparison stays quiet on known-good oracle candidates. We ran CNN, MLP, Transformer, and tiny causal-LM trajectories for 50 steps over three seeds. The paired paths agree at every checked step. The largest maximum loss difference is $3.815\times10^{-6}$, and mean gradient-norm and parameter-update differences stay below $4\times10^{-8}$ and $3.9\times10^{-6}$. All reported differences below are attributable to the migration rather than to the measurement.

\label{sec:main-results}
\textbf{Setup.}
The primary experiment ran the full pool of 50 instances on the MindSpore path. All instances were hidden from the repair prompts, each allowed at most four repair attempts, and failed repairs were rolled back. The transfer experiment repeated the same protocol on the PyTorch-to-JAX path.

\textbf{Repair on the MindSpore path.}

\subsection{Ablation Studies}
\label{sec:ablations}
\textbf{Feedback granularity.}
The first ablation removes layers from the feedback rather than from the model. Four model families each received exactly one fault per semantic layer, drawn from the same 25-category pool. That gives 12 controlled tasks. The repair loop ran under execution-only feedback, execution plus numerical feedback, or the full diagnosis, for 36 repair episodes under a four-round budget. Table~\ref{tab:feedback-ablation} shows a stepwise improvement as the loop receives the layer each fault class requires. Each added layer repairs exactly the fault class it targets and leaves the others unchanged. Execution feedback alone resolves the execution faults and none of the deeper ones; adding numerical feedback resolves the numerical faults; adding gradient/update feedback resolves the remainder. Every successful repair completes in the first round, so Repair@1 and Repair@4 coincide. One fault per layer per model keeps the design balanced. That balance is what makes the layer-to-fault correspondence readable, and the correspondence is what identifies the ordering as the source of the improvement.

\textbf{Framework documentation.}
The second ablation varies what the prompts know about the target framework, independently of the feedback. Besides the diagnosis, the fixer prompt can carry documentation for the target framework, covering its operator conventions and optimizer interfaces. Two experiments place it in turn at each end of the pipeline. The first holds the translator fixed and crosses pass/fail against hierarchical feedback, with the documentation off against on. It covers 24 base tasks: 12 candidate-level, eight core-operator, and four core autograd/optimizer. Each ran under all four conditions with a four-round budget. The second moves the same documentation to the translator prompt. The fixer was disabled, so each run made one translation call and no repair round could compensate for a weak first attempt. Five held-out tasks ran at three repeats per condition.

Panel (a) of Table~\ref{tab:guidance-ablations} isolates the two factors in the fixer. Pass/fail feedback repairs nothing, with or without the documentation. Hierarchical feedback repairs most tasks with the documentation off and somewhat fewer with it on. The feedback is the dominant source of repair improvement. The documentation eliminates core-operator out-of-scope edits and lowers candidate-level success, trading repair rate for scope discipline. Core autograd/optimizer repair is the hardest scope in every condition.

Panel (b) reverses the picture at the translator. The documentation dominates one-shot translation. Without it, most outputs fail to compile and none complete the training check, and with it every output passes all three checks on the first attempt. Framework documentation matters most before any feedback exists, whereas panel (a) shows the feedback carrying the repair loop afterwards.

\subsection{Analysis}
\label{sec:analysis}
The ablations show that the ordering carries the repair improvement. This analysis asks whether each signal actually detects the fault class it was designed to expose, independently of whether a repair follows. We used controlled fault injection rather than automatic repair. For each model and seed we compared a PyTorch reference step with a \texttt{torch4ms} candidate under one of three injected conditions. The evaluation used four model families and three seeds per fault. The thresholds are $\Delta_{\mathrm{loss}}>0.02$, $\Delta_{\mathrm{grad}}>0.05$, and $\Delta_{\mathrm{param}}>0.03$.

Table~\ref{tab:signal-effectiveness} shows that the expected signal detects its corresponding fault in all 36 fault-injection runs. Execution faults are isolated by the execution signal. For training faults, the gradient signal records missing-gradient evidence and the update signal captures the divergent parameter update. Numerical faults are detected at the forward layer even when their effects propagate to gradient or update metrics. This is the case the first-failure rule exists to handle. A deeper signal also fires, but the forward layer is the one that names the cause. Every fault class keeps a distinct diagnostic handle, which is the property the repair routing depends on.

\subsection{Threats to Validity}
The MindSpore study covers four model families, 25 fault categories, three repair scopes, and 50-step training trajectories; the JAX transfer study covers six MLP/CNN faults. The results establish transfer across two target paths.

\section{Conclusion}

We introduced LADDER, which validates cross-framework training-code migration through execution, forward-numerical, and gradient/update semantics in order. Specifically, LADDER reports the first failing semantic layer and routes that diagnosis to a targeted repair and re-verification loop. This design makes repair guidance actionable at the layer where the divergence originates, rather than at the point of failure. A common adapter interface keeps the ordering independent of the target runtime and its differentiation system. Experiments across MindSpore and JAX target paths demonstrate that LADDER repairs more faults than execution-only and agent baselines at substantially lower token cost.
