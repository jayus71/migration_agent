\title{LADDER: Training-Code Migration Repair via Layered Diagnosis}

\author{\IEEEauthorblockN{Anonymous Authors}
\IEEEauthorblockA{Anonymous Institution\\
anonymous@example.com}}

\maketitle

\begin{abstract}
Large language models can translate deep learning training
programs across frameworks, but a translated script may execute
successfully while computing incorrect gradients or updating
the wrong parameters. A single pass or fail result for the whole program
does not identify which training stage needs repair. We
introduce LADDER, a repair framework with three agents that
organizes verification around the ordered stages of training.
Its verifier runs the translation alongside the source,
checking execution first, then forward values, and finally
gradients and parameter updates. The first stage at which they
diverge guides the repair agent's edits, while an orchestrator limits
repair attempts and rolls back failed changes. On a MindSpore benchmark
containing 50 fault instances across three classes, LADDER
achieves 100\% repair acceptance within four attempts, with
84\% accepted on the first attempt. It reduces token cost per
accepted repair by a factor of approximately 29 compared with
the strongest external baseline. Evaluations on MindSpore and
JAX demonstrate the effectiveness of the same diagnosis and
repair procedure across target frameworks.
\end{abstract}

\begin{IEEEkeywords}
cross-framework migration, training-code translation, layered feedback, program repair, differential testing
\end{IEEEkeywords}

\section{Introduction}

Large language models (LLMs) translate source code across programming languages, and recent systems refine translations through execution feedback, repository context, and iterative repair~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent,erer2025fullyautomated,gray2025workflows}. Migrating deep learning (DL) training code across frameworks, such as porting a program from PyTorch to MindSpore or JAX, extends this task to the tensor computations, automatic differentiation, optimizer state, and parameter updates that determine learning.

A translated training script may run to completion while producing different forward values, match the source loss but propagate incorrect gradients, or compute plausible gradients while updating a different parameter set. Such failures arise because runtimes differ in operator conventions, execution modes, differentiation interfaces, and optimizer semantics~\cite{paszke2019pytorch,mindspore2020whitepaper,google2025torchax}.

Existing systems supply repair feedback in three main ways. Translation pipelines validate against a single outcome such as compilation, unit tests, or pass rates across a repository~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent}. Repair agents explore the program until a test or execution trace identifies the fault~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact,xia2023aprplm,yang2024sweagent}. Conversion tools and differential tests compare a converted output or a single behavioral property against a reference~\cite{mindspore2023mindconverter,yang2011csmith,pei2017deepxplore}. All three use a result for the whole program to guide repair.

Training code requires feedback that distinguishes failures at different stages. Fig.~\ref{fig:gradient-drift} shows what a check of forward values alone misses. With the injected gradient fault, the mean loss difference remains below its detection threshold for 30 training steps, while the signals for gradient norms and parameter updates cross theirs at step~1. Of the 25 fault categories recorded from real migrations, 15 produce programs that run to completion but fail during forward computation or gradient computation. A translation must first execute, then match the source's forward values, and finally match its gradients and parameter updates. Each stage depends on the one before it, so the earliest disagreement identifies the failing stage and guides the repair.

We introduce LADDER (Layered Differential Diagnosis for Execution Repair). Given the initial translation, a verifier executes it alongside the source and reports the first stage at which they disagree. This diagnosis directs the repair agent's edits to the failing stage and reduces the search needed for repair. An orchestrator repeats the cycle, limits repair attempts, and rolls back failed changes. The three signals describe training behavior and support the same repair loop across target frameworks. We run the loop on \texttt{torch4ms}/MindSpore\footnote{The primary prototype repository is available at \url{https://gitee.com/feixiao13/ascend-torch4ms.git}.} and on TorchAX/JAX by changing only the execution adapter.

This paper makes three contributions.
\begin{itemize}
  \item We design verification checks to localize faults during migration repair. Three ordered signals identify the first training stage that fails and use this information to guide repair.
  \item We implement this diagnosis in LADDER, a repair framework that uses agents to turn each verification result into a targeted edit within a fixed number of attempts. Its signals follow training semantics, allowing the same diagnosis and repair procedure to apply unchanged across target frameworks.
  \item We evaluate LADDER on controlled MindSpore and JAX faults drawn from observed migration failures. Verification in training order repairs instances left unresolved by an overall pass or fail result and accurately localizes the failing stage.
\end{itemize}

\section{Related Work}
We group related work by how it obtains repair feedback, covering validation by overall outcome, fault localization through search, and conversion tools or tests of individual properties.

\paragraph{Validation by overall outcome}
Most translation systems validate a translation by one pass or fail result for the whole program. Early neural translation learned from multilingual corpora without direct supervision~\cite{roziere2020transcoder}. Later work used automated unit tests to validate translations and supervise training on the model's own outputs~\cite{roziere2021unittests}, and compiler representations reduced semantic gaps between source and target languages~\cite{szafraniec2023compiler}. Recent systems using LLMs improve validation through executability representations, intermediate translation paths, and repository context~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent}. MatchFixAgent distributes equivalence checking across specialized agents within a repository and repairs code that causes differences in behavior~\cite{ibrahimzada2025matchfixagent}. These methods expand the evidence behind an overall verification result. LADDER includes the failing training stage in that result so the repair agent can select an edit from the diagnosis.

\paragraph{Fault localization through search}
Automated program repair uses tests or semantic constraints to locate faults and guide patch generation~\cite{nguyen2013semfix}. Pretrained language models improve patch generation and enable iterative repair from execution feedback~\cite{xia2023aprplm}. Agents such as SWE-agent edit repository code through interactive tools and tests~\cite{yang2024sweagent}. Reflection and agent methods feed critiques in natural language, debugging traces, or executable code actions back into generation~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact}, while systems with multiple agents assign specialized roles and structure their interaction~\cite{qian2023chatdev,hong2023metagpt,wu2023autogen,chen2023agentverse}. Locating the failing training stage remains part of this search. Providing that stage directly from paired executions reduces the search required by LADDER's repair loop.

\paragraph{Conversion and tests of individual properties}
Conversion tools and differential tests compare a translation with a reference at a chosen interface. MindConverter targets migration from other frameworks to MindSpore~\cite{mindspore2023mindconverter}. Ivy\footnote{\url{https://github.com/unifyai/ivy}} and \texttt{torch2jax}\footnote{\url{https://github.com/rdyro/torch2jax}} convert PyTorch computations to JAX, while TorchAX preserves the PyTorch programming interface over a JAX backend~\cite{google2025torchax}. Differential testing compares semantically related executions and has exposed bugs in compilers and program analysis~\cite{yang2011csmith,le2014emi}. Testing of DL systems extends this idea to behavioral coverage and comparisons between networks~\cite{pei2017deepxplore,ma2018deepgauge}. LADDER uses comparisons between source and target executions to distinguish execution failures from failures during forward or backward computation. It checks these stages in order to identify the earliest disagreement.

\section{Method}

\subsection{Task and Verification}
Given a training program $P$ in a source framework $F_s$ and a target framework $F_t$, the migration task is to produce a translation $\hat{P}$ that executes under $F_t$ while preserving the training behavior checked in our experiments. We check compatibility of tensors and modules, agreement in forward values and losses, comparable gradients, and parameter updates with comparable direction and magnitude. We evaluate this task on \texttt{torch4ms}/MindSpore and TorchAX/JAX.

We evaluate a translation by running the source and translated programs with controlled inputs, synchronized initialization, and matched optimizer settings. Let $\mathcal{O}_{t}(P)$ denote the recorded state at training step $t$, including execution status, selected outputs or losses, gradients, and statistics of parameter updates. A translation passes when $\mathcal{O}_{t}(\hat{P})$ remains within predefined tolerances of $\mathcal{O}_{t}(P)$ for the checked steps. The adapters report these results in a common format so that the same signals apply to different target runtimes.

\subsection{What Makes a Diagnosis Useful}
Let $\mathcal{C}=(c_1,c_2,c_3)$ be the signals for execution, forward values, and gradients and updates, and let $\mathrm{fail}(\hat{P})\subseteq\mathcal{C}$ be the signals that detect a failure in the translation. The verifier maps $\hat{P}$ to the feedback supplied to the repair agent. Validation by overall outcome uses
\begin{equation}
v_{\mathrm{single}}(\hat{P}) = \mathbb{1}\!\left[\mathrm{fail}(\hat{P}) \neq \emptyset\right],
\end{equation}
which represents every failure with the same value. LADDER reports the first failing signal,
\begin{equation}
v_{\mathrm{ladder}}(\hat{P}) =
\begin{cases}
\min\left\{\, i : c_i \in \mathrm{fail}(\hat{P}) \,\right\}, & \mathrm{fail}(\hat{P}) \neq \emptyset,\\
\text{verified}, & \text{otherwise},
\end{cases}
\end{equation}
together with the metrics that produced it. Each index identifies a different repair action. Index 1 points to compatibility or operator lowering, index 2 to operator semantics, and index 3 to differentiation, parameter registration, or optimizer behavior. Two translations with the same $v_{\mathrm{single}}$ but different $v_{\mathrm{ladder}}$ require different edits. Fig.~\ref{fig:gradient-drift} illustrates this distinction. A check of forward values alone accepts a translation with faulty gradients for tens of steps. The verifier therefore includes the index and the corresponding measurements in the feedback sent to the repair agent.

\subsection{Layered Feedback}
\label{sec:hierarchy}

\paragraph{Ordering}
LADDER checks training code in the order its computation requires. The translation must execute, then preserve the forward computation, then preserve the backward and update behavior that determines learning. Each check depends on the preceding check passing,
\[
\text{execution} \rightarrow \text{forward-value} \rightarrow \text{gradient and update}.
\]
The first failing stage determines the repair target. Later signals may provide supporting evidence for that diagnosis.

\paragraph{Common adapter}
Each target framework supplies an execution adapter that runs the translation and reports execution status, selected forward values, gradients, and parameter updates in a common format. The adapter handles the details of each runtime, keeping the signals and their order unchanged.

\paragraph{Execution signal}
The execution signal determines whether $\hat{P}$ completes the required training step under the target backend. It records where execution fails, including module construction, data movement, forward execution, loss computation, backward execution, and optimizer updates, together with the exception and operator details when available. This information identifies failures in compatibility, operator lowering, device placement, data type, shape, or parameter registration. The check fails when execution raises an exception. Omitting a backward call can therefore pass the execution check, leaving the missing gradients and updates to be detected at the third stage.

\paragraph{Signal for forward values}
Once both executions complete, the signal for forward values compares logits, selected intermediate activations, and losses under controlled inputs $(x,y)$ and synchronized initialization. The simplest comparison uses the loss difference,
\begin{equation}
\Delta_{\mathrm{loss}} =
\left| L(P; x, y) - L(\hat{P}; x, y) \right|.
\end{equation}
When intermediate outputs are available, the verifier also compares outputs and individual modules to locate the earliest module whose difference exceeds tolerance. These comparisons locate mismatches in operators, reductions, broadcasting, normalization, or loss computation that would otherwise appear only in the final loss.

\paragraph{Gradient and update signal}
The gradient and update signal determines whether the translation preserves backward and optimizer behavior. Two programs may produce similar forward losses while computing different gradients, updating different parameter subsets, or applying optimizer state differently. The verifier compares gradient norms and parameter updates using
\begin{equation}
\Delta_{\mathrm{grad}} =
\left|
\|\nabla_{\theta} L(P)\|_2 -
\|\nabla_{\hat{\theta}} L(\hat{P})\|_2
\right|,
\end{equation}
\begin{equation}
\Delta_{\mathrm{param}} =
\frac{\|\Delta \theta - \Delta \hat{\theta}\|_2}
{\|\Delta \theta\|_2 + \epsilon}.
\end{equation}
Beyond aggregate norms, the verifier records missing gradients, parameters with zero gradients, mismatches in parameter names, and update outliers. A normal forward loss with missing gradients indicates a defect in automatic differentiation or parameter registration. Aligned gradients with divergent updates indicate a defect in optimizer state or parameter updates.

\subsection{Repair Loop}

\label{fig:architecture}

The repair loop in Fig.~\ref{fig:architecture} runs through an execution adapter. The primary adapter uses \texttt{torch4ms}, which provides the PyTorch programming interface and dispatches operators, backward execution, and optimizer behavior to implementations in MindSpore. The second adapter uses TorchAX with JAX automatic differentiation and Optax updates. Both report execution status, forward values, gradient measurements, and statistics of parameter updates to the verifier.

For each checked training step, we synchronize inputs, initialization, and optimizer settings between the source and translated programs. We record execution status, differences in loss and optional module outputs, differences in gradient norms, and relative $\ell_2$ differences in parameter updates. A translation is accepted only after its final version passes all three signals.

\section{Evaluation}

\subsection{Experimental Setup}
\label{sec:setup}
The evaluation answers four questions.

\begin{itemize}
  \item[\textbf{RQ1}] How does LADDER compare with existing repair systems on repair acceptance under a fixed budget?
  \item[\textbf{RQ2}] Can the three signals distinguish fault classes and locate the failing stage?
  \item[\textbf{RQ3}] How do signal coverage and repair guidance for each stage affect acceptance?
  \item[\textbf{RQ4}] Does the repair loop generalize to a second target framework and to different prompt configurations?
\end{itemize}

We collected fault categories by migrating PyTorch training programs to the two target frameworks and recording the failures. The recurring failures fall into 25 categories, grouped by the stage at which they occur and the framework mechanism responsible. We reproduce each observed category by injecting the fault into a correct implementation. This gives each instance a known fault location for evaluating diagnosis and reduces the variation present in failures collected directly from migrations. Creating instances of each category on two model families gives a set of 50 instances across CNN, image MLP, Transformer classifier, and tiny causal LM. The JAX set follows the same construction and contains six MLP and CNN faults across the three stages.

The required repair location specifies which code must change to correct a fault. One group permits changes only to the translated program. A second also permits changes to operator implementations in the compatibility layer, and a third additionally permits changes to that layer's automatic differentiation and optimizer code. An edit to code above the fault can hide its effect while leaving the faulty code unchanged. We identify the required repair location for each instance and restrict the repair agent to that code.

RQ1 compares LADDER with direct LLM repair and with the external systems SWE-agent and MatchFixAgent; the JAX study of RQ4 adds the conversion tools Ivy and \texttt{torch2jax}. RQ3 compares reduced feedback configurations, defined in Section~\ref{sec:ablations}. The MindSpore repair comparisons use the same LLM (\texttt{deepseek-v4-flash}), decoding temperature (0.1), budget of four attempts, and faulty translations. These settings hold the model and budget fixed when comparing feedback. The JAX study uses the same LLM and allows LADDER up to three repair rounds, while Direct LLM and each conversion tool run once. MatchFixAgent additionally receives the correct implementation of the changed function. This reference is available only to that baseline and gives it more information than LADDER receives.

Repair acceptance on the set of 50 instances uses checks specific to each injected fault. We report acceptance within one attempt and within a budget of four attempts. Keeping all measured differences between the source and target within their thresholds at every training step is a separate diagnostic criterion. These comparisons use $\Delta_{\mathrm{loss}}\leq0.02$, $\Delta_{\mathrm{grad}}\leq0.05$, and $\Delta_{\mathrm{param}}\leq0.03$, with the quantities defined in Section~\ref{sec:hierarchy}. These studies compare controlled executions; longer training runs and additional framework pairs remain for future evaluation. We also record edits outside the repair agent's permitted code. Token cost per accepted repair is total prompt plus completion tokens over all attempted instances divided by the number accepted. Elapsed time per accepted repair uses the same denominator.

\subsection{RQ1: Overall Repair Effectiveness}
\label{sec:main-results}
The primary experiment evaluated all 50 instances on MindSpore. All instances were hidden from the repair prompts, each allowed at most four repair attempts, and failed repairs were rolled back.

Table~\ref{tab:main-results}(a) reports repair acceptance within the shared budget of four attempts. LADDER reaches 84.0\% acceptance on the first attempt and 98.0\% by the second, with all 50 accepted within the budget. The strongest external baseline, MatchFixAgent, reaches 74.0\% and 86.0\% at the same two attempt budgets and finishes at 47/50. LADDER improves acceptance on the first attempt by 10 percentage points and is the only method to reach 50/50 within four attempts.

Results grouped by fault stage and required repair location show where methods differ. LADDER reaches 16/16 acceptance on gradient and update faults, against 13/16 for MatchFixAgent and 14/16 for direct LLM repair. For faults requiring edits to autodiff and optimizer code, LADDER reaches 4/4, MatchFixAgent 1/4, and SWE-agent 3/4. These four instances cover two categories involving alignment between gradients and parameters; one category remains unresolved by every baseline.

LADDER reaches full acceptance on all four model families. Direct LLM repair leaves six image MLP instances unresolved, accounting for six of its ten failures. MatchFixAgent's three failures occur on the Transformer classifier and image MLP.

LADDER uses 3.8K tokens and 21.8 seconds per accepted repair, against 110.7K tokens and 74.2 seconds for MatchFixAgent. These costs are lower by factors of 29 and 3.4, respectively. Fig.~\ref{fig:repair-comparison} plots cost and cumulative acceptance at the recorded budgets of one, two, and four attempts. Section~\ref{sec:ablations} examines the contribution of the feedback.

\subsection{RQ2: Fault Characterization}
\label{sec:fault-characterization}

\paragraph{Detection by fault type}
We isolate each fault's effect by synchronizing the translated model with the source at each checked step, over 50 steps, four model families, and three seeds. Execution faults cause the runtime check to fail, after which the numerical metrics are unavailable. Faults in forward computation cross the loss threshold and can also affect gradients and updates. Gradient faults leave the loss below threshold but affect gradients and updates; update faults affect only the update comparison. We record whether any run crosses each threshold. Runs without faults pass every check. The first failing check identifies the stage to repair.

\paragraph{Detection latency}
Fig.~\ref{fig:gradient-drift} shows 24 training runs with faults in which the translated model trains independently of the source, with 12 runs per fault type. The gradient signal detects the injected gradient fault at step~1 in every run, and the update signal detects the update fault at step~1. The mean loss difference crosses its threshold at steps 31 and 18, respectively. Checking forward values alone therefore delays detection of these faults.

\paragraph{Fault localization}
LADDER reports the first failing check to classify each fault as an execution, numerical, or gradient and update failure. On the set of 50 instances used to evaluate localization, this rule classifies 48 of 50 faults correctly (96\% accuracy). Both misclassified instances involve overflow during mixed precision computation. They crash before producing a loss value, so the execution check catches them before the forward comparison can run. LADDER correctly localizes all execution faults (20/20) and all gradient and update faults (16/16).

\subsection{RQ3: Ablation of the Layered Feedback}
\label{sec:ablations}
We examine which faults each signal detects and how guidance for each stage affects repair in two studies. Table~\ref{tab:feedback-ablation} compares feedback configurations on the set of 50 instances. A separate matched study adds signals one at a time on 12 tasks.

The study on 50 instances holds the tasks, attempt budget, and LLM fixed. Feedback from execution alone reports runtime status. The All signals condition supplies all three signals together without identifying the first failing stage or specifying which stage to repair. LADDER supplies the stage diagnosis and the corresponding repair guidance. The comparison varies stage selection and repair guidance together.

Adding the two numerical signals without guidance on which stage to repair raises acceptance from 33/50 to 34/50. LADDER reaches 50/50, with acceptance on the first attempt of 84\% against 66\% for All signals. The gains occur in repairs to adapter code. Acceptance rises from 8/20 to 20/20 for faults in operator code and from 0/4 to 4/4 for autodiff and optimizer faults. Token cost per accepted repair falls from 5.3K to 3.8K. Identifying the failing stage and directing the repair agent to it improve both acceptance and cost on these tasks.

The matched study adds verification signals one at a time across four model families with one fault per stage, giving 12 tasks under the same budget of four rounds. Feedback from execution alone accepts 4/12 repairs, all execution faults. Adding feedback on forward values raises acceptance to 8/12 by repairing the four numerical faults. Adding gradient and update feedback repairs the remaining four, reaching 12/12. All accepted repairs finish in the first round. Each additional signal enables repair of the fault class it detects.

\paragraph{Generalization Across Frameworks}
We evaluate LADDER on migration from PyTorch to JAX to assess its generalization across target frameworks. The same diagnostic signals and repair procedure remain effective with JAX as the target framework. As shown in Table~\ref{tab:main-results}(b), LADDER repairs all six faults in one round. It matches Direct LLM repair on execution and gradient and update faults and repairs both numerical faults, against one for Direct LLM. LADDER repairs all three instances on each model family, while Direct LLM repairs three MLP and two CNN instances. Token cost per accepted repair is 2.9K for LADDER and 15.0K for Direct LLM. Ivy and \texttt{torch2jax} produce no translation that passes training verification at any stage.

\paragraph{Framework documentation}
We test where framework documentation helps by providing it to the repair agent or the translator in separate experiments. The documentation describes operator conventions and optimizer interfaces. The repair experiment holds the translator fixed and tests pass/fail and layered feedback with documentation present or absent. It covers 24 base tasks, with 12 requiring edits to the translated program, eight to core operators, and four to core autograd or optimizer code. Each task runs under all four conditions with a budget of four rounds. The translator experiment places the same documentation in the translator prompt and disables repair. Each run therefore makes one translation call without subsequent repair. Five tasks held out for evaluation run at three repeats per condition.

Panel (a) of Table~\ref{tab:guidance-ablations} compares feedback and documentation in the repair agent. Pass/fail feedback repairs no task with documentation either present or absent. Layered feedback repairs most tasks without documentation and enables repairs in both documentation conditions. Documentation eliminates edits outside the permitted operator code. Acceptance remains lowest for faults requiring changes to automatic differentiation and optimizer code.

In panel (b), framework documentation enables every translation to pass all three checks in one attempt. Without documentation, most outputs fail to compile and none pass training verification. Together, the two experiments show that documentation is most useful during initial translation, while layered feedback guides subsequent repair.

\section{Conclusion}

We introduced LADDER, a framework for repairing training programs migrated across frameworks. It checks execution, forward values, and gradients and updates in sequence, then directs repair to the first failing stage. The diagnosis localizes 48 of 50 faults correctly (96\% accuracy). On the MindSpore benchmark of 50 instances, LADDER achieves 100\% repair acceptance within four attempts and reduces token cost per accepted repair by a factor of 29 compared with the strongest external baseline. The same loop repairs all six faults in the JAX study, demonstrating the effectiveness of the diagnosis and repair procedure across target frameworks.
