\title{MARS: A Multi-Agent Repair System for Training Code Migration via Layered Diagnosis}

\author{\IEEEauthorblockN{Anonymous Authors}
\IEEEauthorblockA{Anonymous Institution\\
anonymous@example.com}}

\maketitle

\begin{abstract}
Large language models can translate deep learning training
programs across frameworks, but an executable translation may still
compute incorrect gradients or update the wrong parameters. These
faults can remain hidden when verification checks only forward values,
and an overall pass or fail result provides little guidance on where
to repair. Training stages depend on one another, so the earliest disagreement
between source and target executions can help distinguish operator
errors from failures in differentiation or optimization. In this paper, we
propose MARS, a multi-agent repair system that uses layered diagnosis
to repair migrated training code. An orchestrator coordinates three agents
for translation, verification, and repair. The translator produces an
initial target program. The verifier compares execution status, forward
values, gradients, and parameter updates between source and target
programs in training order. The resulting diagnosis directs the repair agent
to the affected computation and supplies the measurements needed to
revise the code. After each edit, the orchestrator invokes verification
again and uses the updated diagnosis to coordinate further repair
within a fixed attempt budget. On 50 MindSpore fault instances, MARS
achieves full acceptance within four attempts, with 84\% accepted on
the first attempt and approximately 29-fold lower token cost per accepted
repair than MatchFixAgent. Evaluations on MindSpore and
JAX demonstrate the effectiveness of the same diagnosis and
repair procedure across target frameworks.
\end{abstract}

\begin{IEEEkeywords}
cross-framework migration, training-code translation, layered feedback, program repair, differential testing
\end{IEEEkeywords}

\section{Introduction}

Large language model (LLM) agents support code migration by translating programs and iteratively repairing them with execution feedback~\cite{he-etal-2025-execoder,guan2025repotransagent,ibrahimzada2025matchfixagent}. Migrating deep learning training code from PyTorch to MindSpore or JAX also requires preserving the computations that determine learning. A translated program may execute while producing different forward values, match the source loss but compute incorrect gradients, or update a different parameter set despite plausible gradients. Frameworks differ in operator conventions, differentiation interfaces, and optimizer semantics, so execution success alone does not establish correct training behavior~\cite{paszke2019pytorch,mindspore2020whitepaper,google2025torchax}. An overall pass or fail result does not distinguish these failures or indicate which computation the agent should correct. Effective repair requires feedback that detects discrepancies in training behavior and relates them to the code requiring an edit.

Agreement in forward values can conceal faults in the computations that follow them. In Fig.~\ref{fig:gradient-drift}, the corresponding gradient or parameter update check detects each injected fault at step~1 in every run, whereas the mean loss difference crosses its threshold only at steps 31 and 18 in panels (a) and (b), respectively. Incorrect updates accumulate before their effects become apparent in the loss. Comparing gradients and parameter updates makes these faults observable, and the dependencies between training stages give the measurements a diagnostic order. Execution failures must be resolved before numerical agreement can be assessed. Once forward values agree, discrepancies in gradients or parameter updates point to differentiation, parameter registration, or optimizer behavior. Reporting the earliest disagreement in this order directs the agent to the computation requiring correction and provides a basis for choosing its next edit.

We propose MARS (Multi-Agent Repair System), which uses layered diagnosis to coordinate translation, verification, and repair. The translator agent supplies an initial target program. The verifier agent compares it with the source in training order and reports the earliest failing stage together with the measurements that explain the discrepancy. The repair agent uses this diagnosis to edit the affected code. An orchestrator coordinates the three agents and invokes verification after each edit, using the updated diagnosis to guide subsequent attempts within a fixed budget. Experiments on MindSpore and JAX evaluate the same diagnostic signals and repair procedure across target frameworks. On the 50-instance MindSpore repair set, MARS achieves full acceptance within four attempts with approximately 29-fold lower token cost per accepted repair than MatchFixAgent. Ablations show that identifying the failing stage and supplying repair guidance improve acceptance beyond providing all measured signals together. This paper makes three contributions.
\begin{itemize}
  \item We develop layered training diagnosis that checks execution, forward values, gradients, and parameter updates in training order and reports the earliest disagreement to guide repair.
  \item We introduce MARS, a multi-agent system that coordinates translation, verification, and repair around this diagnosis, linking code edits to updated verification within a fixed attempt budget.
  \item We evaluate MARS on MindSpore and JAX, demonstrating improved repair acceptance and lower token cost, and analyze the roles of diagnostic signal coverage and guidance for the failing stage.
\end{itemize}

\section{Related Work}
We group related work by how it obtains repair feedback, covering validation by overall outcome, fault localization through search, and conversion tools or tests of individual properties.

\paragraph{Validation by overall outcome}
Most translation systems validate a translation by one pass or fail result for the whole program. Early neural translation learned from multilingual corpora without direct supervision~\cite{roziere2020transcoder}. Later work used automated unit tests to validate translations and supervise training on the model's own outputs~\cite{roziere2021unittests}, and compiler representations reduced semantic gaps between source and target languages~\cite{szafraniec2023compiler}. Recent systems using LLMs improve validation through executability representations, intermediate translation paths, and repository context~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent}. MatchFixAgent distributes equivalence checking across specialized agents within a repository and repairs code that causes differences in behavior~\cite{ibrahimzada2025matchfixagent}. These methods expand the evidence behind an overall verification result. MARS includes the failing training stage in that result so the repair agent can select an edit from the diagnosis.

\paragraph{Fault localization through search}
Automated program repair uses tests or semantic constraints to locate faults and guide patch generation~\cite{nguyen2013semfix}. Pretrained language models improve patch generation and enable iterative repair from execution feedback~\cite{xia2023aprplm}. Agents such as SWE-agent edit repository code through interactive tools and tests~\cite{yang2024sweagent}. Reflection and agent methods feed critiques in natural language, debugging traces, or executable code actions back into generation~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact}, while systems with multiple agents assign specialized roles and structure their interaction~\cite{qian2023chatdev,hong2023metagpt,wu2023autogen,chen2023agentverse}. Locating the failing training stage remains part of this search. Providing that stage directly from paired executions reduces the search required by MARS's repair loop.

\paragraph{Conversion and tests of individual properties}
Conversion tools and differential tests compare a translation with a reference at a chosen interface. MindConverter targets migration from other frameworks to MindSpore~\cite{mindspore2023mindconverter}. Ivy\footnote{\url{https://github.com/unifyai/ivy}} and \texttt{torch2jax}\footnote{\url{https://github.com/rdyro/torch2jax}} convert PyTorch computations to JAX, while TorchAX preserves the PyTorch programming interface over a JAX backend~\cite{google2025torchax}. Differential testing compares semantically related executions and has exposed bugs in compilers and program analysis~\cite{yang2011csmith,le2014emi}. Testing of deep learning systems extends this idea to behavioral coverage and comparisons between networks~\cite{pei2017deepxplore,ma2018deepgauge}. MARS uses comparisons between source and target executions to distinguish execution failures from failures during forward or backward computation. It checks these stages in order to identify the earliest disagreement.

\section{Method}

\subsection{Task and Verification}
Given a training program $P$ in a source framework $F_s$ and a target framework $F_t$, the migration task is to produce a translation $\hat{P}$ that executes under $F_t$ while preserving the training behavior checked in our experiments. We check compatibility of tensors and modules, agreement in forward values and losses, comparable gradients, and parameter updates with comparable direction and magnitude. We evaluate this task on \texttt{torch4ms}/MindSpore and TorchAX/JAX.

We evaluate a translation by running the source and translated programs with controlled inputs, synchronized initialization, and matched optimizer settings. Let $\mathcal{O}_{t}(P)$ denote the recorded state at training step $t$, including execution status, selected outputs or losses, gradients, and statistics of parameter updates. A translation passes when $\mathcal{O}_{t}(\hat{P})$ remains within predefined tolerances of $\mathcal{O}_{t}(P)$ for the checked steps. The adapters report these results in a common format so that the same signals apply to different target runtimes.

\subsection{What Makes a Diagnosis Useful}
Let $\mathcal{C}=(c_1,c_2,c_3)$ be the signals for execution, forward values, and gradients and updates, and let $\mathrm{fail}(\hat{P})\subseteq\mathcal{C}$ be the signals that detect a failure in the translation. The verifier maps $\hat{P}$ to the feedback supplied to the repair agent. Validation by overall outcome uses
\begin{equation}
v_{\mathrm{single}}(\hat{P}) = \mathbf{1}\!\left[\mathrm{fail}(\hat{P}) \neq \emptyset\right],
\end{equation}
which represents every failure with the same value. MARS reports the first failing signal,
\begin{equation}
v_{\mathrm{mars}}(\hat{P}) =
\begin{cases}
\min\left\{\, i : c_i \in \mathrm{fail}(\hat{P}) \,\right\}, & \mathrm{fail}(\hat{P}) \neq \emptyset,\\
\text{verified}, & \text{otherwise},
\end{cases}
\end{equation}
together with the metrics that produced it. Each index identifies a different repair action. Index 1 points to compatibility or operator lowering, index 2 to operator semantics, and index 3 to differentiation, parameter registration, or optimizer behavior. Two translations with the same $v_{\mathrm{single}}$ but different $v_{\mathrm{mars}}$ require different edits. Fig.~\ref{fig:gradient-drift} illustrates this distinction. A check of forward values alone accepts a translation with faulty gradients for tens of steps. The verifier therefore includes the index and the corresponding measurements in the feedback sent to the repair agent.

\subsection{Layered Feedback}
\label{sec:hierarchy}

\paragraph{Ordering}
MARS checks training code in the order its computation requires. The translation must execute, then preserve the forward computation, then preserve the backward and update behavior that determines learning. Each check depends on the preceding check passing,
\[
\text{execution} \rightarrow \text{forward values} \rightarrow \text{gradients and updates}.
\]
The first failing stage determines the repair target. Later signals may provide supporting evidence for that diagnosis.

\paragraph{Common adapter}
Each target framework supplies an execution adapter that runs the translation and reports execution status, selected forward values, gradients, and parameter updates in a common format. The adapter handles the details of each runtime, keeping the signals and their order unchanged.

\paragraph{Execution signal}
The execution signal determines whether $\hat{P}$ completes the required training step under the target backend. It records where execution fails, including module construction, data movement, forward execution, loss computation, backward execution, and optimizer updates, together with the exception and operator details when available. This information identifies failures in compatibility, operator lowering, device placement, data type, shape, or parameter registration. The check fails when execution raises an exception. Omitting a backward call can therefore pass the execution check, leaving the missing gradients and updates to be detected at the third stage.

\paragraph{Signal for forward values}
Once both executions complete, the signal for forward values compares logits, selected intermediate activations, and losses under controlled inputs $(x,y)$ and synchronized initialization. The simplest comparison uses the loss difference,
\begin{equation}
\Delta_{\mathrm{loss}} =
\left| L(P; x, y) - L(\hat{P}; x, y) \right|.
\end{equation}
When intermediate outputs are available, the verifier also compares outputs and individual modules to locate the earliest module whose difference exceeds tolerance. These comparisons locate mismatches in operators, reductions, broadcasting, normalization, or loss computation that would otherwise appear only in the final loss.

\paragraph{Gradient and parameter update signal}
The gradient and parameter update signal determines whether the translation preserves backward and optimizer behavior. Two programs may produce similar forward losses while computing different gradients, updating different parameter subsets, or applying optimizer state differently. The verifier compares gradient norms and parameter updates using
\begin{equation}
\Delta_{\mathrm{grad}} =
\left|
\|\nabla_{\theta} L(P)\|_2 -
\|\nabla_{\hat{\theta}} L(\hat{P})\|_2
\right|,
\end{equation}
\begin{equation}
\Delta_{\mathrm{param}} =
\frac{\|\Delta \theta - \Delta \hat{\theta}\|_2}
{\|\Delta \theta\|_2 + \epsilon}.
\end{equation}
Beyond aggregate norms, the verifier records missing gradients, parameters with zero gradients, mismatches in parameter names, and update outliers. A normal forward loss with missing gradients indicates a defect in automatic differentiation or parameter registration. Aligned gradients with divergent updates indicate a defect in optimizer state or parameter updates.

\subsection{Repair Loop}

\centering
\includegraphics[width=0.97\textwidth]{figures/hierarchical_feedback_architecture.png}
\caption{MARS's repair loop. An orchestrator coordinates the translator, verifier, and repair agents. The verifier's diagnosis guides edits to the permitted code, followed by verification of the updated program. The \texttt{torch4ms}/MindSpore and TorchAX/JAX implementations use the same diagnostic signals and repair procedure.}
\label{fig:architecture}
\end{figure*}

The repair loop in Fig.~\ref{fig:architecture} runs through an execution adapter. The primary adapter uses \texttt{torch4ms}, which provides the PyTorch programming interface and dispatches operators, backward execution, and optimizer behavior to implementations in MindSpore.\footnote{The primary prototype repository is available at \url{https://gitee.com/feixiao13/ascend-torch4ms.git}.} The second adapter uses TorchAX with JAX automatic differentiation and Optax updates. Both report execution status, forward values, gradient measurements, and statistics of parameter updates to the verifier.

The translator agent supplies the initial program, the verifier agent identifies the first failing stage, and the repair agent edits the permitted code using that diagnosis. The orchestrator coordinates these three agents, repeats verification after each edit, and enforces the attempt budget. It retains edits that improve the verification score and rolls back those that do not.

For each checked training step, we synchronize inputs, initialization, and optimizer settings between the source and translated programs. We record execution status, differences in loss and optional module outputs, differences in gradient norms, and relative $\ell_2$ differences in parameter updates. The verifier reports unavailable measurements when execution fails. Acceptance follows the checks specified for each experiment in Section~\ref{sec:setup}.

\section{Evaluation}

\subsection{Experimental Setup}
\label{sec:setup}
The evaluation answers four questions.

\begin{itemize}
  \item[\textbf{RQ1}] How does MARS compare with existing repair systems on repair acceptance under a fixed budget?
  \item[\textbf{RQ2}] Can the three signals distinguish fault classes and locate the failing stage?
  \item[\textbf{RQ3}] How do signal coverage and repair guidance for each stage affect acceptance?
  \item[\textbf{RQ4}] Does the repair loop generalize to a second target framework and to different prompt configurations?
\end{itemize}

We collected fault categories by migrating PyTorch training programs to the two target frameworks and recording the failures. The recurring failures fall into 25 categories, grouped by the stage at which they occur and the framework mechanism responsible. Ten categories cause execution failures, seven affect forward values, and eight affect gradients or parameter updates. The latter 15 produce executable programs with incorrect training behavior. We reproduce each observed category by injecting the fault into a correct implementation. This gives each instance a known fault location for evaluating diagnosis and reduces the variation present in failures collected directly from migrations. Creating instances of each category on two model families gives a set of 50 instances across CNN, image MLP, Transformer classifier, and tiny causal LM. The JAX set follows the same construction and contains six MLP and CNN faults across the three stages.

The required repair location specifies which code must change to correct a fault. One group permits changes only to the translated program. A second also permits changes to operator implementations in the compatibility layer, and a third additionally permits changes to that layer's automatic differentiation and optimizer code. An edit to code above the fault can hide its effect while leaving the faulty code unchanged. We identify the required repair location for each instance and restrict the repair agent to that code.

RQ1 compares MARS with direct LLM repair and with the external systems SWE-agent and MatchFixAgent; the JAX study of RQ4 adds the conversion tools Ivy and \texttt{torch2jax}. RQ3 compares reduced feedback configurations, defined in Section~\ref{sec:ablations}. The MindSpore repair comparisons use the same LLM (\texttt{deepseek-v4-flash}), decoding temperature (0.1), budget of four attempts, and faulty translations. These settings hold the model and budget fixed when comparing feedback. The JAX study uses the same LLM and allows MARS up to three repair rounds, while Direct LLM and each conversion tool run once. MatchFixAgent additionally receives the correct implementation of the changed function. This reference is available only to that baseline and gives it more information than MARS receives.

We also evaluate complete migration from PyTorch source programs to MindSpore on five held-out tasks: image MLP, CNN, ResNet, Transformer classifier, and tiny causal language model. Each method is evaluated with three seeds. MARS allows an initial translation followed by up to four repair rounds; Direct LLM and CodeTransEngine translate once. MSAdapter uses one candidate per task, with a common CPU compatibility patch. This study checks whether the resulting programs complete training and preserve paired loss, gradient, and parameter update measurements.

Repair acceptance on the set of 50 instances uses checks specific to each injected fault. We report acceptance within one attempt and within a budget of four attempts. Keeping all measured differences between the source and target within their thresholds at every training step is a separate diagnostic criterion. These comparisons use $\Delta_{\mathrm{loss}}\leq0.02$, $\Delta_{\mathrm{grad}}\leq0.05$, and $\Delta_{\mathrm{param}}\leq0.03$, with the quantities defined in Section~\ref{sec:hierarchy}. Token cost per accepted repair is total prompt plus completion tokens over all attempted instances divided by the number accepted. Elapsed time per accepted repair uses the same denominator.

All correct reference translations in the diagnostic study pass the checks. We trained CNN, MLP, Transformer, and tiny causal LM models for 50 steps over three seeds. Differences between the source and translated models remain below the diagnostic thresholds at every checked step. The maximum loss difference is $3.815\times10^{-6}$, and mean differences in gradient norms and parameter updates stay below $4\times10^{-8}$ and $3.9\times10^{-6}$.

We measure detection independently of repair to determine whether each signal identifies its intended fault class. The study covers four model families and three seeds for each of the three fault classes. The intended signal detects all 36 injected faults. An incorrect forward value can also perturb gradients and trigger later signals. Reporting the earliest disagreement keeps the diagnosis at the stage where the fault occurs. On the tiny causal LM, for example, the forward comparison detects the forward fault even though the gradient signal remains below threshold.

\subsection{RQ1: Overall Repair Effectiveness}
\label{sec:main-results}
Layered diagnosis improves both early repair acceptance and the result reached within the attempt budget. On the 50 MindSpore instances in Table~\ref{tab:main-results}, MARS's first-attempt acceptance exceeds the strongest external baseline by 10 percentage points. Fig.~\ref{fig:repair-comparison} shows that subsequent attempts preserve this advantage: MARS approaches full acceptance by the second attempt and resolves the remaining instance within four. The diagnosis therefore helps across the repair process, including cases that require revision of an initial edit.

The remaining difficulty for external agents lies primarily in repairing the target implementation. SWE-agent and MatchFixAgent resolve every fault confined to the translated program, but leave faults in automatic differentiation or optimizer code unresolved. These faults concern alignment between gradients and parameters, where a program can execute and produce a plausible loss despite incorrect learning behavior. MARS resolves all four such instances, including an instance missed by every baseline. This pattern connects the repair advantage to the backward and update behavior that the layered verifier explicitly checks. Section~\ref{sec:ablations} examines the effect of supplying that diagnosis to the repair agent.

Higher acceptance is accompanied by lower repair cost. MARS uses approximately 29-fold fewer tokens and 3.4-fold less elapsed time per accepted repair than MatchFixAgent. Because both measures include unsuccessful attempts, they account for the cost of the full repair process. The cost and acceptance curves in Fig.~\ref{fig:repair-comparison} show that MARS attains higher acceptance at a lower token cost under the same attempt budget.

\subsection{RQ2: Fault Characterization}
\label{sec:fault-characterization}

\paragraph{Detection by fault type}
We isolate each fault's effect by synchronizing the translated model with the source at each checked step, over 50 steps, four model families, and three seeds. Execution faults cause the runtime check to fail, after which the numerical metrics are unavailable. Faults in forward computation cross the loss threshold and can also affect gradients and updates. Gradient faults leave the loss below threshold but affect gradients and updates; update faults affect only the update comparison. We record whether any run crosses each threshold. Runs without faults pass every check. The first failing check identifies the stage to repair.

\paragraph{Detection latency}
Incorrect gradients and parameter updates can affect learning before they produce a detectable loss difference. In Fig.~\ref{fig:gradient-drift}, the translated model retains its own state across steps, so incorrect updates accumulate and affect later forward computations. The corresponding gradient or update check detects each fault immediately, while the mean loss difference crosses its threshold only after further training. The study covers four model families and three seeds for each fault type, giving 24 runs. This delay explains why agreement in forward values alone provides incomplete feedback for repairing training code.

\paragraph{Fault localization}
MARS reports the first failing check to classify faults in execution, forward computation, or gradients and parameter updates. On the set of 50 instances used to evaluate localization, this rule classifies 48 of 50 faults correctly (96\% accuracy). Both misclassified instances involve overflow during mixed precision computation. They crash before producing a loss value, so the execution check catches them before the forward comparison can run. MARS correctly localizes all execution faults (20/20) and all gradient and parameter update faults (16/16).

\subsection{RQ3: Ablation of the Layered Feedback}
\label{sec:ablations}
We examine which faults each signal detects and how guidance for each stage affects repair in two studies. Table~\ref{tab:feedback-ablation} compares feedback configurations on the set of 50 instances. A separate matched study adds signals one at a time on 12 tasks.

The study on 50 instances holds the tasks, attempt budget, and LLM fixed. Feedback from execution alone reports runtime status. The All signals condition supplies all three signals together without identifying the first failing stage or specifying which stage to repair. MARS supplies the stage diagnosis and the corresponding repair guidance. The comparison varies stage selection and repair guidance together.

Supplying all measured signals adds only one accepted repair over execution feedback alone. Stage selection and repair guidance account for the larger gain in Table~\ref{tab:feedback-ablation}, and all 16 additional repairs occur in adapter code. Both the All signals condition and MARS resolve the faults confined to the translated program; their difference emerges when an error must be traced into operator implementations or automatic differentiation and optimizer code. Organizing the measurements into a diagnosis helps the repair agent act on these failures. The improvement in first-attempt acceptance and the lower token cost show that this guidance also reduces the cost of reaching an accepted repair.

The separate 12-task study explains why all three signals are needed. With one fault per stage across four model families and a budget of four rounds, execution feedback repairs the four execution faults. Adding forward comparisons exposes and repairs the four forward faults, while gradient and parameter update feedback enables repair of the remaining four. Acceptance thus increases from 4/12 to 8/12 to 12/12, with every accepted repair completing in the first round. Here the additional signals change which faults the agent can address, rather than how many iterations it needs for a fault it already detects.

\paragraph{Complete migration to MindSpore}
Completing a training update does not ensure that a translation preserves the source computation. Table~\ref{tab:framework-results}(a) makes this distinction visible for MSAdapter: every candidate produces gradients and parameter updates, yet none passes paired verification. Its relative parameter update differences range from 1.38 to 2.81, well above the threshold of 0.03. Direct LLM and CodeTransEngine also lose accepted cases when moving from executable training to numerical agreement. These results explain the need to verify the training behavior of an executable translation. MARS's initial translations pass both checks on these tasks without invoking the repair agent.

\paragraph{Generalization Across Frameworks}
The same diagnostic signals and repair procedure remain effective with JAX as the target framework. In Table~\ref{tab:framework-results}(b), MARS repairs faults at all three stages in one round. The additional repair over Direct LLM concerns forward computation in the CNN, showing that the diagnosis remains useful when the target operator implementations change. Ivy and \texttt{torch2jax} execute some programs and pass selected forward checks, but none of their outputs passes final training verification. This progression again separates execution compatibility from preservation of learning behavior. MARS also uses fewer tokens per accepted repair than Direct LLM, 2.9K versus 15.0K, including the tokens spent on unsuccessful attempts.

\paragraph{Framework documentation}
Framework documentation supplies operator conventions and optimizer interfaces, while a diagnosis identifies the computation that failed in a particular program. We examine their roles by providing documentation to the repair agent or the translator in separate experiments. The repair study holds the translator fixed and crosses pass/fail or layered feedback with documentation present or absent. Its 24 tasks require edits to the translated program, operator code, or automatic differentiation and optimizer code, under four repair rounds. The translation study disables repair and evaluates five held-out tasks with three repeats per condition.

During repair, documentation improves adherence to the permitted editing scope without consistently improving acceptance. In Table~\ref{tab:guidance-ablations}(a), it eliminates edits outside operator code while leaving the number of accepted operator repairs unchanged. It also reduces acceptance for faults in the translated program, and neither documentation condition resolves the automatic differentiation and optimizer faults. The pass/fail conditions accept no repairs, whereas layered feedback supports repair with documentation present or absent. These outcomes distinguish information about framework conventions from the diagnosis needed to act on a specific fault.

Documentation has a more direct effect on initial translation. Without it, most generated programs fail to compile; with it, all translations pass training verification in one attempt (Table~\ref{tab:guidance-ablations}(b)). Supplying the target conventions before code generation prevents failures that would otherwise enter the repair loop. Once a faulty program exists, the layered diagnosis provides the program-specific evidence needed to choose an edit.

\section{Conclusion}

We introduced MARS, a framework that repairs training code across deep learning frameworks through layered diagnosis. Specifically, MARS checks execution, forward values, gradients, and parameter updates in training order, then uses the first failing stage to guide repair. This design detects faults that forward checks miss and turns verification results into guidance for editing the affected computation. Experiments on MindSpore and JAX demonstrate that MARS improves repair acceptance and reduces token cost while applying the same diagnosis and repair procedure across target frameworks.
