\title{LADDER: Training-Code Migration Repair via Layered Diagnosis}

\author{\IEEEauthorblockN{Anonymous Authors}

\maketitle

\begin{abstract}
The maturation of LLM-based code translation has made it practical to port deep learning training programs across frameworks. Automated migration offers a route to reusing these programs on a new backend, but is frequently defeated by differences in operator semantics, automatic differentiation, and optimizer behavior. Existing translation and repair pipelines validate a candidate against a single outcome such as a clean execution or a passing test, without asking which training stage failed. We argue that the granularity of repair feedback, and not only its accuracy, governs whether a migration failure can be repaired: a candidate that executes cleanly and reproduces the source loss at every step can still apply a zero parameter update, so one verdict cannot separate a healthy migration from a silently broken one. We introduce Layered Differential Diagnosis for Execution Repair (LADDER), which compares paired source and candidate executions at the execution, forward-value, and gradient/update stages and uses the first failing stage to guide repair. Each check is enabled only after its prerequisite stage passes, so the order follows the dependency of training computation. A common adapter interface carries the same checks to a second target framework. On a 50-instance MindSpore pool, LADDER is the only method that verifies every migration, reaching 84.0\% repair on the first attempt against 74.0\% for the strongest repair baseline while using $27\times$ fewer tokens; a six-instance JAX study verifies all instances.
\end{abstract}

\begin{IEEEkeywords}
cross-framework migration, training-code translation, layered feedback, program repair, differential testing
\end{IEEEkeywords}

\section{Introduction}

Large language models (LLMs) have made source-code translation increasingly practical, and recent systems improve generated programs through execution, repository context, and iterative feedback~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent,erer2025fullyautomated,gray2025workflows}. Cross-framework migration of deep learning (DL) training code raises a stricter problem. Correctness for such a program extends beyond control flow and API behavior to the tensor computations, automatic differentiation, optimizer state, and parameter updates that determine learning.

This requirement creates failures that ordinary executability checks cannot see. A translated training script may run successfully while producing different logits or losses. It may match the forward computation but propagate incorrect gradients, or compute plausible gradients while updating a different parameter set. Such failures arise across framework boundaries because runtimes differ in operator conventions, execution modes, differentiation interfaces, and optimizer semantics~\cite{paszke2019pytorch,mindspore2020whitepaper,google2025torchax}. A successful run is only the first condition of a correct training migration.

Existing systems supply repair feedback in three main ways. Translation pipelines validate against a single outcome such as compilation, unit tests, or repository-level pass rates~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent}. Repair agents explore the program until a test or execution trace exposes the fault~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact,xia2023aprplm,yang2024sweagent}. Conversion and differential-testing tools compare a converted output or a single behavioral property against a reference~\cite{mindspore2023mindconverter,yang2011csmith,pei2017deepxplore}. Despite their variety, all three share a critical implicit assumption, that one verdict on the whole program is a sufficient unit of repair feedback.

This assumption, however, does not hold for training code. Figure~\ref{fig:divergence} makes the failure concrete. A candidate that runs to completion and reproduces the source loss to within $2\times10^{-4}$ of the forward tolerance at every one of 50 steps applies a zero parameter update throughout, and its gradient is never computed at all. Execution feedback reports success, forward feedback reports agreement, and the migration is nonetheless broken in the one respect that matters for learning. Execution failures, forward mismatches, and backward/update errors collapse onto the same verdict even though each calls for a different repair. Training correctness follows an ordered sequence. A candidate first executes, then preserves the forward computation, and finally preserves gradients and parameter updates. The first stage that fails provides actionable repair guidance. Execution failures point to compatibility and lowering, forward failures point to operator semantics, and gradient/update failures point to automatic differentiation, parameter registration, or optimizer behavior.

Based on this observation, we propose Layered Differential Diagnosis for Execution Repair (LADDER), which turns the three checks into an ordered verdict rather than a single one. Paired source and candidate executions are normalized into a common report, and a repair component uses the first failing stage to produce a targeted patch before re-verification. Because each check is meaningful only after the preceding check passes, the order follows the dependency of training computation. A common adapter interface separates the checks from backend execution, so the same repair guidance applies to \texttt{torch4ms}/MindSpore\footnote{The primary prototype repository is available at \url{https://gitee.com/feixiao13/ascend-torch4ms.git}.} and TorchAX/JAX.

This paper makes three contributions:
\begin{itemize}
  \item We show that a single execution verdict cannot guide repair for training-code migration, and formulate validation as a sequence of execution, forward-value, and gradient/update checks.
  \item We introduce LADDER, which turns the first failing check into targeted repair guidance and re-verifies the candidate through a common interface across target frameworks.
  \item On 50 real migration failures, LADDER verifies 50/50 instances, repairs 84.0\% on the first attempt, and uses 0.19M tokens; it also verifies all six faults in a JAX study.
\end{itemize}

\section{Related Work}
We group related work by how it obtains repair feedback: outcome-level validation, search-based fault localization, and conversion or single-property comparison.

\textbf{Outcome-level validation.}
Most translation systems validate a candidate by one verdict on the whole program. Early neural translation learned from multilingual corpora without direct supervision~\cite{roziere2020transcoder}; later work added automated unit tests as both validation and a self-training signal~\cite{roziere2021unittests}; and compiler representations were introduced to narrow source--target semantic gaps~\cite{szafraniec2023compiler}. Recent LLM-based systems enrich what the candidate is checked against through executability representations, intermediate translation paths, and repository-level context~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent}. MatchFixAgent decomposes repository-level equivalence checking across specialized agents and repairs the inequivalences it finds~\cite{ibrahimzada2025matchfixagent}. These systems improve the information available to validation, but their feedback remains organized around an overall outcome. LADDER instead reports which training stage fails first, making that stage the unit of repair guidance.

\textbf{Search-based fault localization.}
This group treats fault location as something to be discovered by exploring the program. Automated program repair has long used tests or semantic constraints to guide patch generation~\cite{nguyen2013semfix}, and pretrained language models made patch generation more fluent while enabling iterative repair from execution feedback~\cite{xia2023aprplm}. Repository-level agents such as SWE-agent edit code iteratively through interactive tools and test feedback~\cite{yang2024sweagent}; reflection and agent-based methods return natural-language critiques, self-debugging traces, or executable code actions to the generation loop~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact}; and multi-agent systems add role specialization and structured workflows~\cite{qian2023chatdev,hong2023metagpt,wu2023autogen,chen2023agentverse}. These methods search for a repair location because a whole-program failure does not identify the failing training stage. LADDER supplies that stage directly from paired executions, reducing the amount of search required by the repair loop.

\textbf{Conversion and single-property comparison.}
Conversion tools and differential tests compare a candidate with a reference at a chosen interface. MindConverter targets migration from third-party frameworks to MindSpore~\cite{mindspore2023mindconverter}; Ivy\footnote{\url{https://github.com/unifyai/ivy}} and \texttt{torch2jax}\footnote{\url{https://github.com/rdyro/torch2jax}} convert PyTorch computations to JAX; and TorchAX preserves a PyTorch-style front end over a JAX backend~\cite{google2025torchax}. Differential testing compares semantically related executions and has exposed compiler and program-analysis bugs~\cite{yang2011csmith,le2014emi}; DL-system testing has extended this idea to behavioral coverage and network-level comparisons~\cite{pei2017deepxplore,ma2018deepgauge}. These tools establish the value of comparing source and target executions, but a single comparison does not distinguish an execution failure from a forward or backward failure. LADDER makes that distinction explicit by checking the three stages in order.

\section{Method}

\subsection{Task and Verification}
Given a training program $P$ in a source framework $F_s$ and a target framework $F_t$, the migration task is to produce a candidate $\hat{P}$ that executes under $F_t$ while preserving the training behavior checked in our experiments. These checks cover compatible tensors and modules, comparable forward values and losses, comparable gradients, and parameter updates with comparable direction and magnitude. We instantiate this task on \texttt{torch4ms}/MindSpore and TorchAX/JAX.

We evaluate a candidate through paired executions under controlled inputs, synchronized initialization, and matched optimizer settings. Let $\mathcal{O}_{t}(P)$ denote the observable state at training step $t$, comprising execution status, selected outputs or losses, gradients, and parameter-update statistics. A candidate passes when $\mathcal{O}_{t}(\hat{P})$ remains within predefined tolerances of $\mathcal{O}_{t}(P)$ for the checked steps. The adapters expose these observables in a common form so that the same checks apply to different target runtimes.

\subsection{What Makes a Diagnosis Useful}
Before describing the checks, we state the property the feedback must have. Let $\mathcal{C}=(c_1,c_2,c_3)$ be the execution, forward-value, and gradient/update checks, and let $\mathrm{fail}(\hat{P})\subseteq\mathcal{C}$ be the checks the candidate violates. A verdict is a map from $\hat{P}$ to the feedback the repair component receives. Outcome-level validation uses
\begin{equation}
v_{\mathrm{single}}(\hat{P}) = \mathbb{1}\!\left[\mathrm{fail}(\hat{P}) \neq \emptyset\right],
\end{equation}
which collapses every distinct failure onto one bit. LADDER instead reports the first failing check,
\begin{equation}
v_{\mathrm{ladder}}(\hat{P}) =
\begin{cases}
\min\left\{\, i : c_i \in \mathrm{fail}(\hat{P}) \,\right\}, & \mathrm{fail}(\hat{P}) \neq \emptyset,\\
\text{verified}, & \text{otherwise},
\end{cases}
\end{equation}
together with the metrics that produced it. The value of $v_{\mathrm{ladder}}$ is useful because each index names a different repair action: index 1 points to compatibility or lowering, index 2 to operator semantics, and index 3 to differentiation, parameter registration, or optimizer behavior. Two candidates with the same $v_{\mathrm{single}}$ but different $v_{\mathrm{ladder}}$ require different edits, which is precisely the distinction Figure~\ref{fig:divergence} shows a single verdict discarding. The verifier therefore preserves the index and its evidence in the feedback delivered to the repair component.

\subsection{Layered Feedback}
\label{sec:hierarchy}

\paragraph{Ordering.}
LADDER checks training code in the order required by its computation: the candidate must execute, preserve the forward computation, and preserve the backward and update behavior that determines learning. A later check is meaningful only after its prerequisite passes:
\[
\text{execution} \rightarrow \text{forward numerical} \rightarrow \text{gradient/update}.
\]
The first failing stage becomes the primary repair guidance. Later checks may provide supporting evidence, but they do not replace the earliest point at which the source and candidate executions diverge.

\paragraph{Common adapter.}
Each target path supplies an execution adapter that runs the candidate and exposes phase status, selected forward values, gradients, and parameter deltas in a common report. Runtime-specific details remain inside the adapter; the checks and their order remain unchanged.

\paragraph{Execution check.}
The execution check determines whether $\hat{P}$ completes the required training step under the target backend. It records the phase of failure, including module construction, data movement, forward execution, loss computation, backward execution, and optimizer stepping, together with the exception and operator context when available. This phase identifies compatibility, lowering, placement, dtype, shape, and parameter-registration failures.

\paragraph{Forward-value check.}
Once both executions complete, the forward-value check compares logits, selected intermediate activations, and losses under controlled inputs $(x,y)$ and synchronized initialization. The minimal scalar comparison is
\begin{equation}
\Delta_{\mathrm{loss}} =
\left| L(P; x, y) - L(\hat{P}; x, y) \right|.
\end{equation}
When intermediate outputs are available, the verifier also computes output- and module-level discrepancies and locates the earliest module whose difference exceeds tolerance. This distinguishes an operator, reduction, broadcasting, normalization, or loss mismatch that would otherwise appear only as an end-to-end loss difference.

\paragraph{Gradient and update check.}
The gradient and update check determines whether the candidate preserves backward and optimizer behavior. Two programs may produce similar forward losses while computing different gradients, updating different parameter subsets, or applying optimizer state differently. The verifier compares gradient norms and parameter-update statistics:
\begin{equation}
\Delta_{\mathrm{grad}} =
\left|
\|\nabla_{\theta} L(P)\|_2 -
\|\nabla_{\hat{\theta}} L(\hat{P})\|_2
\right|,
\end{equation}
\begin{equation}
\Delta_{\mathrm{param}} =
\frac{\|\Delta \theta - \Delta \hat{\theta}\|_2}
{\|\Delta \theta\|_2 + \epsilon}.
\end{equation}
Beyond aggregate norms, the verifier records missing gradients, zero-gradient parameters, parameter-name mismatches, and update outliers. A normal forward loss with missing gradients indicates an automatic-differentiation or parameter-registration issue, whereas aligned gradients with divergent updates indicates an optimizer-state or parameter-step issue.

\paragraph{Repair guidance.}
The verifier emits the status of each check, the first failing stage, the supporting metrics, and likely repair cues. Execution failures guide compatibility edits, forward-value failures guide operator-semantics edits, and gradient/update failures guide backward or optimizer edits. The report turns the checks into an interface between validation and repair rather than a collection of independent metrics.

\subsection{Repair Loop}

\begin{figure*}[t]
\centering

\caption{The migration-repair loop on \texttt{torch4ms}/MindSpore. Translation, three-stage verification, targeted repair, and re-verification communicate through explicit artifacts. The TorchAX/JAX implementation uses the same checks.}
\label{fig:architecture}
\end{figure*}

Figure~\ref{fig:architecture} shows the iterative repair loop. A translator produces an initial candidate, the verifier compares paired source and candidate executions, and the fixer edits the candidate using the first failing stage and its evidence. An orchestrator controls repair rounds, stopping rules, and rollback of failed attempts. The same loop is used on both target frameworks.

The primary execution adapter uses \texttt{torch4ms}, which provides a PyTorch-style front end and dispatches operators, backward execution, and optimizer behavior to MindSpore-backed implementations. The second adapter uses TorchAX with JAX automatic differentiation and Optax updates. Both expose phase status, forward values, gradient evidence, and parameter-update statistics to the verifier.

For each checked training step, paired harnesses synchronize inputs, initialization, and optimizer settings before recording execution status, loss and optional module-level differences, gradient-norm differences, and parameter-update relative $\ell_2$ differences. A candidate is accepted only after its final version passes all three checks.

\section{Evaluation}

\subsection{Experimental Setup}
\label{sec:setup}
The evaluation answers three questions. Does LADDER improve verified repair success under a fixed budget (RQ1)? Why does the ordered feedback improve repair (RQ2)? Can the same procedure be applied to a second framework (RQ3)?

\textbf{Fault pool.}
The faults come from real migration failures rather than synthetic mutation. We migrated PyTorch training programs to the two target paths and recorded the cases that failed. The recurring failures fall into 25 categories, grouped by the stage at which each one surfaced and by the framework mechanism responsible. Each category is instantiated on two model families, giving a pool of 50 instances over CNN, image MLP, Transformer classifier, and tiny causal LM. The JAX pool is built the same way and contributes six MLP and CNN faults across the three stages.

\textbf{Repair scope.}
A repair scope is the code the fixer is permitted to edit. Candidate-level repairs may change only the migrated program. Core-operator repairs may also change the adapter's operator implementations. Core autograd/optimizer repairs may additionally change its differentiation and optimizer code. Scopes matter because the same observed failure can be fixed at more than one level, and an edit outside the assigned scope may mask the fault instead of repairing it.

\textbf{Conditions and baselines.}
We compare LADDER with two reduced forms of our own feedback, with direct LLM repair, and with the external systems SWE-agent, MatchFixAgent, Ivy, and \texttt{torch2jax}. The execution-only condition reports runtime status alone and withholds the forward-value and gradient/update comparisons. The unordered condition computes every check but presents them together without ranking them or naming the first stage that failed. It isolates what the ordering contributes, separately from what measuring the checks contributes. All six methods run on the same backbone (\texttt{deepseek-v4-flash}), the same decoding temperature (0.1), and the same four-attempt budget, and every method receives the same faulty candidate, so the efficiency differences reported below come from the feedback rather than from the model or the budget. MatchFixAgent additionally receives the healthy implementation of the changed function, which LADDER never sees; we keep that advantage in place rather than adjusting the denominator, so its numbers are an upper bound on what the strongest baseline achieves with strictly more information.

\textbf{Metrics.}
A repair counts as verified only when the patched candidate passes all three checks against the source execution. The patched candidate runs to completion and holds $\Delta_{\mathrm{loss}}\leq0.02$, $\Delta_{\mathrm{grad}}\leq0.05$, and $\Delta_{\mathrm{param}}\leq0.03$ at every checked step, using the quantities defined in Section~\ref{sec:hierarchy}. Repair@$k$ is the fraction of instances verified within $k$ repair attempts, so Repair@4 equals verified success under the four-attempt budget used throughout. The out-of-scope edit rate is the fraction of repairs that modified code outside the assigned scope. Tokens are prompt plus completion tokens summed over the pool, and time is wall-clock time divided by the 50 instances.

Because every result below is read off a comparison between two executions, we first confirm that the comparison stays quiet on known-good reference candidates. We ran CNN, MLP, Transformer, and tiny causal-LM trajectories for 50 steps over three seeds. The paired paths agree at every checked step. The largest maximum loss difference is $3.815\times10^{-6}$, and mean gradient-norm and parameter-update differences stay below $4\times10^{-8}$ and $3.9\times10^{-6}$. All reported differences below are attributable to the migration rather than to the measurement.

\subsection{RQ1: Overall Repair Effectiveness}
\label{sec:main-results}
\textbf{Setup.}
The primary experiment ran the full pool of 50 instances on the MindSpore path. All instances were hidden from the repair prompts, each allowed at most four repair attempts, and failed repairs were rolled back.

\textbf{Repair on the MindSpore path.}
Table~\ref{tab:main-results} shows a clear advantage for LADDER under the shared four-attempt budget. LADDER repairs 84.0\% of instances on the first attempt and 98.0\% by the second, and closes all 50 within the budget. The strongest external baseline, MatchFixAgent, reaches 74.0\% and 86.0\% at the same two checkpoints and finishes at 47/50. LADDER gains 10 percentage points on first-attempt repair and is the only method that closes the pool, verifying all 50 instances where the strongest baseline leaves three unresolved. The fault-stage columns show where the gain comes from: LADDER repairs all 16 gradient/update faults, compared with 13 for MatchFixAgent and 14 for direct LLM repair. Locating the failing stage also makes the repair cheaper rather than more expensive, at 0.191M tokens per pool and 21.8 seconds per instance against 5.205M tokens and 69.7 seconds for MatchFixAgent, a $27\times$ reduction in tokens and a $3.2\times$ reduction in time. The reduced internal controls establish the mechanism: adding undifferentiated checks gives only a small improvement, while identifying the first failing stage produces the large jump in repair success. Figure~\ref{fig:cost-quality} makes the joint quality--cost advantage visible.

\label{sec:ablations}
\textbf{Feedback detail.}
This experiment tests whether the improvement comes from the ordered feedback rather than from measuring more quantities. Four model families each received one fault per stage, drawn from the same 25-category pool, giving 12 controlled tasks. The repair loop ran under execution-only feedback, execution plus forward-value feedback, or the full LADDER report for 36 repair episodes under a four-round budget. Table~\ref{tab:feedback-ablation} shows a direct stepwise effect: execution-only feedback repairs the execution faults, adding the forward check repairs the numerical faults, and the full report repairs the gradient/update faults as well. Every successful repair completes in the first round. The correspondence between the added check and the newly repaired fault class shows why the ordered feedback, rather than a larger undifferentiated report, drives the improvement.

\subsection{Additional Analysis: Framework Documentation}
The experiments above vary the feedback. This one varies what the prompts know about the target framework, independently of the feedback, and locates where that knowledge matters. Besides the diagnosis, the fixer prompt can carry documentation for the target framework, covering its operator conventions and optimizer interfaces. Two experiments place it in turn at each end of the pipeline. The first holds the translator fixed and crosses pass/fail against layered feedback, with the documentation off against on. It covers 24 base tasks: 12 candidate-level, eight core-operator, and four core autograd/optimizer. Each ran under all four conditions with a four-round budget. The second moves the same documentation to the translator prompt. The fixer was disabled, so each run made one translation call and no repair round could compensate for a weak first attempt. Five held-out tasks ran at three repeats per condition.

Panel (a) of Table~\ref{tab:guidance-ablations} isolates the two factors in the fixer. Pass/fail feedback repairs nothing, with or without the documentation. Layered feedback repairs most tasks with the documentation off and remains the decisive factor when documentation is added. The documentation eliminates core-operator out-of-scope edits, while core autograd/optimizer repair remains the hardest scope in every condition.

Panel (b) reverses the picture at the translator. The documentation dominates one-shot translation. Without it, most outputs fail to compile and none complete the training check, and with it every output passes all three checks on the first attempt. Framework documentation matters most before any feedback exists, whereas panel (a) shows the feedback carrying the repair loop afterwards.

\subsection{Threats to Validity}
The evidence spans four model families, 25 fault categories, three repair scopes, and 50-step training trajectories on the MindSpore path, and the JAX study shows with six MLP/CNN faults that the same checks transfer to a different differentiation system and optimizer stack. Two boundaries are worth stating. The JAX result establishes transfer rather than breadth, and the checks compare controlled paired executions, so longer training horizons and further framework pairs are open questions rather than settled ones.

\section{Conclusion}

We introduced LADDER, which validates cross-framework training-code migration through execution, forward-value, and gradient/update checks in order. The first failing stage becomes targeted repair guidance, and the candidate is accepted only after all three checks pass. On 50 real MindSpore migration failures, LADDER reaches 84.0\% repair on the first attempt and closes the pool at 100\% within four attempts, using $27\times$ fewer tokens than the strongest repair baseline; it also repairs all six faults in the JAX study. Locating the failing stage therefore makes repair both more effective and cheaper, because a diagnosis that names the layer replaces the search that a whole-program verdict forces the repair loop to perform.
