\title{MARS: A Multi-Agent Repair System\\
for Training Code Migration via\\
Layered Diagnosis}

\author{Anonymous Authors}

\maketitle

\begin{abstract}
Migrating deep learning training code across frameworks requires preserving
training behavior. Large language models can produce executable translations
whose forward values agree with the source, yet whose gradients or parameter
updates are incorrect. Checking these stages exposes such faults, but error
propagation can produce multiple discrepancies and obscure which computation
needs repair. We propose MARS, a multi-agent repair system that uses
dependencies between training stages to organize verification evidence into
layered diagnoses. Its verifier compares execution status, forward values,
gradients, and parameter updates in training order, and reports the first
failing stage together with the supporting measurements. The translator
supplies an initial target program, and the repair agent uses this diagnosis
to edit the permitted code. An orchestrator coordinates translation,
verification, and repair, using updated diagnoses after each edit to guide
subsequent attempts within a fixed budget. On 50 MindSpore fault instances,
MARS achieves full acceptance within four attempts, with 84\% accepted on
the first attempt and approximately 29-fold lower token cost per accepted
repair than the strongest state-of-the-art baseline tested.
Experiments on MindSpore and JAX demonstrate the effectiveness of the same
diagnosis and repair procedure across target frameworks.
\end{abstract}



\section{Introduction}

Large language models (LLMs) support code translation across programming languages, reducing the manual effort needed to reuse existing implementations~\citep{he-etal-2025-execoder,macedo2024intertrans}. For deep learning, migration makes training programs available in another framework and its software and hardware ecosystem. Moving a program from PyTorch to MindSpore or JAX involves tensor computations, automatic differentiation, and optimizer behavior. The objective is to preserve the learning process implemented by the source program when it executes in the target runtime.

An executable translation can still change this learning process. It may produce different forward values, match the source loss but compute incorrect gradients, or update a different parameter set despite plausible gradients. Such failures arise from differences in operator conventions, differentiation interfaces, and optimizer semantics~\citep{paszke2019pytorch,mindspore2020whitepaper,google2025torchax}. Correct training behavior depends on several computations that execute in sequence. Verification must cover these computations and relate a detected discrepancy to the part of the program that requires correction.

Existing translation and repair systems provide several forms of evidence for making code edits. Unit tests check translated behavior~\citep{roziere2021unittests}, and interactive repair agents inspect source code and execution results~\citep{yang2024sweagent}. RepoTransAgent combines repository context, test failures, and reflection during refinement~\citep{guan2025repotransagent}. MatchFixAgent supplies reports from multiple semantic analyses to an agent that generates tests and repairs translations~\citep{ibrahimzada2025matchfixagent}. These systems provide increasingly rich evidence, but do not explicitly organize it according to the dependency structure of training computation. Consequently, when several downstream observations disagree, the repair process must still infer which discrepancy identifies the computation that requires correction and which are propagated consequences of an earlier failure.

Figure~\ref{fig:gradient-drift} illustrates the distinction between a failing computation and its later effects. The corresponding gradient or parameter update check detects each injected fault at step~1 in every run. The mean loss difference crosses its threshold only at steps 31 and 18 in panels (a) and (b), respectively. Incorrect updates therefore affect the training process before their accumulated effects become apparent in the loss.

The dependencies between training stages provide an order for interpreting these discrepancies. Execution failures must be resolved before numerical agreement can be assessed. An error in forward computation can also change gradients and parameter updates, while agreement in forward values allows later discrepancies to direct attention to differentiation or optimizer behavior. We therefore use the first failing training stage to direct repair. The diagnostic signals expose faults, and their order helps determine which computation the repair agent should inspect.

We introduce MARS (Multi-Agent Repair System), which implements this principle through layered diagnosis and a multi-agent repair framework. The verifier compares execution status, forward values, gradients, and parameter updates in training order, and reports the first failing stage with its measurements. A translator agent provides the initial target program, and a repair agent uses the diagnosis to edit the affected code. An orchestrator coordinates the three agents and supplies updated verification results for subsequent attempts. Experiments on MindSpore and JAX examine repair effectiveness, diagnosis, and the contribution of the feedback design. On the 50-instance MindSpore repair set, MARS achieves full acceptance within four attempts with approximately 29-fold lower token cost per accepted repair than MatchFixAgent. This paper makes three contributions.
\begin{itemize}
  \item We formulate training-code repair through diagnosis along ordered training computations, using the first failing stage to connect verification evidence with a repair target.
  \item We develop MARS, a layered multi-agent repair framework in which an orchestrator coordinates specialized translator, verifier, and repair agents around this diagnosis.
  \item We evaluate repair effectiveness and cross-framework applicability on MindSpore and JAX, and analyze diagnostic accuracy, signal coverage, and guidance for the failing stage.
\end{itemize}

\section{Related Work}
We organize related work by the evidence supplied for repair and how that evidence is used. The organization of diagnostic information and the division of work among agents address different aspects of a repair system.

\paragraph{Translation and verification evidence}
Neural code translation uses multilingual corpora, automated tests, and compiler representations to learn or validate translations~\citep{roziere2020transcoder,roziere2021unittests,szafraniec2023compiler}. ExeCoder represents functional semantics, syntax structure, and variable dependencies to improve translation~\citep{he-etal-2025-execoder}. InterTrans explores intermediate translation paths~\citep{macedo2024intertrans}. RepoTransAgent uses retrieved context, test failures, and reflection to refine translations~\citep{guan2025repotransagent}. MatchFixAgent combines analysis of control flow, data flow, input and output behavior, libraries, exceptions, and specifications with test generation and repair~\citep{ibrahimzada2025matchfixagent}. These methods provide representations, tests, or explanatory reports that help establish functional equivalence. MARS organizes paired training measurements by their computational dependencies and supplies the first failing stage as additional repair information.

\paragraph{Interactive program repair}
Automated program repair uses tests or semantic constraints to locate faults and guide patch generation~\citep{nguyen2013semfix}, while pretrained language models support patch generation from code and failure evidence~\citep{xia2023aprplm}. SWE-agent provides tools for repository navigation, editing, and test execution~\citep{yang2024sweagent}. Reflection, self-debugging, and executable code actions allow agents to use critiques and execution results during further repair~\citep{shinn2023reflexion,chen2023selfdebugging,wang2024codeact}. These workflows allow an agent to investigate a failure and revise its hypothesis. MARS provides a training-stage diagnosis and the corresponding measurements before the next edit, directing that investigation to the computation implicated by verification.

\paragraph{Conversion and differential testing}
Conversion tools provide mappings between framework interfaces. MindConverter targets MindSpore~\citep{mindspore2023mindconverter}; Ivy\footnote{\url{https://github.com/unifyai/ivy}} and \texttt{torch2jax}\footnote{\url{https://github.com/rdyro/torch2jax}} convert computations to JAX, while TorchAX exposes the PyTorch interface over a JAX backend~\citep{google2025torchax}. Differential testing compares related executions to expose compiler and program behavior differences~\citep{yang2011csmith,le2014emi}. Tests of deep learning systems also examine behavioral coverage and differences between networks~\citep{pei2017deepxplore,ma2018deepgauge}. Such comparisons depend on which observations are selected. MARS includes gradients and parameter updates, and uses the order of training computations to turn the observed differences into a repair target.

\paragraph{Multi-agent systems}
ChatDev and MetaGPT distribute software development among specialized roles~\citep{qian2023chatdev,hong2023metagpt}; AutoGen and AgentVerse organize communication and cooperation among agents~\citep{wu2023autogen,chen2023agentverse}. RepoTransAgent and MatchFixAgent apply specialization to repository context and translation verification, respectively~\citep{guan2025repotransagent,ibrahimzada2025matchfixagent}. Role decomposition determines how work is assigned, while a diagnostic structure determines what information guides a repair. MARS combines these two design choices by passing layered training diagnoses between specialized translation, verification, and repair agents under an orchestrator.

\subsection{Problem Setup}
Given a training program $P$ in a source framework $F_s$ and a target framework $F_t$, migration produces a target program $\hat{P}$ that preserves the source's training computations. We examine execution, forward values, gradients, and parameter updates. The repair task takes the source program, an initial target implementation, and the code the repair agent is permitted to edit. It returns a revised implementation that passes the specified verification checks. The permitted code can include the translated program or the framework implementation needed to execute it.

The verifier runs the source and target programs with controlled inputs, synchronized initialization, and matched optimizer settings. Let $\mathcal{O}_{t}(P)$ denote the observations at training step $t$, including execution status, selected outputs or losses, gradients, and parameter updates. Differences between $\mathcal{O}_{t}(P)$ and $\mathcal{O}_{t}(\hat{P})$ provide the evidence for diagnosis. Section~\ref{sec:setup} specifies the checked conditions, tolerances, and repair acceptance criteria used in the experiments.

\subsection{Layered Diagnosis}
MARS interprets verification evidence in the order required by training computation. Execution failures prevent numerical comparison. A discrepancy in forward computation can propagate to gradients and parameter updates, so several failing measurements may reflect the same earlier error. When forward values agree, discrepancies in gradients or parameter updates direct attention to differentiation or optimizer behavior. This dependency structure determines which failing stage guides the next repair.

Let $\mathcal{C}=(c_1,c_2,c_3)$ be the ordered diagnostic signals for execution, forward values, and gradients and parameter updates. Let $\mathrm{fail}(\hat{P})\subseteq\mathcal{C}$ contain the signals that detect a failure in the target implementation. MARS identifies the first failing stage,
\begin{equation}
v_{\mathrm{mars}}(\hat{P}) =
\begin{cases}
\min\left\{\, i : c_i \in \mathrm{fail}(\hat{P}) \,\right\}, & \mathrm{fail}(\hat{P}) \neq \emptyset,\\
\text{verified}, & \text{otherwise},
\end{cases}
\end{equation}
and reports its supporting measurements, available module locations, and exception details when execution fails. We refer to the selected stage together with its supporting measurements and available failure details as the layered diagnosis; when supplied to the repair agent with the editable code, this information forms the repair guidance. The stage index identifies the type of computation to inspect; the accompanying evidence guides the specific code edit. Index 1 directs attention to execution compatibility or operator implementation, index 2 to forward operator semantics, and index 3 to differentiation, parameter registration, or optimizer behavior. Later signals can provide supporting evidence for the diagnosis. The resulting layered diagnosis connects a detected discrepancy to a repair action.

\subsection{Diagnostic Signals}
\label{sec:hierarchy}

\paragraph{Execution signal}
The verifier checks whether $\hat{P}$ completes the training step under the target runtime. When execution fails, it records the operation, exception, and location available from the run. Failures can occur during module construction, data movement, forward computation, loss computation, backward computation, or parameter updates. These observations direct repair toward compatibility, operator implementation, device placement, data type, shape, or parameter registration. Numerical measurements are unavailable after an execution failure. Omitting a backward call can pass the execution check, leaving missing gradients and parameter updates to be detected by the third signal.

\paragraph{Signal for forward values}
Once both executions complete, the signal for forward values compares logits, selected intermediate activations, and losses under controlled inputs $(x,y)$ and synchronized initialization. The simplest comparison uses the loss difference,
\begin{equation}
\Delta_{\mathrm{loss}} =
\left| L(P; x, y) - L(\hat{P}; x, y) \right|.
\end{equation}
When intermediate outputs are available, the verifier also locates the earliest module whose difference exceeds tolerance. These comparisons provide evidence of mismatches in operators, reductions, broadcasting, normalization, or loss computation that would otherwise appear only in the final loss.

\paragraph{Gradient and parameter update signal}
The gradient and parameter update signal compares backward computation and optimizer behavior. The verifier measures differences in gradient norms and relative differences in parameter updates using
\begin{equation}
\Delta_{\mathrm{grad}} =
\left|
\|\nabla_{\theta} L(P)\|_2 -
\|\nabla_{\hat{\theta}} L(\hat{P})\|_2
\right|,
\end{equation}
\begin{equation}
\Delta_{\mathrm{param}} =
\frac{\|\Delta \theta - \Delta \hat{\theta}\|_2}
{\|\Delta \theta\|_2 + \epsilon}.
\end{equation}
Here $\Delta\theta$ and $\Delta\hat{\theta}$ are the source and target parameter updates, and $\epsilon$ prevents division by zero. The verifier also records missing gradients, parameters with zero gradients, mismatches in parameter names, and update outliers. Missing target gradients for parameters differentiated in the source direct attention to automatic differentiation or parameter registration. Matching gradient measurements with divergent parameter updates direct attention to optimizer behavior.

\subsection{Multi-Agent Repair}

The three agents in Figure~\ref{fig:architecture} use the diagnosis to connect verification with code generation. The translator receives the source program and target framework information and supplies an initial target program. The verifier runs the paired comparisons and produces the layered diagnosis. The repair agent receives the diagnosis, the permitted code, and feedback from the previous attempt, and produces an edit directed at the failing computation.

This role separation is deliberate: generation, measurement, repair, and control are assigned to distinct components. The translator generates a candidate without judging its correctness; the verifier derives correctness evidence from paired executions rather than relying on LLM self-assessment; and the repair agent acts on a structured diagnosis instead of re-inferring the failure from the full execution history. The orchestrator maintains cross-round state, enforces the attempt budget, and retains or rolls back edits according to verification results. This decomposition makes the layered diagnosis an explicit interface between verification and repair.

The orchestrator manages the interaction among these three agents. It invokes verification after an edit and uses the new report to evaluate the change. It retains edits that improve the verification score and rolls back those that do not, passing the previous attempt's outcome into subsequent repair. Verification success ends the loop; otherwise, the updated diagnosis guides further repair within the attempt budget. Each repair decision therefore uses evidence from the current execution and the preceding modification.

Execution adapters provide the observations used by the verifier in a common format. The primary adapter uses \texttt{torch4ms}, which provides the PyTorch programming interface and dispatches operators, backward computation, and optimizer behavior to MindSpore implementations.\ificlrfinal\footnote{The primary prototype repository is available at \url{https://gitee.com/feixiao13/ascend-torch4ms.git}.}\fi The second adapter uses TorchAX with JAX automatic differentiation and Optax updates. Both supply execution status, forward values, gradients, and parameter updates, allowing the diagnostic order and repair procedure to remain the same across target frameworks.

\section{Experiments}

\subsection{Experimental Setup}
\label{sec:setup}
The experiments answer four questions.

\begin{itemize}
  \item[\textbf{RQ1}] How does MARS compare with existing repair systems on repair acceptance under a fixed budget?
  \item[\textbf{RQ2}] Can the three signals distinguish fault classes and locate the failing stage?
  \item[\textbf{RQ3}] What information and guidance are necessary for effective repair?
  \item[\textbf{RQ4}] Does the same diagnosis and repair procedure apply across target frameworks?
\end{itemize}

We collected fault categories by migrating PyTorch training programs to the two target frameworks and recording the failures. The recurring failures fall into 25 categories, grouped by the stage at which they occur and the framework mechanism responsible. Ten categories cause execution failures, seven affect forward values, and eight affect gradients or parameter updates. The latter 15 produce executable programs with incorrect training behavior. We reproduce each observed category by injecting the fault into a correct implementation. This gives each instance a known fault location for evaluating diagnosis and reduces the variation present in failures collected directly from migrations. Creating instances of each category on two model families gives a set of 50 instances across CNN, image MLP, Transformer classifier, and tiny causal LM. The JAX set follows the same construction and contains six MLP and CNN faults across the three stages.

The required repair location specifies which code must change to correct a fault. One group permits changes only to the translated program. A second also permits changes to operator implementations in the compatibility layer, and a third additionally permits changes to that layer's automatic differentiation and optimizer code. An edit to code above the fault can hide its effect while leaving the faulty code unchanged. We identify the required repair location for each instance and restrict the repair agent to that code.

\subsection{RQ1: Overall Repair Effectiveness}
\label{sec:main-results}
MARS achieves higher repair acceptance under the shared attempt budget. On the 50 MindSpore instances in Table~\ref{tab:main-results}, its first-attempt acceptance is 84\%, compared with 74\% for MatchFixAgent, the strongest external baseline. The cumulative results in Figure~\ref{fig:repair-comparison} show that this advantage persists as the budget increases: MARS approaches full acceptance by the second attempt and resolves the remaining instance within four. The benefit is visible both when a repair must succeed immediately and when further revision is allowed.

The difference between systems is concentrated in faults that require changes to adapter code. SWE-agent and MatchFixAgent resolve every fault confined to the translated program, but leave faults in automatic differentiation or optimizer code unresolved. These faults affect the relation between gradients and parameters, where an executable program can produce a plausible loss despite incorrect learning behavior. MARS resolves all four such instances, including an instance missed by every baseline. This pattern identifies the training computations that account for the remaining repair difficulty. Section~\ref{sec:ablations} examines the contribution of diagnosis and repair guidance.

Higher acceptance is accompanied by lower repair cost. MARS uses approximately 29-fold fewer tokens and 3.4-fold less elapsed time per accepted repair than MatchFixAgent. Both measures include unsuccessful attempts and therefore account for the cost of reaching accepted repairs across the task set.

\paragraph{Detection by fault type}
The signals distinguish failures in different training computations. We isolate each fault's effect by synchronizing the translated model with the source at each checked step, over 50 steps, four model families, and three seeds. The intended signal detects all 36 injected faults across the three fault classes. Execution failures leave numerical measurements unavailable. Forward faults cross the loss threshold and can also affect gradients and parameter updates. Gradient faults leave the loss below threshold but affect gradients and parameter updates; parameter update faults affect only the update comparison. These patterns explain the diagnostic order: a discrepancy in an earlier computation can cause several later measurements to fail. On the tiny causal LM, the forward comparison detects the forward fault even though the gradient signal remains below threshold.

\paragraph{Detection latency}
Incorrect gradients and parameter updates can affect learning before they produce a detectable loss difference. In Figure~\ref{fig:gradient-drift}, the translated model retains its own state across steps, so incorrect updates accumulate and affect later forward computations. The corresponding gradient or parameter update check detects each fault immediately, while the mean loss difference crosses its threshold only after further training. The study covers four model families and three seeds for each fault type, giving 24 runs. This delay explains why agreement in forward values alone provides incomplete feedback for repairing training code.

\paragraph{Fault localization}
The first failing stage agrees with the fault-stage labels on 48 of 50 instances (96\% accuracy). The two disagreements involve overflow during mixed precision computation. Execution fails before a loss can be compared, so the execution signal reports the fault before the forward comparison can run. The diagnosis follows how the fault manifests in execution, which explains these differences from the injected-stage labels. MARS correctly localizes all execution faults (20/20) and all gradient and parameter update faults (16/16).

\subsection{RQ3: Ablation Study}
\label{sec:ablations}
We first ablate signal coverage and then stage selection and repair guidance, the two components of layered diagnosis. We also vary framework documentation as auxiliary context. The first two studies examine what diagnostic information enables repair, while the documentation study distinguishes program-specific diagnosis from general knowledge of the target framework.

\paragraph{Signal coverage}
The 12-task study shows that each additional signal enables repair of faults that earlier observations do not expose. With one fault per stage across four model families and a budget of four rounds, execution feedback repairs the four execution faults. Adding forward comparisons enables repair of the four forward faults, and gradient and parameter update feedback enables repair of the remaining four. Acceptance increases from 4/12 to 8/12 to 12/12, with every accepted repair completing in the first round. The change concerns which faults the feedback makes accessible to repair, rather than the number of iterations needed for an already detected fault.

\paragraph{Stage selection and repair guidance}
The 50-instance comparison holds the tasks, attempt budget, and LLM fixed. Execution only reports runtime status. All signals supplies all three signals without identifying the first failing stage or specifying which stage to repair. MARS adds stage selection and corresponding repair guidance. This comparison evaluates the two additions together.

Organizing the measurements into a diagnosis has a larger effect than supplying the measurements together. All signals adds only one accepted repair over execution feedback alone. MARS accepts 16 additional repairs over All signals, all in adapter code. Both conditions resolve the faults confined to the translated program; their difference emerges when repair requires examining operator implementations or automatic differentiation and optimizer code. The higher first-attempt acceptance and lower token cost further show that stage selection and guidance help the agent use the measurements to reach an accepted edit.

\paragraph{Framework documentation}
We separately evaluate the effect of framework documentation. Documentation describes operator conventions and optimizer interfaces, while diagnosis connects the current discrepancy to the computation requiring an edit. Table~\ref{tab:guidance-ablations} examines documentation during repair and initial translation separately.

During repair, documentation improves adherence to the permitted editing scope without consistently improving acceptance. In Table~\ref{tab:guidance-ablations}(a), it eliminates edits outside operator code while leaving the number of accepted operator repairs unchanged. It reduces acceptance for faults in the translated program, and neither documentation condition resolves the automatic differentiation and optimizer faults. The condition labeled layered feedback supports repair with documentation present or absent, whereas the pass/fail conditions accept no repairs. Framework conventions alone do not supply the evidence needed to diagnose the current failure.

Documentation has a more direct effect on initial translation. Without it, most generated programs fail to compile; with it, all translations pass training verification in one attempt (Table~\ref{tab:guidance-ablations}(b)). These results support supplying target framework conventions during code generation. During repair, the diagnostic measurements instead identify the discrepancy in the program being revised.

\subsection{RQ4: Generalization Across Frameworks}
\label{sec:generalization}

The same diagnostic order applies when JAX replaces MindSpore as the target framework. In Table~\ref{tab:framework-results}, MARS repairs faults in execution, forward computation, and gradients and parameter updates. The extra accepted repair over Direct LLM concerns forward computation in the CNN. The execution adapter changes how the observations are collected, while the layered diagnosis retains the same interpretation in the order of execution, forward values, and gradients and parameter updates.

\section{Conclusion}

We introduced MARS, a multi-agent repair system that uses the order of training computations to diagnose migration failures. The first failing stage connects verification evidence to a computation that requires correction, including faults that remain hidden in forward observations. MARS turns this diagnosis into code edits through specialized translation, verification, and repair agents coordinated by an orchestrator. Experiments on MindSpore and JAX show improved repair acceptance and lower token cost with the same diagnosis and repair procedure across target frameworks.
