\title{Beyond Executability: Hierarchical Feedback for Cross-Framework Training-Code Migration Repair}

\author{\IEEEauthorblockN{Anonymous Authors}
\IEEEauthorblockA{Anonymous Institution\\
anonymous@example.com}}

\maketitle

\begin{abstract}
Cross-framework migration of deep learning training code must preserve more than executability: a translated program must reproduce forward values, gradients, and parameter updates across different runtime and automatic-differentiation systems. Existing translation and repair pipelines often rely on binary tests or execution errors, allowing a runnable candidate to silently change training semantics. We introduce a hierarchical feedback framework that compares paired executions through execution, forward-numerical, and gradient/update signals and reports the first failing semantic layer for targeted repair and strict re-verification. A common diagnostic schema separates this feedback logic from backend-specific execution, allowing the same design to operate on both \texttt{torch4ms}/MindSpore-backed and TorchAX/JAX-backed migration paths. On a 12-task sentinel set, execution-only feedback repairs 4/12 tasks, execution-plus-numerical feedback repairs 8/12, and the full hierarchy repairs 12/12 under the same repair budget. The final real-LLM repair loop succeeds on 46/50 instances across 25 migration-fault categories. Without changing the feedback hierarchy, the TorchAX/JAX instantiation correctly localizes and repairs all six execution, numerical, and gradient/update faults. These results demonstrate that hierarchical semantic feedback provides actionable repair guidance and transfers across framework backends.
\end{abstract}

\begin{IEEEkeywords}
cross-framework migration, training-code translation, hierarchical feedback, program repair, differential testing
\end{IEEEkeywords}

\section{Introduction}

Large language models (LLMs) have made source-code translation increasingly practical, and recent systems improve generated programs through execution, repository context, and iterative feedback~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent,erer2025fullyautomated,gray2025workflows}. Cross-framework migration of deep learning (DL) training code raises a stricter problem. A migrated program must preserve not only control flow and API behavior, but also the tensor computations, automatic differentiation, optimizer state, and parameter updates that determine learning.

This requirement creates failures that ordinary executability checks cannot see. A translated training script may run successfully while producing different logits or losses. It may match the forward computation but propagate incorrect gradients, or compute plausible gradients while updating a different parameter set. Such failures arise across framework boundaries because runtimes differ in operator conventions, execution modes, differentiation interfaces, and optimizer semantics~\cite{paszke2019pytorch,mindspore2020whitepaper,google2025torchax}. A successful run is therefore only the first condition of a correct training migration.

Existing translation and repair systems commonly reduce feedback to compilation, execution, unit-test outcomes, or coarse error messages~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact,xia2023aprplm}. These signals can identify a broken program, but they do not reveal where a runnable training program first diverges from the source semantics. Binary feedback consequently maps execution failures, forward mismatches, and backward/update errors to the same outcome even though they require different repairs.

Our central observation is that training correctness has an ordered semantic structure. A candidate must first execute, then preserve the forward computation, and finally preserve gradients and parameter updates. The first failing layer in this sequence provides an actionable diagnosis: execution failures point to compatibility and lowering, forward failures point to operator semantics, and gradient/update failures point to automatic differentiation, parameter registration, or optimizer behavior.

Based on this observation, we propose a hierarchical feedback mechanism with execution, forward-numerical, and gradient/update signals. Paired source and candidate executions are normalized into a common diagnosis report, and a repair component uses the first failing layer to produce a targeted patch before strict re-verification. The feedback schema is independent of a particular backend. We instantiate the same hierarchy on a \texttt{torch4ms}/MindSpore-backed path\footnote{The primary prototype repository is available at \url{https://gitee.com/feixiao13/ascend-torch4ms.git}.} and on a TorchAX/JAX-backed path without redesigning its semantic layers.

The experiments support the approach at the effect, mechanism, and transfer levels. Under the same repair budget, execution-only feedback repairs 4/12 sentinel tasks, adding forward-numerical feedback repairs 8/12, and the full hierarchy repairs 12/12. On the 50-instance fault pool, the final real-LLM repair loop succeeds on 46/50 instances spanning 25 fault categories. The TorchAX/JAX instantiation correctly localizes and repairs all six faults, demonstrating that the hierarchy transfers across framework backends.

This paper makes three contributions:
\begin{itemize}
  \item We formulate cross-framework training-code migration as an ordered semantic validation problem and identify the first failing layer as the key signal for diagnosis-guided repair.
  \item We design a backend-independent hierarchy over execution, forward-numerical, and gradient/update behavior and integrate it with translation, targeted repair, and strict re-verification.
  \item We establish the effect and mechanism of hierarchical feedback on MindSpore-backed experiments and demonstrate cross-framework transfer through a second TorchAX/JAX-backed instantiation.
\end{itemize}

\section{Related Work}

\subsection{Code Translation and Validation}
Early neural code translation showed that programming languages can be translated without direct supervision when models are trained on multilingual code corpora~\cite{roziere2020transcoder}. Later work improved this line by using automated unit tests as validation and self-training signals~\cite{roziere2021unittests} and by introducing compiler representations to reduce source-target semantic gaps~\cite{szafraniec2023compiler}. Recent LLM-based systems further incorporate executability representations, intermediate translation paths, repository-level context, and validation~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent}. These studies motivate feedback-aware translation pipelines. Their validation, however, is typically organized around compilation, unit tests, or repository-level pass rates. DL framework migration needs a more specific validator that distinguishes execution failures, forward numerical divergence, and backward/update inconsistency in training code.

\subsection{Feedback-Driven Repair and Multi-Agent Systems}
Automated program repair has long used tests or semantic constraints to guide patch generation~\cite{nguyen2013semfix}. Large pre-trained language models have changed this space by making patch generation more fluent and enabling iterative repair from execution feedback~\cite{xia2023aprplm}. Reflection and agent-based methods feed natural-language feedback, self-debugging traces, or executable code actions back into the generation loop~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact}. Multi-agent LLM systems further show that role specialization, structured communication, shared artifacts, and explicit workflows can improve complex software tasks~\cite{qian2023chatdev,hong2023metagpt,wu2023autogen,chen2023agentverse}. These approaches motivate our translator--verifier--fixer decomposition; our verifier contributes the migration-specific semantic layers that connect agent feedback to targeted training-code repair.

\subsection{Framework Migration and Runtime Bridging}
Modern DL frameworks expose different execution models and optimization abstractions. PyTorch emphasizes an imperative, dynamic front end~\cite{paszke2019pytorch}, whereas TensorFlow demonstrates large-scale dataflow execution for machine learning systems~\cite{abadi2016tensorflow}; compiler infrastructures such as MLIR further show how domain-specific computation can be lowered through extensible intermediate representations~\cite{lattner2021mlir}. Existing migration and bridging tools address parts of this compatibility problem. MindConverter targets migration from third-party frameworks to MindSpore~\cite{mindspore2023mindconverter}. Runtime bridges such as TorchAX preserve a PyTorch-style front end while dispatching execution to another backend~\cite{google2025torchax}. Our hierarchy builds on these migration paths by diagnosing preservation at the execution, forward, gradient, and update levels.

\subsection{Differential and DL-System Testing}
Differential testing has been effective for finding compiler and program-analysis bugs by comparing semantically related executions~\cite{yang2011csmith,le2014emi}. Testing work for DL systems has similarly explored behavioral coverage and differential-style validation of neural networks~\cite{pei2017deepxplore,ma2018deepgauge}. These methods establish behavioral discrepancy as useful diagnostic evidence. Our work specializes differential validation to DL training migration and uses it to build hierarchical feedback over execution status, forward numerical behavior, gradient behavior, and parameter updates.

\section{Problem Formulation}

\subsection{Task Formulation}
Given a training program $P$ in a source framework $F_s$ and a target framework path $F_t$, the migration task is to produce a candidate $\hat{P}$ that executes under $F_t$ while preserving the training semantics of $P$. Training semantics includes the quantities that determine whether learning remains equivalent in practice: compatible tensors and modules, comparable forward values and losses, comparable gradients, and parameter updates with comparable direction and magnitude. Our primary instantiation migrates PyTorch training programs to a \texttt{torch4ms}/MindSpore-backed path, and the transfer study instantiates the same formulation on a TorchAX/JAX-backed path.

We evaluate correctness through paired executions under controlled inputs, synchronized initialization, and matched optimizer settings. Let $\mathcal{O}_{t}(P)$ denote the observable state at training step $t$: execution status, selected outputs or losses, gradients, and parameter-update statistics. A candidate is semantically aligned when $\mathcal{O}_{t}(\hat{P})$ remains within predefined tolerances of $\mathcal{O}_{t}(P)$ for the checked steps. The formulation focuses on framework-independent training observables, allowing the same diagnostic logic to compare executions produced by different target runtimes.

\subsection{Diagnosis-Guided Repair Objective}
The repair objective is not merely to assign a final pass/fail label. It is to identify the earliest semantic layer at which $\hat{P}$ departs from $P$ and expose evidence that supports a corresponding edit. Execution failures call for compatibility or lowering changes; forward mismatches call for operator-semantics changes; and gradient/update mismatches call for differentiation, parameter-registration, or optimizer changes. A useful verifier must therefore preserve this diagnostic structure in the feedback delivered to the repair component.

\section{Hierarchical Semantic Feedback}

\subsection{Design Principle}
Training-code correctness is evaluated as an ordered hierarchy. A migrated program must first execute under the target backend, then preserve the forward computation, and finally preserve the backward and update behavior that determines learning. We therefore organize validation around three semantic layers:
\[
\text{execution} \rightarrow \text{forward numerical} \rightarrow \text{gradient/update}.
\]
This ordering defines both a testing procedure and a repair policy. A deeper comparison is interpreted only after its prerequisites are available, and the first failing layer becomes the primary diagnosis. Later signals may provide supporting evidence, but they do not replace the earliest point at which the source and candidate executions diverge.

\subsection{Framework Adapter Interface}
The hierarchy operates on a common observation schema rather than framework-specific error formats. Each target path supplies an execution adapter that runs the candidate and exposes phase status, selected forward values, gradients, and parameter deltas in a normalized report. Runtime-specific details remain inside the adapter; the layer ordering, comparison metrics, diagnosis format, and repair routing remain unchanged. The \texttt{torch4ms}/MindSpore and TorchAX/JAX instantiations use this same interface, which makes cross-framework transfer a property of the design rather than a separate repair strategy.

\subsection{Execution Signal}
The execution signal checks whether $\hat{P}$ can complete the required training step under the target backend. It records whether module construction, data movement, forward execution, loss computation, backward execution, and optimizer stepping terminate without runtime failure. When a failure occurs, the verifier stores the exception type, stack location, operator or API name when available, tensor shape and dtype context, and the phase in which the failure appears. Typical failure classes include missing operators, unsupported lowering paths, interface mismatches, device-placement errors, dtype incompatibilities, shape errors, and invalid optimizer or parameter-registration behavior.

\subsection{Forward-Numerical Signal}
The forward-numerical signal checks whether the computation of $\hat{P}$ remains aligned with $P$ once both executions complete. Under controlled inputs $(x,y)$ and synchronized initialization, the verifier compares quantities such as logits, selected intermediate activations, and losses. The minimal scalar comparison is
\begin{equation}
\Delta_{\mathrm{loss}} =
\left| L(P; x, y) - L(\hat{P}; x, y) \right|.
\end{equation}
When intermediate outputs are available, the verifier also computes output- or layer-level discrepancies and locates the earliest module whose difference exceeds tolerance. This localization is important because an end-to-end loss mismatch can be caused by an early operator difference, a reduction convention, a broadcasting rule, a normalization layer, or a later loss-function discrepancy.

\subsection{Gradient and Update Signal}
The gradient/update signal checks whether the migrated candidate preserves backward and optimizer behavior. This layer is necessary because two programs may produce similar forward losses while computing different gradients, updating different parameter subsets, or applying optimizer state differently. The verifier compares gradient norms and parameter-update statistics:
\begin{equation}
\Delta_{\mathrm{grad}} =
\left|
\|\nabla_{\theta} L(P)\|_2 -
\|\nabla_{\hat{\theta}} L(\hat{P})\|_2
\right|,
\end{equation}
\begin{equation}
\Delta_{\mathrm{param}} =
\frac{\|\Delta \theta - \Delta \hat{\theta}\|_2}
{\|\Delta \theta\|_2 + \epsilon}.
\end{equation}
In addition to aggregate norms, the verifier can record missing gradients, zero-gradient parameters, parameter-name mismatches, and update outliers. A normal forward loss with missing gradients suggests an automatic-differentiation or parameter-registration issue, whereas aligned gradients with divergent updates suggests an optimizer-state or parameter-step issue.

\subsection{Structured Diagnosis and Repair Routing}
The verifier emits the status of each layer, the first failing layer, the supporting metrics, and a bounded set of root-cause hints. The repair component routes execution failures to compatibility edits, forward-numerical failures to operator-semantics edits, and gradient/update failures to backward or optimizer edits. This report turns the hierarchy into an actionable interface between validation and repair instead of a collection of independent metrics.

\section{Cross-Framework Migration Repair System}

\begin{figure*}[t]
\centering
\includegraphics[width=0.97\textwidth]{figures_to_be_redrawed/hierarchical_feedback_architecture.png}
\caption{Primary \texttt{torch4ms}/MindSpore-backed instantiation of the migration-repair system. Translation, hierarchical verification, diagnosis-guided repair, and strict re-verification communicate through explicit artifacts. The same execution, forward-numerical, and gradient/update diagnosis schema is reused by the TorchAX/JAX instantiation.}
\label{fig:architecture}
\end{figure*}

Figure~\ref{fig:architecture} shows the primary instantiation as an iterative repair system rather than a single-pass converter. A translator produces an initial target-path candidate, the verifier compares paired source and candidate executions, and the fixer applies bounded patches from the structured diagnosis. An orchestrator controls rounds, stopping rules, rollback, and snapshot logging. The components communicate through a shared artifact pool containing the source program, candidate program, diagnosis report, and patch log, so every repair action is tied to an executable artifact and explicit evidence.

The primary execution adapter uses \texttt{torch4ms}, which provides a PyTorch-style front end and dispatches operators, backward execution, and optimizer behavior to MindSpore-backed implementations. The transfer instantiation uses TorchAX to execute through a JAX-backed target path. Both adapters expose the same phase status, forward values, gradient evidence, and parameter-update statistics to the verifier. The repair loop therefore changes its framework-specific execution layer while preserving the diagnostic hierarchy and diagnosis-to-repair policy.

For each migration anchor, paired harnesses synchronize inputs, initialization, and optimizer settings before recording execution status, loss and optional layer-level differences, gradient-norm differences, and parameter-update relative $\ell_2$ differences. A candidate is accepted only after the final snapshot passes strict re-verification across all configured semantic layers.

\section{Evaluation}

\subsection{Research Questions}
We organize the evaluation around three questions that follow the paper's main claim:
\begin{itemize}
  \item \textbf{RQ1: Repair effect.} Does hierarchical feedback improve strict repair success under the same repair budget?
  \item \textbf{RQ2: Diagnostic mechanism.} Do the semantic layers expose the intended failure types and support repair across failure layers and edit scopes?
  \item \textbf{RQ3: Cross-framework transfer.} Does the same hierarchy localize and repair faults on a second framework path without redesigning the feedback schema?
\end{itemize}

\subsection{Experimental Scope and Metrics}
The evaluation uses vision and language training programs, controlled migration faults, and real-LLM translation and repair. The MindSpore-backed experiments span CNN, MLP, Transformer, and tiny causal-LM families, three semantic failure layers, and candidate, core-operator, and core-autograd/optimizer edit scopes. The cross-framework experiment instantiates the same hierarchy on a TorchAX/JAX-backed path with CNN and MLP tasks and representative faults from all three semantic layers.

The main task-level metrics are strict repair success, Repair@$k$, median repair rounds, and out-of-scope edit rate where applicable. Signal-level metrics include execution status, loss and optional layer-level differences, gradient-norm difference, and parameter-update relative $\ell_2$ difference. Strict success requires the repaired artifact to satisfy the complete verification outcome defined for its experiment.

\subsection{Feedback Mechanism Ablation}
\textbf{Design.}
To evaluate whether richer feedback improves repair under the same repair budget, we ran a real-LLM feedback-granularity ablation on four model families: CNN, image MLP, Transformer classifier, and tiny causal LM. Each model was evaluated under three sentinel fault categories: an execution fault (EX-01), a numerical fault (NU-04), and a gradient/update fault (GR-07). This balanced clean-alias sentinel set isolates the contribution of each semantic layer. The repair loop used one of three feedback conditions: execution-only feedback, execution plus numerical feedback, or the full execution/numerical/gradient-update diagnosis. This produced 36 repair episodes in total. Every episode records final execution, numerical, and gradient/update pass fields, and strict success required all three recorded outcomes to pass.

\textbf{Results.}
Table~\ref{tab:feedback-ablation} shows a stepwise improvement as the repair loop receives the semantic layer needed for each fault class. Execution-only feedback repaired 4 of 12 tasks under strict verification, execution plus numerical feedback repaired 8 of 12, and the full feedback stack repaired all 12 tasks. Because every successful repair completed in the first round, Repair@1 and Repair@4 follow the same 33.3\%, 66.7\%, and 100.0\% pattern. Runtime evidence repairs all four execution faults. Numerical diagnostics add all four numerical repairs, and gradient/update diagnostics add all four gradient/update repairs.

This controlled ablation establishes the causal role of the hierarchy. Execution feedback handles runtime failures, forward-numerical feedback exposes runnable programs with incorrect computation, and gradient/update feedback resolves failures that remain invisible after execution and loss checks. The broader evaluation in Section~\ref{sec:fixer-capability} then measures the complete repair system over 25 fault categories.

\subsection{Cross-Framework Transfer to TorchAX/JAX}
\label{sec:torchax-transfer}
\textbf{Design.}
We instantiated the same execution, forward-numerical, and gradient/update hierarchy on a TorchAX/JAX-backed target path. The layer order, normalized diagnosis fields, first-failure rule, and repair routing were unchanged. The evaluation used MLP and CNN tasks with two execution, two numerical, and two gradient/update faults. For each fault, we first measured first-layer localization and then ran candidate-level repair with the same strict re-verification policy.

\textbf{Results.}
Panel (c) of Table~\ref{tab:end-to-end-results} shows complete transfer of the hierarchy to the TorchAX/JAX-backed path. The verifier localizes all six faults at the correct semantic layer, and every diagnosis leads to a candidate that passes strict re-verification in one round. The execution cases expose runtime failures, the forward-numerical cases expose output or loss divergence, and the gradient/update cases expose missing-gradient and parameter-update evidence. Achieving 6/6 localization and 6/6 strict repair without changing the feedback schema demonstrates cross-framework portability of the diagnosis-to-repair mechanism.

\subsubsection{One-Shot Translator Guidance}
\label{sec:translator-guide-ablation}
\textbf{Design.}
To isolate Translator guidance, we disabled the Fixer and made one Translator call per run. Five held-out migration tasks---Image MLP, CNN, ResNet, Transformer classifier, and tiny causal LM---were evaluated over three repeats in each condition, giving 15 runs without the guide and 15 with it.

\textbf{Results.}
Panel (b) of Table~\ref{tab:guidance-ablations} shows that without Translator guidance, 2/15 outputs compile and execute, and none complete the training check. With guidance, all 15 outputs pass compilation, execution, training, and Translation Success@1. Together with the Fixer ablation, this result separates the strong effect of platform knowledge during initial translation from its different effect during iterative repair.

\subsection{Limitations and Threats to Validity}
The evaluation covers two target backend paths, four model families, 25 fault categories, three repair scopes, and 50-step training trajectories. Repository-scale programs, longer training runs, and additional framework pairs will test the hierarchy at larger scale. Complete per-step gradient capture and versioned prompt, verifier, dataset, and batch manifests will strengthen future replications.


\section{Conclusion}

Cross-framework training-code migration requires feedback that reaches beyond executability. We introduced an ordered hierarchy over execution, forward-numerical, and gradient/update semantics and used the first failing layer to connect validation with targeted repair. The MindSpore-backed experiments show a stepwise repair gain as semantic feedback is added and a 46/50 strict success rate on the final fault pool. Reusing the same hierarchy on a TorchAX/JAX-backed path yields 6/6 first-layer localization and 6/6 strict repair, demonstrating cross-framework transfer without redesigning the diagnosis schema. These results establish hierarchical semantic feedback as a practical foundation for training-code migration repair. Future work will broaden the framework pairs and program scale, strengthen complete gradient/update collection, and evaluate longer generated training trajectories.
