\title{Beyond Executability: Hierarchical Feedback for Cross-Framework Training-Code Migration Repair}

\author{\IEEEauthorblockN{Anonymous Authors}
\IEEEauthorblockA{Anonymous Institution\\
anonymous@example.com}}

\maketitle

\begin{abstract}
Cross-framework migration of deep learning training code must preserve more than executability, since a translated program must reproduce forward values, gradients, and parameter updates across different runtime and automatic-differentiation systems. Existing translation and repair pipelines reduce feedback to binary tests or execution errors. A runnable candidate can therefore change training semantics without producing any signal that something is wrong. We argue that the granularity of repair feedback is itself a critical but overlooked factor in migration correctness. To this end, we introduce a hierarchical feedback framework that compares paired source and candidate executions through execution, forward-numerical, and gradient/update signals, reporting the first failing semantic layer as the diagnosis that drives targeted repair and re-verification. A common adapter interface keeps this logic independent of the target backend. We implement the framework on MindSpore and JAX target paths. Extensive experiments across both paths demonstrate that the full hierarchy verifies more migrations than execution-only feedback under a matched repair budget. It also exceeds the strongest blind-repair baseline on a controlled fault pool while using an order of magnitude fewer tokens. The same hierarchy transfers to a PyTorch-to-JAX path on which existing conversion tools fail outright.
\end{abstract}

\begin{IEEEkeywords}
cross-framework migration, training-code translation, hierarchical feedback, program repair, differential testing
\end{IEEEkeywords}

\section{Introduction}

Large language models (LLMs) have made source-code translation increasingly practical, and recent systems improve generated programs through execution, repository context, and iterative feedback~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent,erer2025fullyautomated,gray2025workflows}. Cross-framework migration of deep learning (DL) training code raises a stricter problem. A migrated program must preserve not only control flow and API behavior, but also the tensor computations, automatic differentiation, optimizer state, and parameter updates that determine learning.

This requirement creates failures that ordinary executability checks cannot see. A translated training script may run successfully while producing different logits or losses. It may match the forward computation but propagate incorrect gradients, or compute plausible gradients while updating a different parameter set. Such failures arise across framework boundaries because runtimes differ in operator conventions, execution modes, differentiation interfaces, and optimizer semantics~\cite{paszke2019pytorch,mindspore2020whitepaper,google2025torchax}. A successful run is therefore only the first condition of a correct training migration.

Existing systems supply repair feedback in three main ways. Translation pipelines validate against a single outcome such as compilation, unit tests, or repository-level pass rates~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent}. Repair agents explore the program until a test or execution trace exposes the fault~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact,xia2023aprplm,yang2024sweagent}. Conversion and differential-testing tools compare a converted output or a single behavioral property against a reference~\cite{mindspore2023mindconverter,yang2011csmith,pei2017deepxplore}. Despite their differences, all three collapse distinct semantic failures onto one verdict. Execution failures, forward mismatches, and backward/update errors therefore arrive as the same signal even though each requires a different repair.

Our central observation is that training correctness has an ordered semantic structure. A candidate must first execute, then preserve the forward computation, and finally preserve gradients and parameter updates. The first failing layer in this sequence provides an actionable diagnosis: execution failures point to compatibility and lowering, forward failures point to operator semantics, and gradient/update failures point to automatic differentiation, parameter registration, or optimizer behavior.

Based on this observation, we propose a hierarchical feedback mechanism with execution, forward-numerical, and gradient/update signals. Paired source and candidate executions are normalized into a common diagnosis report, and a repair component uses the first failing layer to produce a targeted patch before re-verification. A common adapter interface separates this feedback logic from backend execution. We implement the method on \texttt{torch4ms}/MindSpore\footnote{The primary prototype repository is available at \url{https://gitee.com/feixiao13/ascend-torch4ms.git}.} and TorchAX/JAX.

The evaluation covers the effect of feedback granularity, the diagnostic behavior of each individual layer, comparison against repair agents, and transfer to a second backend. Under a matched repair budget, richer feedback repairs strictly more faults at every level of the hierarchy.

This paper makes three contributions:
\begin{itemize}
  \item We formulate cross-framework training-code migration as an ordered semantic validation problem and identify the first failing layer as the key signal for diagnosis-guided repair.
  \item We design a backend-independent hierarchy over execution, forward-numerical, and gradient/update behavior and integrate it with translation, targeted repair, and re-verification.
  \item We implement the method on MindSpore and JAX target paths and establish its effect, mechanism, and advantage over repair baselines.
\end{itemize}

\section{Related Work}

\subsection{Translation with Outcome-Level Validation}
Early neural code translation showed that programming languages can be translated without direct supervision from multilingual code corpora~\cite{roziere2020transcoder}.
Later work added automated unit tests as validation and self-training signals~\cite{roziere2021unittests}.
Compiler representations were then introduced to narrow source--target semantic gaps~\cite{szafraniec2023compiler}.
Recent LLM-based systems incorporate executability representations, intermediate translation paths, and repository-level context~\cite{he-etal-2025-execoder,macedo2024intertrans,guan2025repotransagent}.
MatchFixAgent decomposes repository-level equivalence checking across specialized agents and repairs the inequivalences it finds~\cite{ibrahimzada2025matchfixagent}.
We use it as an external repair baseline.
In each case validation is organized around a single outcome: compilation, unit-test results, or repository-level pass rates.
Our work instead treats validation as an ordered set of semantic layers, so a passing outcome is no longer the unit of feedback.

\subsection{Repair Driven by Execution Feedback}
Automated program repair has long used tests or semantic constraints to guide patch generation~\cite{nguyen2013semfix}.
Pre-trained language models made patch generation more fluent and enabled iterative repair from execution feedback~\cite{xia2023aprplm}.
Repository-level agents such as SWE-agent use interactive tools and test feedback to edit code iteratively~\cite{yang2024sweagent}.
Reflection and agent-based methods feed natural-language critiques, self-debugging traces, or executable code actions back into the generation loop~\cite{shinn2023reflexion,chen2023selfdebugging,wang2024codeact}.
Multi-agent systems show that role specialization, structured communication, and explicit workflows improve complex software tasks~\cite{qian2023chatdev,hong2023metagpt,wu2023autogen,chen2023agentverse}.
These approaches motivate our translator--verifier--fixer decomposition.
They locate a fault by exploring the program until a test or trace reveals it.
We instead read the fault location from the layer at which the two executions first diverge, which removes the search rather than guiding it.

\subsection{Cross-System Comparison and Framework Bridging}
Modern DL frameworks expose different execution models and optimization abstractions.
PyTorch emphasizes an imperative, dynamic front end~\cite{paszke2019pytorch}, whereas TensorFlow demonstrates large-scale dataflow execution~\cite{abadi2016tensorflow}.
Compiler infrastructures such as MLIR lower domain-specific computation through extensible intermediate representations~\cite{lattner2021mlir}.
Bridging tools address parts of the resulting compatibility problem.
MindConverter targets migration from third-party frameworks to MindSpore~\cite{mindspore2023mindconverter}.
Ivy\footnote{\url{https://github.com/unifyai/ivy}} and \texttt{torch2jax}\footnote{\url{https://github.com/rdyro/torch2jax}} convert PyTorch computations to JAX, while TorchAX preserves a PyTorch-style front end over a JAX backend~\cite{google2025torchax}.
A separate line compares semantically related executions to expose defects.
Differential testing has found compiler and program-analysis bugs this way~\cite{yang2011csmith,le2014emi}, and DL-system testing has explored behavioral coverage and differential-style validation of networks~\cite{pei2017deepxplore,ma2018deepgauge}.
Both lines compare either the conversion output or a single behavioral property.
We instead compare paired training executions at several ordered semantic depths, so the comparison itself yields the repair target.

\section{Problem Formulation}

\subsection{Task Formulation}
Given a training program $P$ in a source framework $F_s$ and a target framework path $F_t$, the migration task is to produce a candidate $\hat{P}$ that executes under $F_t$ while preserving the training semantics of $P$. Training semantics includes the quantities that determine whether learning remains equivalent in practice: compatible tensors and modules, comparable forward values and losses, comparable gradients, and parameter updates with comparable direction and magnitude. We instantiate this formulation on \texttt{torch4ms}/MindSpore and TorchAX/JAX target paths.

We evaluate correctness through paired executions under controlled inputs, synchronized initialization, and matched optimizer settings. Let $\mathcal{O}_{t}(P)$ denote the observable state at training step $t$: execution status, selected outputs or losses, gradients, and parameter-update statistics. A candidate is semantically aligned when $\mathcal{O}_{t}(\hat{P})$ remains within predefined tolerances of $\mathcal{O}_{t}(P)$ for the checked steps. All observables are framework-independent. The same diagnostic logic therefore compares executions produced by different target runtimes.

\subsection{Diagnosis-Guided Repair Objective}
The repair objective identifies the earliest semantic layer at which $\hat{P}$ departs from $P$ and exposes evidence for the corresponding edit. Execution failures call for compatibility or lowering changes; forward mismatches call for operator-semantics changes; and gradient/update mismatches call for differentiation, parameter-registration, or optimizer changes. Each layer implies its own edit. The verifier preserves this structure in the feedback delivered to the repair component.

\section{Hierarchical Semantic Feedback}

\subsection{Design Principle}
Training-code correctness is evaluated as an ordered hierarchy. A migrated program must first execute under the target backend, then preserve the forward computation, and finally preserve the backward and update behavior that determines learning. The order is not a convention. Each layer is only measurable once the layer above it holds. We therefore organize validation around three semantic layers:
\[
\text{execution} \rightarrow \text{forward numerical} \rightarrow \text{gradient/update}.
\]
This ordering defines both a testing procedure and a repair policy. A deeper comparison is interpreted only after its prerequisites are available, and the first failing layer becomes the primary diagnosis. Later signals may provide supporting evidence, but they do not replace the earliest point at which the source and candidate executions diverge.

\subsection{Framework Adapter Interface}
The hierarchy operates on a common observation schema rather than framework-specific error formats. Each target path supplies an execution adapter that runs the candidate and exposes phase status, selected forward values, gradients, and parameter deltas in a normalized report. The adapter is the only backend-specific component. Runtime-specific details remain inside it; the layer ordering, comparison metrics, diagnosis format, and repair routing remain unchanged.

\subsection{Execution Signal}
The execution signal checks whether $\hat{P}$ can complete the required training step under the target backend, recording whether module construction, data movement, forward execution, loss computation, backward execution, and optimizer stepping each terminate without runtime failure. When a failure occurs, the verifier stores the exception type, stack location, operator or API name when available, tensor shape and dtype context, and the phase in which the failure appears. The phase is what makes the record actionable. Typical failure classes include missing operators, unsupported lowering paths, interface mismatches, device-placement errors, dtype incompatibilities, shape errors, and invalid parameter registration.

\subsection{Forward-Numerical Signal}
The forward-numerical signal checks whether the computation of $\hat{P}$ remains aligned with $P$ once both executions complete. Under controlled inputs $(x,y)$ and synchronized initialization, the verifier compares quantities such as logits, selected intermediate activations, and losses. The minimal scalar comparison is
\begin{equation}
\Delta_{\mathrm{loss}} =
\left| L(P; x, y) - L(\hat{P}; x, y) \right|.
\end{equation}
When intermediate outputs are available, the verifier also computes output- and layer-level discrepancies and locates the earliest module whose difference exceeds tolerance. This localization matters because an end-to-end loss mismatch can originate in an early operator difference, a reduction convention, a broadcasting rule, a normalization layer, or the loss function itself. The scalar alone cannot separate these causes. The earliest exceeding module can.

\subsection{Gradient and Update Signal}
The gradient/update signal checks whether the migrated candidate preserves backward and optimizer behavior. This layer is necessary because two programs may produce similar forward losses while computing different gradients, updating different parameter subsets, or applying optimizer state differently. The verifier compares gradient norms and parameter-update statistics:
\begin{equation}
\Delta_{\mathrm{grad}} =
\left|
\|\nabla_{\theta} L(P)\|_2 -
\|\nabla_{\hat{\theta}} L(\hat{P})\|_2
\right|,
\end{equation}
\begin{equation}
\Delta_{\mathrm{param}} =
\frac{\|\Delta \theta - \Delta \hat{\theta}\|_2}
{\|\Delta \theta\|_2 + \epsilon}.
\end{equation}
Beyond aggregate norms, the verifier records missing gradients, zero-gradient parameters, parameter-name mismatches, and update outliers. Norms alone conflate two failures. These fields separate them. A normal forward loss with missing gradients suggests an automatic-differentiation or parameter-registration issue, whereas aligned gradients with divergent updates suggests an optimizer-state or parameter-step issue.

\subsection{Structured Diagnosis and Repair Routing}
The verifier emits the status of each layer, the first failing layer, the supporting metrics, and a bounded set of root-cause hints. The repair component routes execution failures to compatibility edits, forward-numerical failures to operator-semantics edits, and gradient/update failures to backward or optimizer edits. This mapping is fixed rather than learned. The report therefore turns the hierarchy into an actionable interface between validation and repair instead of a collection of independent metrics.

\section{Cross-Framework Migration Repair System}

\begin{figure*}[t]
\centering
\includegraphics[width=0.97\textwidth]{figures_to_be_redrawed/hierarchical_feedback_architecture.png}
\caption{The migration-repair system on \texttt{torch4ms}/MindSpore. Translation, hierarchical verification, diagnosis-guided repair, and re-verification communicate through explicit artifacts. The TorchAX/JAX implementation uses the same diagnosis schema.}
\label{fig:architecture}
\end{figure*}

Figure~\ref{fig:architecture} shows the primary instantiation as an iterative repair system rather than a single-pass converter. A translator produces an initial target-path candidate, the verifier compares paired source and candidate executions, and the fixer edits the candidate using the structured diagnosis. Each patch is restricted to the repair scope the diagnosis points to, so a gradient-layer diagnosis cannot trigger an unrelated rewrite elsewhere. An orchestrator controls rounds, stopping rules, and reversion of failed attempts. No component holds hidden state. The components communicate through a shared pool of files containing the source program, candidate program, diagnosis report, and patch log, so every repair action is tied to an executable artifact and explicit evidence.

The primary execution adapter uses \texttt{torch4ms}, which provides a PyTorch-style front end and dispatches operators, backward execution, and optimizer behavior to MindSpore-backed implementations. The second adapter uses TorchAX with JAX automatic differentiation and Optax updates. Both expose phase status, forward values, gradient evidence, and parameter-update statistics to the verifier.

For each checked training step, paired harnesses synchronize inputs, initialization, and optimizer settings before recording execution status, loss and optional layer-level differences, gradient-norm differences, and parameter-update relative $\ell_2$ differences. A candidate is accepted only after its final version passes re-verification at every configured semantic layer.

\section{Evaluation}

\subsection{Research Questions}
We organize the evaluation around three questions that follow the paper's main claim:
\begin{itemize}
  \item \textbf{RQ1: Repair effect.} Does hierarchical feedback improve verified repair success under the same repair budget?
  \item \textbf{RQ2: Diagnostic mechanism.} Do the semantic layers expose the intended failure types and support repair across semantic layers and repair scopes?
  \item \textbf{RQ3: Comparison and transfer.} How does hierarchical feedback compare with repair and conversion baselines across MindSpore and JAX target paths?
\end{itemize}

\subsection{Experimental Scope and Metrics}
The evaluation uses vision and language training programs, controlled migration faults, and real-LLM translation and repair. The MindSpore experiments span CNN, MLP, Transformer, and tiny causal-LM families. They cover three semantic layers and three repair scopes: candidate code, core operators, and core autograd/optimizer behavior. The JAX experiment uses MLP and CNN faults at all three layers. We compare the hierarchy with two internal feedback conditions, direct LLM repair, SWE-agent, MatchFixAgent, Ivy, and \texttt{torch2jax}. The execution-only condition reports runtime status alone and withholds the numerical and gradient comparisons. The unordered condition computes every signal but presents them together as one undifferentiated set, without ranking them or naming the layer that failed first. It therefore isolates what the ordering contributes, separately from what measuring the signals contributes. Every method receives the same faulty candidate and the same repair budget. Where an external interface exposes more of the reference implementation than ours sees, we report that asymmetry with the result rather than adjusting the denominator.

The main task-level metrics are verified repair success, Repair@$k$, median repair rounds, and out-of-scope edit rate where applicable. Signal-level metrics include execution status, loss and optional layer-level differences, gradient-norm difference, and parameter-update relative $\ell_2$ difference. A repair is verified only when its final artifact passes the fault-specific checks.

\subsection{Feedback Mechanism Ablation}
\textbf{Design.}
We ran a real-LLM feedback-granularity ablation under a fixed repair budget. The ablation covers four model families: CNN, image MLP, Transformer classifier, and tiny causal LM. Each model was evaluated under exactly one fault per semantic layer: an execution fault, a numerical fault, and a gradient/update fault. Fault identifiers carry a layer prefix and an index within the 25-category pool, so the three chosen here are EX-01, NU-04, and GR-07. One fault per layer per model keeps the design balanced, which is what isolates the contribution of each layer. The repair loop used one of three feedback conditions: execution-only feedback, execution plus numerical feedback, or the full diagnosis. This produced 36 repair episodes in total. Every episode records final execution, numerical, and gradient/update pass fields. Verified success requires all three outcomes to pass.

\textbf{Results.}
Table~\ref{tab:feedback-ablation} shows a stepwise improvement as the repair loop receives the layer each fault class requires. Each added layer repairs exactly the fault class it targets and leaves the others unchanged. Execution feedback alone resolves the execution faults and none of the deeper ones. Adding numerical feedback resolves the numerical faults, and adding gradient/update feedback resolves the remainder. Every successful repair completes in the first round, so Repair@1 and Repair@4 coincide.

The layer-to-fault correspondence is exact in this controlled setting, which supports the ordering as the source of the improvement. Execution feedback handles runtime failures, forward-numerical feedback exposes runnable programs with incorrect computation, and gradient/update feedback resolves failures that remain invisible after execution and loss checks. Section~\ref{sec:fixer-capability} measures the complete system over 25 fault categories.

\subsection{Auxiliary Component Analyses}

\subsubsection{Framework Documentation in the Fixer}
\label{sec:fixer-guide-ablation}
\textbf{Design.}
Besides the diagnosis, the fixer prompt can carry documentation for the target framework, covering its operator conventions and optimizer interfaces. The experiment crosses pass/fail against hierarchical feedback with this documentation off against on, holding the translator fixed. It contains 24 base tasks over CNN and MLP models: 12 candidate-level tasks, eight core-operator tasks, and four core autograd/optimizer tasks. \subsubsection{Framework Documentation in the Translator}
\label{sec:translator-guide-ablation}
\textbf{Design.}
We next moved the same documentation to the translator prompt. The fixer was disabled and each run made one translation call, so no repair round could compensate for a weak first attempt. Five held-out migration tasks were evaluated: Image MLP, CNN, ResNet, Transformer classifier, and tiny causal LM. Each task ran three repeats per condition, giving 15 runs without the documentation and 15 with it.

\textbf{Results.}
Panel (b) of Table~\ref{tab:guidance-ablations} shows that the documentation dominates one-shot translation. Without it, most outputs fail to compile and none complete the training check. With it, every output passes all three checks on the first attempt. Framework documentation therefore matters most before any feedback exists, whereas panel (a) shows the feedback carrying the repair loop afterwards.

\subsection{Training-Path Validation}
\label{sec:training-consistency}
\textbf{Design.}
Before interpreting any repair outcome, we check the paired execution paths against known-good oracle candidates. A disagreement here would mean the verifier reports differences that the migration did not cause. The evaluation contains CNN, NLP, Transformer, and tiny causal-LM trajectories, each run for 50 steps over three seeds. The per-step thresholds are $\Delta_{\mathrm{loss}}\leq0.02$, $\Delta_{\mathrm{grad}}\leq0.05$, and $\Delta_{\mathrm{param}}\leq0.03$.

\subsection{Limitations and Threats to Validity}
The MindSpore study covers four model families, 25 fault categories, three repair scopes, and 50-step training trajectories; the JAX transfer study covers six MLP/CNN faults. The results establish transfer across two target paths.


\section{Conclusion}

We introduced a hierarchical feedback framework for cross-framework training-code migration that validates execution, forward-numerical, and gradient/update semantics in order. Specifically, the framework reports the first failing semantic layer and routes that diagnosis to a targeted repair and re-verification loop. This design makes repair guidance actionable at the layer where the divergence originates, rather than at the point of failure. A common adapter interface keeps the hierarchy independent of the target runtime and its differentiation system. Experiments across MindSpore and JAX target paths demonstrate that hierarchical feedback repairs more faults than execution-only and agent baselines at substantially lower token cost.
